<h3 id="q1">1. Устройство сайта и его аппаратно-программного окружения</h3>

**Аппаратное окружение (где живёт сайт):**

- **Клиент** — устройство пользователя (ПК, смартфон, планшет, телевизор, умные часы). Именно с него пользователь отправляет запросы на сервер. Клиент может быть как мощным компьютером, так и маломощным устройством с ограниченными ресурсами.
- **Сервер** — мощный компьютер (или целая сеть серверов), который круглосуточно хранит файлы сайта, обрабатывает запросы и отдаёт ответы. Серверы обычно имеют большое количество оперативной памяти, мощные процессоры и быстрые диски (SSD). Крупные проекты используют кластеры из сотен серверов.
- **Сеть** — интернет-каналы, роутеры, DNS-серверы, оптические магистрали. Это всё, что обеспечивает передачу данных между клиентом и сервером. Скорость и стабильность сети напрямую влияют на работу сайта.

**Программное окружение (из чего состоит):**

- **На сервере:**
  - **Операционная система** — обычно Linux (Ubuntu, CentOS, Debian) реже Windows Server. Linux выбирают за стабильность, безопасность и бесплатность.
  - **Веб-сервер** — программа, которая принимает HTTP-запросы и отдаёт ответы. Самые популярные: Nginx (высокая производительность, обработка статики) и Apache (гибкость, множество модулей).
  - **Интерпретатор** — исполняет код на серверном языке: PHP, Node.js (JavaScript), Python, Ruby, Java, C#. Выбор зависит от проекта и команды.
  - **СУБД (система управления базами данных)** — хранит и управляет данными. Популярные: MySQL, PostgreSQL (реляционные), MongoDB (документная), Redis (кэш/ключ-значение).

- **На клиенте:**
  - **Браузер** — программа, которая отправляет запросы, получает ответы, рендерит HTML/CSS/JS и исполняет JavaScript. Основные движки: Blink (Chrome, Edge), Gecko (Firefox), WebKit (Safari). Браузер также хранит кэш, куки, локальное хранилище.

**Схема работы (полный цикл):**
```
1. Пользователь вводит URL в адресную строку браузера.
2. Браузер отправляет DNS-запрос для получения IP-адреса сервера.
3. DNS-сервер возвращает IP-адрес.
4. Браузер устанавливает TCP-соединение с сервером (3-way handshake).
5. Браузер отправляет HTTP/HTTPS-запрос (метод, путь, заголовки, тело).
6. Сервер обрабатывает запрос (читает файлы, выполняет код, работает с БД).
7. Сервер формирует HTTP-ответ (статус, заголовки, тело — HTML+CSS+JS).
8. Ответ передаётся обратно клиенту.
9. Браузер отображает страницу (парсинг, рендеринг, исполнение скриптов).
```

<h3 id="q2">2. Определение веб-сайта, его передача и отображение в браузере</h3>

**Веб-сайт** — это набор связанных веб-страниц, объединённых под одним доменом, написанных на HTML/CSS/JS, доступных через HTTP/HTTPS. Сайты бывают:
- **Статические** — страницы не меняются, сервер просто отдаёт готовые HTML-файлы.
- **Динамические** — страницы генерируются сервером на основе данных из БД (интернет-магазины, соцсети).
- **Одностраничные приложения (SPA)** — весь сайт загружается один раз, а навигация происходит через JavaScript (React, Vue, Angular).

**Передача (HTTP/HTTPS протокол):**

- Браузер отправляет **HTTP-запрос**, который содержит:
  - **Метод** (GET — получить, POST — отправить, PUT — обновить, DELETE — удалить, PATCH — частично обновить)
  - **Путь** (/index.html, /api/users)
  - **Заголовки** (User-Agent, Accept, Cookie, Authorization)
  - **Тело** (для POST/PUT — данные формы, JSON)

- Сервер отвечает **HTTP-ответом**:
  - **Статус-код** (200 OK, 301 Moved Permanently, 404 Not Found, 500 Internal Server Error)
  - **Заголовки** (Content-Type, Content-Length, Cache-Control, Set-Cookie)
  - **Тело** (HTML, CSS, JS, JSON, картинки, файлы)

- **HTTPS** — это HTTP поверх SSL/TLS, все данные шифруются. Обязателен для любого современного сайта (особенно с формами и авторизацией).

**Отображение (критический путь рендеринга):**

1. **Загрузка HTML** → браузер получает HTML-код и начинает его парсить.
2. **Построение DOM-дерева** (Document Object Model) — браузер превращает HTML в дерево объектов.
3. **Загрузка CSS** → браузер загружает CSS-файлы и строит **CSSOM-дерево** (CSS Object Model).
4. **Объединение в Render Tree** — DOM + CSSOM объединяются в дерево рендеринга (только видимые элементы).
5. **Вычисление геометрии (Layout / Reflow)** — браузер вычисляет размеры и позиции каждого элемента на странице.
6. **Отрисовка пикселей (Paint)** — браузер заполняет пиксели цветом, текстом, тенями.
7. **Композиция слоёв (Composite)** — браузер объединяет несколько слоёв в финальное изображение.

**Что блокирует рендеринг:**
- CSS — блокирует рендеринг (без CSSOM не построить Render Tree).
- JS — блокирует построение DOM (пока скрипт не загрузится и не выполнится).
- Решение: `async` и `defer` для JS, критические CSS инлайнить.

<h3 id="q3">3. Сборка простого сайта: особенности, стек технологий. Дизайн, фронтенд, бекенд, база данных</h3>

**Особенности простого сайта:**
- Без сложной логики (нет авторизации, платежей, чатов).
- До 5–10 страниц.
- Может быть статическим или с минимальной динамикой (форма обратной связи).
- Быстрое создание, низкие требования к хостингу.
- Подходит для лендингов, портфолио, сайтов-визиток, блогов.

**Стек технологий для простого сайта:**

| Тип | Технологии | Когда использовать |
|------|------------|-------------------|
| Фронтенд | HTML5, CSS3, чистый JavaScript | Для любого сайта |
| Фреймворк фронтенда | Vue.js / Svelte / React (легче всего Svelte) | Если нужна реактивность и интерактивность |
| Бекенд (если нужен) | Python + Flask, Node.js + Express, PHP (без фреймворка) | Для обработки форм, подключения БД |
| База данных (если нужна) | SQLite (просто, файловая) → потом PostgreSQL | Для хранения данных (пользователи, посты) |
| Сборка | Vite, Parcel (для новичков — Live Server VS Code) | Для разработки с горячей перезагрузкой |
| Хостинг | Netlify, Vercel, GitHub Pages (для статики) / Beget, Timeweb (shared) | Для простого размещения |

**Структура простого сайта:**
```
site/
├── index.html
├── about.html
├── contact.html
├── css/
│   └── style.css
├── js/
│   └── main.js
└── images/
    ├── logo.png
    └── hero.jpg
```

**Дизайн:**
- Разрабатывается в Figma, Sketch, Photoshop или сразу в коде.
- Включает: цветовую схему, типографику, компоновку элементов.
- Можно использовать готовые UI-киты (Material UI, Tailwind UI).

**Фронтенд:**
- Код, который выполняется в браузере пользователя.
- Отвечает за клики, анимации, валидацию форм, запросы к API.
- Состоит из HTML (структура), CSS (стили), JavaScript (поведение).

**Бекенд:**
- Код, который выполняется на сервере.
- Обрабатывает запросы от фронтенда.
- Работает с базой данных (CRUD: Create, Read, Update, Delete).
- Обеспечивает авторизацию, безопасность, бизнес-логику.
- Пример: проверка, есть ли товар на складе, расчёт стоимости доставки.

**База данных:**
- Хранилище информации: пользователи, товары, заказы, статьи.
- Реляционные (SQL) — данные в таблицах со связями.
- NoSQL — документы (JSON), ключ-значение, графы.

**Связь между компонентами:**
```
Фронтенд → AJAX/fetch → API бекенда → БД → ответ → Фронтенд
```

<h3 id="q4">4. Дизайн-концепция сайта. Определение, подходы, примеры</h3>

**Дизайн-концепция** — это общая идея и визуальный язык сайта: цвета, шрифты, ритмы, настроение, атмосфера. Это не просто «как выглядит», а «что чувствует пользователь». Концепция определяет все визуальные решения и делает сайт целостным.

**Основные подходы в веб-дизайне:**

| Подход | Описание | Особенности |
|--------|----------|-------------|
| **Flat design** | Плоские элементы, без теней, градиентов, объёма | Минимализм, чёткие границы, яркие цвета. Пример: Google Material Design |
| **Neumorphism** | Объёмный, похожий на мягкий пластик | Свет и тень как у физических объектов. Сложно в реализации. Для портфолио |
| **Brutalism** | Нарочито грубо, битые сетки, резкие цвета | "Анти-дизайн", эстетика 90-х. Привлекает внимание |
| **Минимализм** | Много воздуха, минимум деталей, большие заголовки | Фокус на контенте. Пример: Apple |
| **Skeuomorphism** | Имитация реальных материалов (кожа, дерево, бумага) | Было популярно в iOS 6, сейчас почти не используется |
| **Dark mode** | Тёмный фон, светлый текст | Экономит батарею, современный вид |
| **Glassmorphism** | Стеклянный эффект: размытый фон, полупрозрачность | Стильно, но сложно с доступностью |

**Примеры дизайн-концепций для разных ниш:**
- **Сайт студии** — элегантная типографика, плавные скроллы, монохромная палитра, тонкие анимации.
- **Интернет-магазин** — яркие карточки товаров, крупные кнопки «Купить», система скидок, фильтры.
- **Медицинский портал** — спокойные цвета (синий, зелёный), чёткая структура, безопасность.
- **Детский проект** — яркие цвета, скруглённые углы, игровые анимации, крупные элементы.

**Как создать дизайн-концепцию:**
1. Изучить ЦА и их предпочтения.
2. Собрать референсы (примеры удачных решений).
3. Создать Moodboard (доска настроения) — подборка цветов, шрифтов, изображений.
4. Разработать фирменный стиль (логотип, цвета, шрифты, паттерны).
5. Тестировать на пользователях.

<h3 id="q5">5. Экранная типографика, специальные символы и общие правила вёрстки текста в вебе</h3>

**Особенности экранной типографики:**
- **Засечные шрифты** (Times New Roman, Georgia) хуже читаются на экране, особенно в мелком размере. **Без засечек** (Arial, Roboto, Open Sans, Inter) — лучше и для экрана, и для мобильных.
- **Размер текста:** базовый размер для веба — 16px. Рекомендуемый диапазон для основного текста — 16–18px. Нельзя меньше 14px (нарушает доступность).
- **Межстрочный интервал (line-height):** должно быть 1.4–1.5 от размера шрифта. Например, 16px → line-height: 24px (1.5). Меньше 1.4 — текст плохо читается.
- **Ширина строки:** оптимально 50–75 символов на строку (включая пробелы). Если строка длиннее — глаза устают. Управляется через `max-width` блока текста.
- **Интервал между буквами (letter-spacing):** для заголовков можно увеличивать (0.5–1px), для основного текста — оставлять 0.

**Специальные символы (HTML-мнемоники):**

| Символ | Мнемоника | Описание |
|--------|-----------|----------|
| ` ` (пробел) | `&nbsp;` | Неразрывный пробел (не переносить на новую строку) |
| `<` | `&lt;` | Меньше (для отображения тегов) |
| `>` | `&gt;` | Больше |
| `&` | `&amp;` | Амперсанд |
| `©` | `&copy;` | Знак копирайта |
| `—` | `&mdash;` | Длинное тире |
| `–` | `&ndash;` | Среднее тире (диапазон: 10–20) |
| `«` `»` | `&laquo;` `&raquo;` | Кавычки-ёлочки |
| `™` | `&trade;` | Торговая марка |
| `°` | `&deg;` | Градус |
| `×` | `&times;` | Умножить (знак) |
| `÷` | `&divide;` | Деление |

**Правила вёрстки текста:**
- **Никогда не использовать несколько пробелов подряд** (браузер схлопывает их в один). Для отступов используйте CSS (`margin`, `padding`).
- **Заголовки строго по иерархии:** H1 — главный заголовок страницы (один на страницу), H2 — подзаголовки, H3 — подразделы. Не пропускайте уровни (H1 → H2 → H3, не H1 → H3 → H4).
- **Параграфы** — только через тег `<p>`, никогда через `<br>` (двойной `<br>` — антипаттерн).
- **Для списков** используйте `<ul>` (ненумерованный) и `<ol>` (нумерованный), а внутри — `<li>`.
- **Цитаты** — через `<blockquote>`.
- **Код** — через `<code>`.
- **Жирный шрифт** — `<strong>` (логическое ударение) или `<b>` (визуальное).
- **Курсив** — `<em>` (логическое) или `<i>` (визуальное).

<h3 id="q6">6. Проектирование и дизайн веб-форм</h3>

**Принципы проектирования форм:**

1. **Логичная группировка полей:** объединяйте связанные поля (например, «Личные данные», «Адрес доставки», «Платёжные реквизиты»). Это уменьшает когнитивную нагрузку.
2. **Метки (label) всегда над полем или слева:** для мобильных — над полем (экономит ширину). Для десктопа допустимо слева. Метка должна быть кликабельна (привязана к input через `for`).
3. **Порядок полей от простого к сложному:** сначала лёгкие вопросы (имя, email), потом сложные (адрес, детали заказа).
4. **Обязательные поля помечать звёздочкой *:** и добавлять пояснение, что эти поля обязательны.
5. **Подсказки (placeholder):** не должны заменять label. Placeholder — это пример ввода, а не название поля.
6. **Одна цель на форму:** форма регистрации не должна содержать опросов.
7. **Многостраничные формы:** для длинных форм разбивайте на шаги с индикатором прогресса (3–5 шагов).

**Дизайн формы:**

- **Высота поля:** ~ 40px (для десктопа), 44–48px (для мобильных — под палец).
- **Понятный фокус:** `outline: none` + добавьте свой стиль (цветная рамка, тень). Это важно для пользователей с клавиатуры.
- **Валидация «на лету»:** зелёная галочка, если введено правильно; красная рамка, если ошибка. Сообщение об ошибке под полем, а не в алерте.
- **Кнопка отправки:** должна быть заметной (контрастный цвет), большой, с текстом действия («Зарегистрироваться», «Отправить заказ», а не просто «Отправить»).
- **Вторичные действия:** ссылка «Забыли пароль» должна быть меньше по размеру и не конкурировать с основной кнопкой.

**Пример формы логина:**
```
[Email] ________________
[Пароль] ________________
[✓] Запомнить меня
[Войти]  [Забыли пароль?]
```

**Советы по UX форм:**
- После отправки показывайте успешное сообщение.
- Сохраняйте данные формы, если пользователь обновил страницу (localStorage).
- Используйте автозаполнение (`autocomplete="email"`).
- Для телефона — `inputmode="numeric"`, для email — `type="email"`.

<h3 id="q7">7. Реализация веб-форм и отправки информации</h3>

**HTML-структура формы:**

```html
<form id="contact-form" method="POST" action="/send.php" novalidate>
  <!-- novalidate отключает встроенную валидацию -->
  
  <div class="form-group">
    <label for="email">Email *</label>
    <input type="email" id="email" name="email" required placeholder="ivan@mail.ru">
    <div class="error-message" data-error="email">Введите корректный email</div>
  </div>
  
  <div class="form-group">
    <label for="message">Сообщение *</label>
    <textarea id="message" name="message" required minlength="10"></textarea>
  </div>
  
  <button type="submit">Отправить сообщение</button>
</form>
```

**Отправка без перезагрузки (JavaScript + Fetch API):**

```javascript
const form = document.getElementById('contact-form');

form.addEventListener('submit', async (e) => {
  e.preventDefault(); // Останавливаем стандартную отправку
  
  // Сбор данных
  const formData = new FormData(form);
  
  // Отправка
  try {
    const res = await fetch('/api/contact', {
      method: 'POST',
      body: formData  // Формат multipart/form-data
    });
    
    if (res.ok) {
      alert('Сообщение отправлено!');
      form.reset();
    } else {
      throw new Error('Ошибка сервера');
    }
  } catch (error) {
    alert('Ошибка отправки: ' + error.message);
  }
});
```

**Отправка в формате JSON:**

```javascript
const data = {
  email: document.getElementById('email').value,
  message: document.getElementById('message').value
};

await fetch('/api/contact', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(data)
});
```

**Бекенд (Node.js + Express):**

```javascript
const express = require('express');
const app = express();

app.use(express.json());
app.use(express.urlencoded({ extended: true }));

app.post('/api/contact', async (req, res) => {
  const { email, message } = req.body;
  
  // Валидация на бекенде (обязательно!)
  if (!email || !message || message.length < 10) {
    return res.status(400).json({ error: 'Неверные данные' });
  }
  
  try {
    // Сохранить в БД
    await db.query('INSERT INTO messages (email, message) VALUES (?, ?)', [email, message]);
    
    // Отправить письмо
    await sendEmail(email, message);
    
    res.json({ success: true });
  } catch (error) {
    res.status(500).json({ error: 'Ошибка сервера' });
  }
});
```

**Валидация на бекенде — обязательна!** Фронтенд-валидацию можно обойти (инструменты разработчика). Бекенд — последняя линия защиты.

<h3 id="q8">8. Валидация сайта по стандартам HTML и CSS</h3>

**Зачем нужна валидация:**
- **Кроссбраузерность:** код, соответствующий стандартам, одинаково работает во всех браузерах.
- **Доступность:** валидный код легче читается скринридерами.
- **SEO:** поисковики лучше индексируют валидные страницы.
- **Поддержка:** валидный код легче поддерживать и изменять.
- **Будущее:** код по стандартам будет работать в новых версиях браузеров.

**Инструменты валидации:**
- **W3C HTML Validator** (validator.w3.org) — проверяет HTML-код. Можно загрузить файл, вставить код или проверить страницу по URL.
- **W3C CSS Validator** (jigsaw.w3.org/css-validator) — проверяет CSS-код.
- **Встроенные в IDE** — VS Code с расширениями (HTMLHint, Stylelint).
- **Lighthouse в DevTools** — проверяет доступность, производительность, SEO.

**Что проверять в HTML:**
- Все ли теги закрыты (`<div>...</div>`, `<img>` — самозакрывающийся).
- Нет ли устаревших атрибутов (`align`, `bgcolor`, `border` в таблицах). Использовать CSS вместо них.
- Атрибут `alt` у картинок (обязательно для доступности).
- ARIA-атрибуты там, где они нужны (`role`, `aria-label`).
- Вложенность тегов (например, `<li>` только внутри `<ul>` или `<ol>`).
- Правильные типы для `input` (`email`, `number`, `tel`, `date`).

**Что проверять в CSS:**
- Валидность цветов (`#FFF` или `#ffffff`, а не `#ff`).
- Валидность единиц измерения (`px`, `em`, `rem`, `%`, `vh`, `vw`).
- Нет ли свойств, которые не существуют или устарели.
- Правильный синтаксис (закрытые скобки, точки с запятой).

**Советы:**
- Используйте препроцессоры (Sass, Less) — они помогают писать более чистый код.
- Проверяйте сайт в разных браузерах (Chrome, Firefox, Safari, Edge).
- Включите автоформатирование в IDE (Prettier).

<h3 id="q9">9. Оптимизация показателей производительности сайта</h3>

**Ключевые метрики (Core Web Vitals от Google):**

| Метрика | Что измеряет | Норма |
|---------|--------------|-------|
| **LCP** (Largest Contentful Paint) | Загрузка самого большого видимого элемента | < 2.5 сек |
| **FID** (First Input Delay) | Задержка реакции на первое действие пользователя | < 100 мс |
| **CLS** (Cumulative Layout Shift) | Неожиданные сдвиги элементов при загрузке | < 0.1 |

**Дополнительные метрики:**
- **TTFB** (Time To First Byte) — время до первого байта ответа (сервер).
- **FCP** (First Contentful Paint) — появление первого контента.
- **TTI** (Time To Interactive) — когда страница полностью готова к взаимодействию.

**Что делать для улучшения производительности:**

1. **Сжимать изображения:**
   - Использовать формат **WebP** вместо JPEG/PNG (меньше размер при лучшем качестве).
   - Подключать AVIF для ещё большего сжатия.
   - Устанавливать правильные размеры (`width` и `height`).
   - Использовать lazy-loading (`loading="lazy"`).

2. **Кэширование браузера:**
   - Установить правильные заголовки `Cache-Control` для статики (CSS, JS, изображения).
   - Использовать ETag для проверки изменений.

3. **Минификация CSS/JS:**
   - Удалять пробелы, комментарии, лишние точки с запятой.
   - Инструменты: Terser (JS), CSSNano (CSS), UglifyJS.
   - В сборщиках (Webpack, Vite) это включается автоматически для production.

4. **Удалить неиспользуемый CSS:**
   - Инструменты: PurgeCSS, UnusedCSS.
   - Особенно важно для больших фреймворков (Bootstrap, Tailwind).

5. **Подключить CDN (Content Delivery Network):**
   - Файлы раздаются с серверов, географически близких к пользователю.
   - Используйте CDN для популярных библиотек (jQuery, React, Font Awesome) — они могут уже быть в кэше браузера пользователя.

6. **Отложить загрузку скриптов:**
   - `async` — скрипт загружается параллельно и выполняется сразу после загрузки.
   - `defer` — скрипт загружается параллельно, но выполняется после полной загрузки HTML.
   - Для критических скриптов — инлайн в HTML.

7. **Использовать HTTP/2 и HTTP/3:**
   - Множественные соединения, параллельная загрузка ресурсов.

8. **Оптимизировать шрифты:**
   - Использовать `font-display: swap` — текст виден сразу, даже если шрифт не загрузился.
   - Подключать только нужные начертания (weights) и форматы (woff2).

9. **Серверный рендеринг (SSR):** для SPA ускоряет первичную загрузку.
10. **Preload и Preconnect:** подсказывать браузеру, какие ресурсы скоро понадобятся.

<h3 id="q10">10. Развитие IT-специалиста. Оформление кейсов, портфолио, рост</h3>

**Оформление кейсов (Case Study):**

1. **Проблема** (Problem) — что было не так, с чем пришёл клиент.
2. **Решение** (Solution) — как вы решили проблему (дизайн, архитектура, технологии).
3. **Технологии** (Tech Stack) — что использовали (фреймворки, библиотеки, сервисы).
4. **Результат** (Results) — цифры и факты, что изменилось (на сколько выросла конверсия, уменьшилось время загрузки, увеличился трафик).
5. **Сложности** (Challenges) — что было трудно и как вы справились.
6. **Выводы** (Learnings) — чему вы научились.

- **Код должен быть:** читаемым, документированным, с тестами.

**Каналы для портфолио:**
- Личный сайт (всегда лучшее решение).

<h3 id="q11">11. Введение в проектную деятельность. Жизненный цикл продукта. Команда и процессы</h3>

**Жизненный цикл продукта (Product Lifecycle):**

1. **Идея** (Idea) — зарождение мысли, исследование рынка, поиск проблемы.
2. **Анализ** (Analysis) — исследование ЦА, конкурентов, формирование требований.
3. **Проектирование** (Design) — UX/UI-дизайн, архитектура системы, прототипы.
4. **Разработка** (Development) — написание кода (frontend + backend).
5. **Тестирование** (Testing) — QA, проверка, фиксы багов.
6. **Запуск** (Launch) — релиз на production, открытие доступа пользователям.
7. **Поддержка** (Support) — исправление ошибок, обновления, добавление фич.
8. **Утилизация или реинкарнация** — закрытие проекта или новый цикл развития.

**Команда разработки (роли):**

| Роль | Ответственность |
|------|-----------------|
| **Project Manager (PM)** | Управляет сроками, бюджетом, коммуникацией, ресурсами |
| **Product Owner (PO)** | Отвечает за требования (голос клиента) — в Scrum |
| **Аналитик** | Собирает и формализует требования, пишет документацию |
| **Дизайнер (UX/UI)** | Проектирует интерфейсы, макеты, прототипы |
| **Frontend-разработчик** | Пишет код интерфейса (HTML/CSS/JS) |
| **Backend-разработчик** | Пишет серверную логику, API, работает с БД |
| **QA (Quality Assurance)** | Тестирует продукт, находит баги |
| **DevOps** | Настраивает сервера, деплой, CI/CD, мониторинг |
| **Системный архитектор** | Проектирует архитектуру системы (для крупных проектов) |
| **UX-исследователь** | Изучает пользователей, проводит интервью (в больших компаниях) |

**Процессы в проекте:**
- **Daily-митинги (Daily Standup)** — каждый день по 15 минут: что сделал, что буду делать, какие проблемы.
- **Планирование (Sprint Planning)** — в начале каждого спринта планируем задачи на 1–4 недели.
- **Ретроспектива (Sprint Retrospective)** — в конце спринта обсуждаем, что было хорошо, что плохо, что улучшить.
- **Grooming (Backlog Refinement)** — пересмотр бэклога, расстановка приоритетов.
- **Review (Sprint Review)** — демонстрация сделанного за спринт заказчику.

**Таск-трекеры:** Jira, Trello, Asana, ClickUp, YouTrack.

<h3 id="q12">12. Методологии веб-разработки</h3>

**Waterfall (Водопад):**
- Жёсткая последовательность этапов: требования → дизайн → разработка → тестирование → запуск.
- Каждый этап завершается полностью, прежде чем начать следующий.
- **Плюсы:** простота управления, понятная структура.
- **Минусы:** нельзя повернуть назад, трудно вносить изменения.
- **Применение:** госпроекты, где требования строго определены заранее.

**Agile (Гибкая методология):**
- Итеративная разработка с короткими циклами (спринтами).
- Главное — быстрое реагирование на изменения требований.
- **Принципы:** люди и взаимодействие важнее процессов, работающий продукт важнее документации, сотрудничество с заказчиком, реакция на изменения.
- **Применение:** большинство веб-проектов.

**Scrum (разновидность Agile):**
- Роли: Scrum-мастер (фасилитатор), Product Owner (владелец продукта), Команда (разработчики).
- Артефакты: **Product Backlog** (бэклог требований), **Sprint Backlog** (задачи на спринт), **Increment** (результат спринта).
- Церемонии: Sprint Planning, Daily Standup, Sprint Review, Sprint Retrospective.
- Спринт: 1–4 недели.

**Kanban (доска + непрерывный поток):**
- Доска с колонками: To Do → In Progress → Review → Done.
- Без фиксированных итераций, задачи двигаются непрерывно.
- Ограничение на количество задач в работе (WIP limit) — не больше N задач одновременно.
- **Применение:** поддержка, операционные задачи, проекты с приоритетом на быстрое исправление.
- **Можно совмещать: Scrum + Kanban** — «Scrumban».

**Сравнение:**

| Критерий | Waterfall | Agile | Scrum | Kanban |
|----------|-----------|-------|-------|--------|
| Гибкость | ❌ | ✅ | ✅ | ✅ |
| Планирование | в начале | каждый спринт | в начале спринта | непрерывное |
| Роли | жёсткие | гибкие | строгие | гибкие |
| Итерации | нет | есть | спринты | нет |
| Изменения | трудно | легко | легко | очень легко |

<h3 id="q13">13. Методы и параметры аналитики сайта</h3>

**Основные метрики:**

| Метрика | Описание | Для чего |
|---------|----------|----------|
| **Сессии** | количество визитов на сайт за период | общая посещаемость |
| **Пользователи** | уникальные посетители (используются cookies) | аудитория |
| **Bounce Rate (отказы)** | % посетителей, ушедших с одной страницы | качество контента, скорость |
| **Конверсия** | целевое действие (покупка, регистрация, подписка) | эффективность продукта |
| **Среднее время на сайте** | сколько времени проводят пользователи | вовлечённость |
| **Источники трафика** | откуда пришли: поиск, соцсети, прямые, рефералы | маркетинговая стратегия |
| **Exit Rate** | % уходов с конкретной страницы | какие страницы «продают» |
| **Pages per Session** | сколько страниц смотрит пользователь за визит | глубина просмотра |
| **CTR (Click-Through Rate)** | клики / показы | эффективность баннеров, кнопок |
| **CTR (Conversion Rate)** | конверсия / посетители | эффективность воронки |
| **LTV (Lifetime Value)** | доход от клиента за время жизни | ценность пользователя |
| **CAC (Customer Acquisition Cost)** | затраты на привлечение клиента | ROI маркетинга |

**Инструменты аналитики:**

| Инструмент | Описание | Стоимость |
|------------|----------|-----------|
| **Google Analytics 4 (GA4)** | основной инструмент аналитики от Google | Бесплатно |
| **Яндекс.Метрика** | аналог GA4 для рунета, с тепловыми картами | Бесплатно |
| **Hotjar** | тепловые карты, записи сессий, опросы | Бесплатно (ограниченно) |
| **Mixpanel** | продуктовые аналитики (события, воронки) | Бесплатно (ограниченно) |
| **Amplitude** | аналитика пользовательского поведения | Бесплатно (ограниченно) |
| **Open Web Analytics** | самостоятельный хостинг, без ограничений | Open Source |
| **Matomo** | альтернатива GA с открытым кодом | Бесплатно (свой хостинг) |

**Методы анализа:**
- **A/B-тестирование:** сравниваются два варианта (A и B) для выявления лучшего. Инструменты: Google Optimize, Optimizely, VWO.
- **Когортный анализ:** анализ поведения группы пользователей с похожими характеристиками (например, зарегистрировались в январе).
- **Анализ воронок (Funnels):** просмотр каждого шага в последовательности (например, посетил страницу → добавил в корзину → оформил → оплатил). На каком шаге теряются пользователи?
- **Анализ поведения:** запись сессий, тепловые карты, клики, свайпы.
- **Анализ удержания:** сколько пользователей возвращается на сайт через 1 день, 7 дней, 30 дней.

<h3 id="q14">14. Тестирование и публикация продукта</h3>

**Виды тестирования:**

| Вид | Описание | Инструменты |
|-----|----------|-------------|
| **Юнит-тесты** | Проверка отдельных функций и модулей | Jest (JS), PHPUnit (PHP), PyTest (Python) |
| **Интеграционное** | Проверка взаимодействия модулей (БД, API, сервисы) | Jest + Supertest, Mocha |
| **E2E (End-to-End)** | Симуляция действий пользователя (клик, ввод, переход) | Cypress, Playwright, Selenium |
| **Кроссбраузерное** | Проверка в разных браузерах и на разных устройствах | BrowserStack, LambdaTest |
| **Нагрузочное** | Проверка под высокой нагрузкой (много пользователей) | k6, JMeter, Artillery |
| **SMOKE-тестирование** | Быстрая проверка основного функционала после сборки | вручную или скрипты |
| **Регрессионное** | Проверка, что новые изменения не сломали старый код | автоматизированные тесты |
| **Security (безопасность)** | Поиск уязвимостей (XSS, SQL Injection, CSRF) | OWASP ZAP, Burp Suite |

**Публикация (Deploy / Release):**

1. **Подготовка окружения:**
   - Настроить сервер (хостинг/VPS).
   - Установить необходимые пакеты (Node.js, PHP, Nginx, MySQL).
   - Настроить переменные окружения (ключи API, пароли).

2. **Загрузка файлов:**
   - Через **Git** (git push на сервер).
   - Через **FTP/SFTP** (FileZilla, WinSCP).
   - Через **CI/CD** (автоматически при пуше в репозиторий).

3. **Проверить SSL-сертификат:**
   - Должен быть установлен и корректно работать.
   - Автоматическое обновление (Let's Encrypt + certbot).

4. **Сделать бэкап предыдущей версии:**
   - Код, БД, загруженные файлы.
   - Чтобы можно было откатиться в случае проблем.

5. **Переключить DNS или код:**
   - В случае с CI/CD — автоматически.
   - При смене IP-адреса — обновить DNS записи (A, AAAA).

6. **Проверить работоспособность после публикации:**
   - Пройти по всем страницам.
   - Проверить формы, авторизацию, корзину.

**Стратегии деплоя:**
- **Blue/Green Deploy:** два окружения (Blue — старый, Green — новый). Переключаем трафик.
- **Canary Deploy:** постепенное переключение трафика (сначала 1%, потом 10%, потом 100%).
- **Rolling Deploy:** постепенное обновление серверов без остановки.
- **Feature Flags:** включение фич для части пользователей без деплоя.

<h3 id="q15">15. Доменные имена и хостинг</h3>

**Доменные имена:**

**Структура:** `subdomain.name.zone` (например, `blog.my-site.com`)
- **Зона (TLD)** — .com, .ru, .org, .net, .io, .dev.
- **Имя (SLD)** — my-site (вторая часть).
- **Поддомен** — blog (необязательно).

**Регистраторы (где купить домен):**
- Nic.ru, Reg.ru, Timeweb (Россия).
- GoDaddy, Namecheap, Cloudflare (международные).

**DNS записи (Domain Name System):**

| Запись | Назначение | Пример |
|--------|------------|--------|
| **A** | IPv4-адрес сервера | 192.0.2.1 |
| **AAAA** | IPv6-адрес сервера | 2001:db8::1 |
| **CNAME** | алиас (имя в имя) | www → example.com |
| **MX** | почтовый сервер | mail.example.com |
| **TXT** | текстовая информация (проверка домена, SPF, DKIM) | v=spf1 include:_spf.google.com |
| **NS** | DNS-серверы для домена | ns1.reg.ru |

**TTL (Time To Live):** время, в течение которого DNS-запись кэшируется. Чем меньше TTL — тем быстрее обновление, но больше нагрузка на DNS.

---

**Хостинг (типы):**

| Тип | Описание | Плюсы | Минусы | Пример |
|-----|----------|-------|--------|--------|
| **Shared** | Один сервер на много сайтов | Дешёвый, простой | Ограниченные ресурсы, шумные соседи | Beget, Timeweb, HostGator |
| **VPS/VDS** | Виртуальный выделенный сервер | Полный контроль, выделенные ресурсы | Дороже, требует настройки | DigitalOcean, Vultr, Hetzner |
| **Dedicated** | Физический сервер только для вас | Максимальная мощность, полный контроль | Очень дорого | Hetzner, OVH |
| **Serverless** | Вы платите только за выполнение кода | Масштабируется автоматически, не нужно управлять сервером | Ограниченный стек, холодный старт | Vercel, Netlify, AWS Lambda |
| **Cloud** | Аренда ресурсов у облачных провайдеров | Гибкость, надёжность, глобальные сети | Сложнее в настройке | AWS, Google Cloud, Yandex Cloud |

**Как выбрать хостинг:**

| Сайт | Рекомендация |
|------|--------------|
| Простой сайт-визитка (статический) | Netlify, Vercel (бесплатно) или Shared |
| Блог (WordPress) | Shared (Beget, Timeweb) |
| Интернет-магазин | VPS (DigitalOcean, Vultr) |
| Сложное SPA с бекендом | VPS или Cloud |
| Высокая нагрузка (миллионы пользователей) | Cloud + CDN |

<h3 id="q16">16. Развитие, поддержка и мониторинг продукта</h3>

**Поддержка (Maintenance):**

1. **Фикс багов** — по запросам пользователей или по результатам мониторинга.
2. **Обновление зависимостей**:
   - `npm update` / `composer update` / `pip install -U`.
   - Регулярно (раз в месяц) — чтобы не накопились уязвимости.
3. **Безопасность**:
   - Обновление SSL-сертификатов (раз в 1–3 месяца).
   - Регенерация ключей и паролей.
   - Мониторинг уязвимостей (Snyk, Dependabot).
4. **Производительность**:
   - Оптимизация запросов к БД.
   - Регулярная очистка кэша.
   - Удаление неиспользуемых файлов.

**Мониторинг (Monitoring):**

| Тип мониторинга | Что отслеживает | Инструменты |
|-----------------|-----------------|-------------|
| **Uptime** | Доступность сайта (работает/упал) | Pingdom, UptimeRobot, StatusCake |
| **Производительность** | Скорость загрузки, время ответа сервера | New Relic, DataDog, Yandex AppMetrika |
| **Ошибки** | Логи ошибок бекенда и фронтенда | Sentry, Bugsnag, Rollbar |
| **Ресурсы сервера** | CPU, память, диск, сеть | Prometheus + Grafana, Zabbix, Monit |
| **Логи** | Журналы доступа и ошибок | ELK Stack (Elasticsearch + Logstash + Kibana), Loki + Grafana |
| **Аналитика** | Поведение пользователей, метрики | Google Analytics, Яндекс.Метрика |

**Как организовать мониторинг:**
1. Настроить оповещения (email, Telegram, SMS) при падении сайта или ошибках.
2. Включить алерты при превышении порогов (CPU > 80%, память < 10%).
3. Вести дашборды с основными метриками (Grafana, DataDog).
4. Настроить health checks (проверка работоспособности через `/health` или `/ping`).

**Развитие продукта:**
- Добавление новых фич на основе аналитики.
- Улучшение SEO (оптимизация страниц, мета-теги, структура).
- Переделка интерфейса по результатам A/B-тестов.
- Расширение на новые рынки (локализация, мультиязычность).
- Рефакторинг кода для улучшения производительности и поддерживаемости.

**Жизненный цикл бага (Bug Lifecycle):**
```
New → Assigned → In Progress → Fixed → Tested (QA) → Done / Reopened
```

<h3 id="q18">18. Основы UX/UI: Дон Норман, UX, UI, зачем нужен дизайн интерфейсов</h3>

**Дон Норман** — американский учёный, профессор, автор книги «Дизайн привычных вещей» (The Design of Everyday Things). Он ввёл понятие **пользовательского опыта (UX)** и сформулировал принципы человеко-центрированного дизайна. Главная идея Нормана: продукты должны быть интуитивно понятными, а не заставлять пользователя думать. Он также ввёл понятие «аффорданс» — свойства объекта, подсказывающие, как с ним взаимодействовать (например, ручка двери говорит «тяни», а не «толкай»).

**UX (User Experience) — пользовательский опыт**

**Что это:** Всё, что чувствует и переживает пользователь при взаимодействии с продуктом (сайтом, приложением, кнопкой лифта). Это не только экран, а эмоции, время, усилия, впечатления. Это сумма всех касаний пользователя с продуктом — от первого впечатления до финального взаимодействия.

> «Никакой продукт не является островом. Продукт — это набор взаимодействий. UX — это целостное впечатление». — Дон Норман

**Примеры UX:**
- Как быстро вы нашли нужный товар?
- Раздражали ли всплывающие окна?
- Приятно ли было оформлять заказ?
- Сколько времени занял поиск информации?
- Вернётесь ли вы на этот сайт снова?

**UI (User Interface) — пользовательский интерфейс**

**Что это:** Конкретные элементы, с которыми взаимодействует пользователь: кнопки, поля ввода, иконки, цвета, шрифты, анимация, переключатели, чекбоксы, выпадающие списки. UI — это то, что мы видим и трогаем.

**Отличие UX от UI (ёмкая метафора):**

> **UX — это то, как вы себя чувствуете в ресторане.** (удобные стулья, приятная музыка, быстрый официант, приятная атмосфера)  
> **UI — это вилка, тарелка, скатерть и меню.** (то, что вы видите и трогаете)

**Зачем нужен дизайн интерфейсов:**

1. **Снижает когнитивную нагрузку** — пользователь не думает, куда нажать, интуитивно понимает интерфейс.
2. **Увеличивает конверсию** — больше покупок, регистраций, подписок (хороший дизайн продаёт).
3. **Уменьшает количество ошибок и звонков в поддержку** — пользователи не запутываются в формах и навигации.
4. **Создаёт доверие к продукту** — профессиональный вид = надёжность. Пользователь скорее доверит свои деньги сайту с хорошим дизайном.
5. **Улучшает впечатление от бренда** — делает его запоминающимся и приятным.
6. **Повышает удовлетворённость пользователей** — они возвращаются и рекомендуют вас.

<h3 id="q19">19. Целевая аудитория и анализ конкурентов</h3>

**Целевая аудитория — как и зачем делается**

**Зачем:** Нельзя сделать сайт «для всех». Вы получите сайт, который не подходит никому. ЦА помогает решать:
- Какой стиль выбрать (дерзкий или строгий)?
- Какие функции реализовать (чат или телефон)?
- На каком устройстве будет основная аудитория (мобильный или десктоп)?
- Какой язык и тон общения использовать?

**Как делать:**

1. **Соберите гипотезы** — кто обычно приходит: мамы в декрете, айтишники, студенты, пенсионеры, бизнесмены.
2. **Проведите интервью или анкетирование** — спросите реальных или потенциальных пользователей об их потребностях и болях.
3. **Сегментируйте** по трём признакам:
   - **Демография** — возраст, пол, доход, образование, город проживания.
   - **Поведение** — частота использования, цели, сценарии, какой техникой пользуются.
   - **Психография** — ценности, хобби, страхи, мотивация, образ жизни.

**Пример сегментации для интернет-магазина кроссовок:**

| Сегмент | Возраст | Мотивация | Устройство |
|---------|---------|-----------|------------|
| Бегун-любитель | 25–35 лет | технические характеристики, амортизация | десктоп (изучает характеристики) |
| Подросток для школы | 14–17 лет | внешний вид, бренд, мнение друзей | мобильный (быстрое принятие решения) |
| Подарок | 30–50 лет | быстро найти, не разбирается в модели | планшет (удобно показывать) |

---

**Анализ конкурентов — как и зачем**

**Зачем:** Не изобретать велосипед, понять, какие решения работают, а какие бесят пользователей. Конкуренты уже потратили деньги на исследования — воспользуйтесь их опытом (и ошибками).

**Как делать:**

1. **Выберите 3–5 прямых конкурентов** (компании с похожей аудиторией и продуктом).
2. **Проанализируйте по параметрам:**
   - Навигация и структура (сколько кликов до цели).
   - Качество контента (тексты, фото, видео).
   - Формы регистрации/заказа (сколько полей, какие подсказки).
   - Скорость загрузки (инструменты: PageSpeed Insights, GTmetrix).
   - Отзывы пользователей (на картах, в соцсетях, на форумах).
   - Ценообразование и акции.
   - Визуальный стиль (цветовая схема, шрифты, атмосфера).
3. **Составьте таблицу:** «Сильные стороны / Слабые стороны / Что можно взять».

**Пример таблицы конкурентов:**

| Параметр | Конкурент А | Конкурент Б | Конкурент В |
|----------|-------------|-------------|-------------|
| Навигация | ✅ Понятная | ❌ Сложная | ✅ Простая |
| Качество фото | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| Скорость | 2 сек | 5 сек | 3 сек |
| Отзывы | 4.5 ★ | 3.8 ★ | 4.2 ★ |
| Что взять | UI | Форма заказа | Скорость |

<h3 id="q20">20. Исследования: когда нужны, зачем, виды</h3>

**Когда нужны исследования:**
- **Перед началом проектирования** — чтобы не ошибиться с требованиями и не строить продукт, который никому не нужен.
- **После запуска** — чтобы улучшить продукт, исправить слабые места.
- **При падении метрик** — много отказов, низкая конверсия, падение трафика.
- **При выходе на новый рынок** — чтобы понять новую аудиторию.

**Зачем исследования:**
- Принимать решения на основе фактов, а не догадок («я так думаю» — плохой аргумент).
- Снижать риски провала продукта.
- Узнавать реальные боли и потребности пользователей.
- Проверять гипотезы перед тем, как вкладывать деньги в разработку.

---

**Виды исследований (по этапам и типу):**

| Этап | Качественные (почему?) | Количественные (сколько?) |
|------|------------------------|---------------------------|
| **До дизайна** | Интервью, полевые наблюдения, глубинные интервью | Опросы (анкетирование), аналитика конкурентов |
| **Во время дизайна** | Юзабилити-тестирование прототипов | A/B тесты, клики по прототипу (аналитика) |
| **После запуска** | Customer support звонки, сессии с пользователем (запись экрана) | Метрики (GA, Яндекс.Метрика), тепловые карты, опросы |

**Качественные исследования (Qualitative) — ответ на вопрос «Почему?»:**
- Глубинные интервью (1 на 1, 30–60 минут).
- Наблюдения (как пользователь ведёт себя в реальной среде).
- Юзабилити-тестирование (пользователь выполняет задачи, вы смотрите).
- Дневниковые исследования (пользователь записывает свои действия в течение недели).

**Количественные исследования (Quantitative) — ответ на вопрос «Сколько?»:**
- Опросы (Google Forms, SurveyMonkey, Typeform).
- Аналитика (GA, Яндекс.Метрика).
- A/B тесты (сравнение двух версий).
- Тепловые карты (Hotjar, Crazy Egg).
- Клики по прототипу (UXtweak, Maze).

**Главное правило:** сначала качественные (узнать проблемы и гипотезы), потом количественные (подтвердить масштаб и приоритеты). Качественные дают глубину, количественные — статистическую значимость.

<h3 id="q21">21. Проведение интервью</h3>

**Как подготовиться к интервью:**

1. **Составьте сценарий на 30–40 минут** (не больше — пользователь устаёт, качество падает).
2. **Формулируйте открытые вопросы** — «расскажите, как вы обычно...», а не «вам нравится наше приложение?».
3. **Избегайте вопросов-подсказок** — «насколько удобно вам было нажимать на синюю кнопку?» → «расскажите про ваш путь к оплате».
4. **Подготовьте запись** (диктофон или запись экрана с согласия пользователя).
5. **Подготовьте прототип** (если тестируете дизайн).

**Как выбрать респондентов:**

- **Скрининг-анкета** (3–5 вопросов) — отсев нецелевых пользователей.
- Ключевой критерий: **человек реально сталкивается с вашей задачей** (например, покупает авиабилеты раз в месяц, а не раз в год).
- **Разнообразие** — новички и опытные пользователи, разные устройства, разные демографические группы (возраст, пол, город).
- Для исследования достаточно **5–8 респондентов** (по данным Nielsen, 80% проблем выявляется после 5 интервью).

**Как общаться с респондентами (правила):**

1. **Начните с простых фактов** — «чем вы занимаетесь?», «как часто пользуетесь интернетом?».
2. **Просите показать, а не рассказать** — «покажите, как вы ищете товар» (Share screen или дайте телефон в руки).
3. **Не перебивайте** — даже если говорится не по делу, это может быть важным контекстом.
4. **Задавайте «почему» несколько раз подряд** (метод 5 Whys) — чтобы добраться до сути.
   - «Я не люблю этот сайт» → «Почему?» → «Там сложный интерфейс» → «Почему он сложный?» → «Кнопки не на своих местах»...
5. **В конце спросите:** «что мы забыли спросить?» — это часто выдаёт неожиданные инсайты.
6. **Поблагодарите** и дайте небольшой бонус (скидка, подарочный код) — это мотивирует.

**Запрещено:**
- Продавать или рекламировать свой продукт.
- Защищать свой продукт («это же интуитивно понятно!»).
- Подсказывать решения («нажмите сюда»).
- Задавать закрытые вопросы («вам нравится?»).

<h3 id="q22">22. Персоны (Personas)</h3>

**Что это:** Персона — собирательный образ реального пользователя, основанный на исследованиях (интервью, анкетирование, аналитика). Это не «средняя температура по больнице», а конкретный персонаж с именем, фото, целями и болями.

**Зачем нужны персоны:**
- Чтобы вся команда говорила на одном языке («а что подумает Елена Марковна?»).
- Чтобы принимать решения на основе пользователя (кнопку сделать крупнее — Елена Марковна плохо видит).
- Чтобы не делать «функции ради функций» — проверять каждую функцию: «а нужно ли это Елене Марковне?».
- Чтобы фокусироваться на приоритетных пользователях (делать продукт для основной ЦА).

**Как делать персон:**

1. На основе интервью и сегментации выделите **2–5 типов пользователей** (не больше, иначе не запомните).
2. Опишите по шаблону:
   - **Имя и фото** (из бесплатных стоков, не знаменитости).
   - **Демография** — возраст, город, образование, доход.
   - **Работа** — кем работает, профессиональный уровень.
   - **Цели** — что хочет достичь с помощью вашего продукта (конкретные, измеримые).
   - **Боли** — что его бесит, раздражает, мешает ему достичь цели.
   - **Сценарий использования** — когда, где, с какого устройства заходит.
   - **Цитата** — «Я хочу купить билет за 3 минуты без регистрации».
   - **Мотивация** — почему он вообще этим занимается.
3. Повесьте персон на стену в офисе / в Figma / в Miro, чтобы вся команда помнила о пользователях.

**Пример персоны: «Бизнесмен Борис»**

| Параметр | Значение |
|----------|----------|
| Имя | Борис Петров |
| Возраст | 45 лет |
| Город | Москва |
| Работа | Директор по продажам |
| Цели | Купить билет за 3 минуты, отель без регистрации |
| Боли | Ненавидит долгие формы, бесит реклама страховок |
| Сценарий | Заказывает в такси по пути в аэропорт, с телефона |
| Устройство | iPhone 14, мобильный интернет |
| Платит | Apple Pay, гостевой заказ (без регистрации) |
| Цитата | «Зачем мне регистрироваться, я просто покупаю билет» |

<h3 id="q23">23. CJM и User Story</h3>

**CJM (Customer Journey Map) — карта пути клиента**

**Что это:** Визуализация шагов, эмоций, точек касания с продуктом от первого контакта до цели. Это не просто схема, а история пользователя с его чувствами и впечатлениями.

**Зачем:**
- Увидеть, где пользователь злится, бросает или испытывает восторг.
- Найти «точки боли» и «точки счастья».
- Улучшать наиболее проблемные этапы.
- Согласовать видение команды о пользователе.

**Как делать (таблица / пошагово):**

| Этап | Действие пользователя | Эмоция | Боли | Возможности |
|------|----------------------|--------|------|--------------|
| **Поиск** | Гуглит «купить ноутбук» | Нейтрально | Слишком много рекламы | Показать честный обзор |
| **Выбор** | Сравнивает модели | Тревога | Непонятные характеристики | Добавить сравнительную таблицу |
| **Оформление** | Заполняет форму | Раздражение | Просят номер телефона | Сделать быстрый заказ без регистрации |
| **Оплата** | Вводит карту | Волнение | Боится, что данные украдут | Показать иконки безопасности |
| **Получение** | Открывает коробку | Радость | Всё ок | Попросить отзыв |

**Пример для интернет-магазина:** на этапе «Оформление» пользователь бросает корзину (много полей). Возможность: сократить форму до 3 полей и добавить кнопку «Купить в один клик».

---

**User Story (история пользователя)**

**Формат:** «Я как [тип пользователя] хочу [действие] чтобы [достичь цели]».

**Примеры:**
- «Я как **администратор отеля** хочу **видеть все бронирования за месяц** чтобы **планировать загрузку номеров**».
- «Я как **покупатель** хочу **сохранять товары в избранное** чтобы **вернуться к ним позже**».
- «Я как **менеджер** хочу **получать уведомления о новых заказах** чтобы **быстро их обрабатывать**».
- «Я как **пользователь** хочу **восстанавливать пароль по email** чтобы **не терять доступ к аккаунту**».

**Зачем:**
- Перевести требования на язык пользы для пользователя, а не на язык функций.
- Сделать разработку более пользовательской.
- Определить критерии приёмки — «реализовали ли мы то, что хотел пользователь?».
- В Agile методологии User Story — основной способ описания задач.

**Структура Acceptance Criteria (критерии приёмки):**
```
Данные (Given) — предварительные условия
Когда (When) — действие
Тогда (Then) — ожидаемый результат
```

**Пример для User Story «сохранять товары в избранное»:**
```
Given: пользователь авторизован на сайте
When: пользователь нажимает на значок избранного на карточке товара
Then: товар появляется в разделе «Избранное»
```

<h3 id="q24">24. Карта сайта и вайрфреймы</h3>

**Карта сайта (Site Map)**

**Что это:** Иерархическая схема всех страниц и разделов сайта. Как оглавление книги или карта метро.

**Зачем:**
- Понять логику навигации до дизайна.
- Не пропустить важные страницы (404, политика конфиденциальности, контакты).
- Согласовать структуру с заказчиком.
- Продумать пути пользователя (сколько кликов до цели).

**Как делать:** в MindNode, Miro, FigJam, Draw.io или просто в текстовом файле.

**Пример карты сайта для интернет-магазина:**
```
Главная
├── Каталог
│   ├── Кроссовки
│   │   ├── Nike
│   │   ├── Adidas
│   │   └── Puma
│   ├── Одежда
│   │   ├── Футболки
│   │   └── Куртки
│   └── Аксессуары
│       ├── Сумки
│       └── Рюкзаки
├── Личный кабинет
│   ├── Профиль
│   ├── Заказы
│   ├── Избранное
│   └── Способы оплаты
├── О нас
├── Блог
├── Контакты
└── 404 (страница не найдена)
```

---

**Вайрфреймы (Wireframes) — «скелет» интерфейса**

**Что это:** Чёрно-белая схема расположения элементов на странице (без цветов, шрифтов, картинок). Только структура и приоритеты. Вайрфрейм — это про архитектуру страницы, а не про дизайн.

**Уровни проработки:**

| Уровень | Инструменты | Когда использовать |
|---------|-------------|-------------------|
| **Low-fidelity** | Бумага, карандаш, Miro, Balsamiq | Для быстрых идей, скицирование, этап «набросать мысли» |
| **Mid-fidelity** | Figma, Sketch (серые прямоугольники) | Для тестирования навигации и структуры с пользователями |
| **High-fidelity** | Figma (почти как макет, но без стилей) | Для передачи разработчикам, когда стили ещё не готовы |

**Пример вайрфрейма страницы:**
```
[ЛОГО]          [Поиск]          [Вход] [Корзина]
[Главная] [Каталог] [О нас] [Контакты]
----------------------------------------
     [БАННЕР (большой прямоугольник)]
----------------------------------------
Заголовок H1 (крупный текст)
[Карточка 1] [Карточка 2] [Карточка 3] [Карточка 4]
[Кнопка]     [Кнопка]     [Кнопка]     [Кнопка]
----------------------------------------
[Подвал: ссылки, контакты, соцсети]
```

**Советы по вайрфреймам:**
- Не используйте цвета (кроме серого) — они отвлекают.
- Используйте реалистичные тексты (не «Lorem ipsum», а реальные данные).
- Показывайте иерархию через размеры прямоугольников.
- Добавляйте заметки: «здесь будет слайдер», «тут форма подписки».

<h3 id="q25">25. Accessibility (A11y) — доступность</h3>

**Что это:** Accessibility (A11y — буква «а», потом 11 букв, потом «y») — возможность пользоваться сайтом людям с ограничениями: слепым, слабовидящим, с нарушениями моторики, с когнитивными расстройствами, с эпилепсией. По данным ВОЗ, более 1 миллиарда человек имеют инвалидность — это огромная аудитория, которую нельзя игнорировать.

**Уровни по стандарту WCAG 2.1 (Web Content Accessibility Guidelines):**

| Уровень | Описание | Когда требуется |
|---------|----------|-----------------|
| **A** | Минимальный (базовый доступ) | Обязательно для госсайтов в большинстве стран |
| **AA** | Рекомендуемый для коммерческих сайтов | Баланс усилий и пользы. Это цель для большинства |
| **AAA** | Максимальный (полная доступность) | Желательно, но трудно достижимо (для специальных сервисов) |

---

**Как обеспечивать доступность (практические правила):**

1. **Альтернативный текст для всех изображений** (`alt`):
   ```html
   <img src="laptop.jpg" alt="Ноутбук Dell XPS на столе"> <!-- описание, а не 'laptop.jpg' -->
   ```
   Для декоративных изображений: `alt=""` (скринридер пропустит).

2. **Контраст текста** не менее 4.5:1 для обычного текста и 3:1 для крупного (≥ 24px). Проверяйте в Figma (плагин Stark) или в Contrast Checker.

3. **Полная навигация с клавиатуры** — Tab, Enter, Escape, стрелки должны работать без мыши. Видимый фокус (`:focus` стиль) должен быть всегда виден (не `outline: none` без замены).
   ```css
   a:focus, button:focus, input:focus {
     outline: 2px solid #2563eb;
     outline-offset: 2px;
   }
   ```

4. **ARIA-роли** для кастомных элементов:
   ```html
   <div role="button" tabindex="0" aria-label="Закрыть" onclick="close()">×</div>
   ```

5. **Не полагайтесь только на цвет** (сообщения об ошибках):
   - ❌ Только красная рамка.
   - ✅ Красная рамка + иконка + текст ошибки под полем.

6. **Размер кликабельных элементов** не менее 44×44 pt (для пальцев). Расстояние между ними — не менее 8px.

7. **Семантический HTML** (используйте `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<aside>`, `<footer>`) — это улучшает навигацию для скринридеров.

8. **Заголовки в правильной иерархии** (H1 → H2 → H3) — скринридеры используют их для навигации по странице.

9. **Субтитры и транскрипты** для видео и аудио.

10. **Язык страницы** (`lang="ru"`) — помогает синтезаторам речи.

**Инструменты проверки доступности:**
- WAVE (веб-расширение).
- axe DevTools (встроено в DevTools).
- Lighthouse Accessibility (вкладка в DevTools).
- NVDA (скринридер для Windows, бесплатный).
- VoiceOver (встроенный в macOS/iOS).
- Contrast Checker (проверка контраста).

<h3 id="q26">26. Принципы мобильного дизайна</h3>

**Отличия мобильного дизайна от десктопного:**

| Параметр | Десктоп | Мобильный телефон |
|----------|---------|-------------------|
| **Ввод** | Мышь (точный клик) | Палец (не точный, толстый) |
| **Экран** | Большой, можно много колонок | Маленький, одна колонка |
| **Контекст** | Дома / в офисе, стабильное подключение | На ходу, прерывистый интернет, на солнце |
| **Энергия пользователя** | Высокая (работает) | Низкая (в очереди в кофейне, в метро) |
| **Внимание** | Сфокусировано | Рассеянное |
| **Экран** | Горизонтальный | Вертикальный |

---

**Принципы мобильного дизайна (Mobile First):**

1. **Tap target (размер цели касания)** — минимум 44×44 pt (Apple) или 48×48 dp (Google Material). Расстояние между кликабельными элементами — не менее 8 pt, чтобы не нажимать на соседнее.

2. **Жесты** — свайп назад, pull-to-refresh (обновление), double-tap (увеличение). Но не прячьте важные функции только за жестами (они не всегда интуитивны). Дублируйте кнопками.

3. **Приоритет контента** — на десктопе можно показать много второстепенного; на мобильном прячьте почти всё (аккордеоны, вкладки, скрытые меню). Показывайте только то, что нужно здесь и сейчас.

4. **Нижняя навигация (таб-бар)** — для частых действий (главная, каталог, корзина, профиль). Верхняя — только поиск/профиль. Большие пальцы пользователя находятся внизу, так что самые важные кнопки — в нижней части экрана.

5. **Адаптивные формы**:
   - Клавиатура с кнопкой «Далее» (переключение между полями).
   - Поле телефона сразу переключает на цифры (`inputmode="numeric"` или `type="tel"`).
   - Крупные поля ввода (высота 44–48px).
   - Подписи над полями (не слева) — экономит ширину.

6. **Не убивайте скролл** — мобильные пользователи привыкли скроллить, не пытайтесь втиснуть всё на один экран. Бесконечная прокрутка (infinite scroll) хороша для соцсетей, но плоха для интернет-магазинов (трудно найти товар).

7. **Используйте системные шрифты** (San Francisco для iOS, Roboto для Android) — они оптимизированы для чтения с экрана.

8. **Учитывайте различные размеры экранов** — от 320px (iPhone SE) до 428px (iPhone 14 Pro Max). Используйте отзывчивую вёрстку (CSS Grid, Flexbox, `clamp()`).

9. **Учитывайте сценарии использования** — пользователь может быть в шумном месте, на солнце, с плохим интернетом. Шрифты должны быть крупными, кнопки — контрастными.

<h3 id="q27">27. Подготовка макетов для передачи в разработку</h3>

**Это мост между дизайном и кодом.** Если сделать плохо — разработчик реализует не то, что вы нарисовали, а вы будете плакать на ретроспективе. Хорошая подготовка ускоряет разработку в 2–3 раза.

---

**✅ В Figma / Sketch / Penpot:**

1. **Именование слоёв и групп** — не `Rectangle 34`, а `header/button_signup`. Разработчик должен понимать, что это за элемент, не заглядывая в дизайн.
   
   Примеры имён:
   - `home/hero/title`
   - `product/card/price`
   - `cart/checkout_button`

2. **Автолейауты (Auto Layout)** — используйте их, чтобы разработчик понял отступы (padding, margin), направление (row/column) и поведение при изменениях (растяжение, сжатие). Разработчик увидит: «а, здесь flex-direction: column, gap: 16px».

3. **Стили текста (Text Styles)** — создайте стили для каждого типа текста:
   - `H1` — 48px, Bold, Inter, line-height 1.2
   - `Body` — 16px, Regular, Inter, line-height 1.5
   - `Caption` — 14px, Regular, Inter, line-height 1.4

4. **Цвета (Color Styles)** — создайте стили для всех цветов:
   - `primary-brand` — #2563EB
   - `error-red` — #DC2626
   - `background-grey` — #F3F4F6
   - `text-primary` — #111827

5. **Компоненты** — создайте компоненты для повторяющихся элементов: кнопка, карточка товара, инпут, чекбокс, переключатель. И все их состояния:
   - `default` — обычное состояние.
   - `hover` — при наведении мыши.
   - `active` — нажато.
   - `disabled` — неактивное (серое).
   - `focus` — при фокусе с клавиатуры (важно для доступности).

6. **Сетка** — укажите сколько колонок, ширину контейнера (обычно 1200px для десктопа), отступы (gutters). Сетка помогает разработчику понять систему и не делать ошибок.

---

**✅ Документация к макету:**

- **Интерактивные прототипы** — клик по кнопке → переход на нужный экран. Это помогает разработчику понять навигацию.

- **Экспорт иконок и иллюстраций**:
  - Иконки — SVG (маленький размер, масштабируемость).
  - Фотографии — WebP или JPG, 2x/3x для ретины (с указанием размеров).

- **Поведение ошибок** — что показывать, когда поле не прошло валидацию (красная рамка, текст ошибки). Разработчик должен знать все состояния каждого поля.

- **Адаптив** — как выглядит на мобильном, планшете, десктопе. Покажите ключевые точки перелома (breakpoints): 320px, 768px, 1024px, 1200px.

- **Текст-заглушка** — лучше реальный контент (или максимально похожий), а не Lorem ipsum. Так разработчик сможет проверить, как ведёт себя интерфейс с реальными данными (длинные названия, переносы, сокращения).

---

**✅ Финальный шаг — ревиз дизайна с разработчиком:**

- Figma сама показывает CSS-свойства при наведении (Dev Mode).
- Но **проведите созвон на 15–30 минут** и пройдитесь по макету:
  - «Здесь отступ 24px, там 16px, здесь hover — синий цвет, модальное окно закрывается по клику на оверлей, на мобильном это сворачивается в аккордеон».

**Чек-лист для созвона:**
- [ ] Все ли состояния показаны? (hover, active, disabled, focus)
- [ ] Понятны ли переходы между экранами?
- [ ] Учтены ли сценарии ошибок (пустые поля, невалидные данные)?
- [ ] Согласован ли адаптив?
- [ ] Есть ли все необходимые иконки в нужных форматах?

**Инструменты для передачи:** Figma Dev Mode, Zeplin, Avocode, Sketch Inspect.

```
Исследования → Сегментация → Персоны → CJM → Карта сайта → Вайрфреймы → 
Дизайн-концепция → Дизайн интерфейса → Прототипирование → 
Тестирование → Подготовка макетов → Передача в разработку.
```
