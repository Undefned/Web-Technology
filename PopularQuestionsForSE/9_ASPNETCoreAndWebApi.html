REST API — принципы (ресурсы, HTTP методы, stateless).
обяз

REST (Representational State Transfer) — архитектурный стиль для API.

Основные принципы:

1. Ресурсы (Resources)

  • Всё — это ресурс (пользователь, заказ, товар)
  • Ресурс идентифицируется URL: /api/users/5
  • Ресурс представляется в форматах: JSON, XML

2. HTTP методы (Verbs)

  • GET — получение ресурса (без изменений)
  • POST — создание нового ресурса
  • PUT — полная замена ресурса
  • PATCH — частичное обновление
  • DELETE — удаление ресурса
  • OPTIONS — информация о ресурсе
  • HEAD — заголовки без тела

3. Stateless (отсутствие состояния)

  • Каждый запрос независим от других
  • Не хранится состояние на сервере
  • Аутентификация в каждом запросе (JWT)
  • Упрощает масштабирование

4. HATEOAS (Hypermedia as the Engine of Application State)

  • Ответ содержит ссылки на возможные действия
  • Редко используется на практике

Пример REST API:

GET    /api/users         → Список пользователей
GET    /api/users/5       → Пользователь #5
POST   /api/users         → Создать пользователя
PUT    /api/users/5       → Обновить #5
PATCH  /api/users/5       → Частично обновить #5
DELETE /api/users/5       → Удалить #5
GET vs POST vs PUT vs PATCH vs DELETE.
обяз
Метод Назначение Идемпотентность Тело Кэширование
GET Получение ресурса ✅ Да Нет ✅ Да
POST Создание ресурса ❌ Нет Да ❌ Нет
PUT Полная замена ресурса ✅ Да Да ❌ Нет
PATCH Частичное обновление ⚠️ Зависит Да ❌ Нет
DELETE Удаление ресурса ✅ Да Нет ❌ Нет

Идемпотентность — повторный запрос даёт тот же результат.

Примеры:

// GET — безопасный и идемпотентный
GET /api/users/5 → 200 OK

// POST — не идемпотентный (создаёт новый ресурс)
POST /api/users → 201 Created

// PUT — идемпотентный (полная замена)
PUT /api/users/5 → 200 OK или 204 No Content

// PATCH — может быть идемпотентным
PATCH /api/users/5 → 200 OK

// DELETE — идемпотентный (первый раз 200, второй — 404)
DELETE /api/users/5 → 200 OK

Когда что использовать:

  • GET: получение данных (без изменений)
  • POST: создание нового ресурса
  • PUT: полное обновление (замена)
  • PATCH: частичное обновление
  • DELETE: удаление
HTTP коды: 200, 201, 204, 400, 401, 403, 404, 409, 500.
обяз

2xx — Успех (Success)

  • 200 OK — запрос успешно выполнен
  • 201 Created — ресурс создан (обычно с POST)
  • 204 No Content — успешно, но тело ответа пустое

4xx — Ошибка клиента (Client Error)

  • 400 Bad Request — неверный запрос (валидация)
  • 401 Unauthorized — требуется аутентификация
  • 403 Forbidden — нет прав доступа
  • 404 Not Found — ресурс не найден
  • 409 Conflict — конфликт (например, дубликат)
  • 422 Unprocessable Entity — ошибка бизнес-логики

5xx — Ошибка сервера (Server Error)

  • 500 Internal Server Error — внутренняя ошибка сервера
  • 501 Not Implemented — метод не реализован
  • 503 Service Unavailable — сервис недоступен

Примеры использования:

// GET /api/users/5
200 OK → { id: 5, name: "Alice" }

// POST /api/users (создание)
201 Created → Location: /api/users/5

// PUT /api/users/5
204 No Content → тело пустое

// GET /api/users/999
404 Not Found → { error: "User not found" }

// POST /api/users (валидация)
400 Bad Request → { errors: { email: "Invalid email" } }

// POST /api/users (дубликат)
409 Conflict → { error: "User already exists" }

// Внутренняя ошибка
500 Internal Server Error → { error: "Something went wrong" }
Middleware — что это, порядок регистрации.
обяз

Middleware — компоненты в конвейере обработки HTTP-запросов.

Как работает:

  • Каждый middleware может обработать запрос
  • Может передать управление следующему middleware
  • Может выполнить код до и после следующего middleware
  • Запрос проходит по цепочке туда и обратно

Порядок регистрации (важен!):

var app = builder.Build();

// Порядок имеет значение!
app.UseExceptionHandler();          // 1. Обработка ошибок (первым!)
app.UseHttpsRedirection();          // 2. HTTPS
app.UseStaticFiles();               // 3. Статические файлы
app.UseRouting();                   // 4. Маршрутизация
app.UseAuthentication();            // 5. Аутентификация
app.UseAuthorization();             // 6. Авторизация
app.MapControllers();               // 7. Контроллеры (последним!)

// Custom middleware
app.Use(async (context, next) =>
{
    Console.WriteLine("До следующего middleware");
    await next();  // Передаём дальше
    Console.WriteLine("После следующего middleware");
});

Создание собственного middleware:

public class LoggingMiddleware
{
    private readonly RequestDelegate _next;
    
    public LoggingMiddleware(RequestDelegate next)
    {
        _next = next;
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        Console.WriteLine($"Запрос: {context.Request.Method} {context.Request.Path}");
        
        await _next(context);  // Передаём дальше
        
        Console.WriteLine($"Ответ: {context.Response.StatusCode}");
    }
}

// Регистрация
app.UseMiddleware<LoggingMiddleware>();
JWT-токен — структура (Header, Payload, Signature).
обяз

JWT (JSON Web Token) — стандарт для аутентификации и обмена данными.

Структура:

// Формат: header.payload.signature
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE1MTYyMzkwMjJ9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

1. Header (Заголовок)

  • Алгоритм шифрования (alg)
  • Тип токена (typ)
{
  "alg": "HS256",
  "typ": "JWT"
}

2. Payload (Данные)

  • Claims (утверждения о пользователе)
  • Стандартные: iss, exp, iat, sub
  • Кастомные: userId, role, email
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022,
  "exp": 1516242622,
  "userId": 42,
  "role": "admin"
}

3. Signature (Подпись)

  • Создаётся из header + payload + секрет
  • Обеспечивает целостность (нельзя подделать)
  • Проверяется на сервере
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

Использование в ASP.NET Core:

// Генерация токена
var claims = new[]
{
    new Claim(ClaimTypes.Name, user.Email),
    new Claim(ClaimTypes.Role, "Admin"),
    new Claim("userId", user.Id.ToString())
};

var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes("super-secret-key"));
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

var token = new JwtSecurityToken(
    issuer: "myapp",
    audience: "myapp",
    claims: claims,
    expires: DateTime.Now.AddHours(1),
    signingCredentials: creds
);

var tokenString = new JwtSecurityTokenHandler().WriteToken(token);
Аутентификация vs Авторизация — разница.
обяз

Аутентификация (Authentication) — Кто ты?

  • Проверка личности пользователя
  • Логин + пароль, JWT, OAuth, биометрия
  • Вопрос: "Ты действительно тот, за кого себя выдаёшь?"
  • Отвечает за вход в систему

Авторизация (Authorization) — Что тебе можно?

  • Проверка прав доступа
  • Роли, разрешения, политики
  • Вопрос: "Имеешь ли ты право делать это?"
  • Отвечает за доступ к ресурсам

Пример в ASP.NET Core:

// Аутентификация — проверка JWT
[Authorize]
public class UsersController : ControllerBase
{
    // Авторизация — проверка ролей
    [Authorize(Roles = "Admin")]
    [HttpGet]
    public IActionResult GetAll()
    {
        return Ok(_userService.GetAll());
    }
    
    // Авторизация — проверка политики
    [Authorize(Policy = "CanEditUsers")]
    [HttpPut("{id}")]
    public IActionResult Update(int id, UserDto user)
    {
        return Ok(_userService.Update(id, user));
    }
}

Порядок в Middleware:

app.UseAuthentication();  // Сначала аутентификация
app.UseAuthorization();   // Потом авторизация

Схема:

  • Вход: Аутентификация → Проверка пароля → Создание JWT
  • Запрос: JWT → Аутентификация → Проверка токена → Авторизация → Проверка прав
Dependency Injection в ASP.NET Core — встроенный контейнер.
обяз

Dependency Injection (DI) — паттерн, где зависимости внедряются извне.

Регистрация сервисов:

// Program.cs или Startup.cs
var builder = WebApplication.CreateBuilder(args);

// Регистрация сервисов
builder.Services.AddControllers();
builder.Services.AddScoped<IUserService, UserService>();
builder.Services.AddTransient<ILogger, ConsoleLogger>();
builder.Services.AddSingleton<ICache, MemoryCache>();

// Регистрация с фабрикой
builder.Services.AddScoped<IRepository>(sp =>
{
    var config = sp.GetRequiredService<IConfiguration>();
    return new Repository(config.GetConnectionString("Default"));
});

var app = builder.Build();

Внедрение зависимостей:

// Конструкторная инъекция (рекомендуется)
[ApiController]
[Route("api/users")]
public class UsersController : ControllerBase
{
    private readonly IUserService _userService;
    private readonly ILogger _logger;
    
    public UsersController(IUserService userService, ILogger logger)
    {
        _userService = userService;
        _logger = logger;
    }
    
    [HttpGet]
    public IActionResult GetUsers()
    {
        _logger.LogInformation("Получение пользователей");
        return Ok(_userService.GetAll());
    }
}

Жизненные циклы:

  • AddTransient — новый экземпляр каждый раз
  • AddScoped — один экземпляр на запрос
  • AddSingleton — один экземпляр на всё приложение
Transient / Scoped / Singleton — жизненные циклы.
обяз
Жизненный цикл Описание Создание Когда использовать
Transient Новый экземпляр при каждом внедрении Каждый раз Лёгкие, stateless сервисы
Scoped Один экземпляр на HTTP-запрос На каждый запрос DbContext, бизнес-логика
Singleton Один экземпляр на всё приложение Один раз Кэш, конфигурация, логирование

Примеры:

// Transient — каждый раз новый
builder.Services.AddTransient<IMathService, MathService>();

// Scoped — один на запрос
builder.Services.AddScoped<IDbContext, AppDbContext>();

// Singleton — один на приложение
builder.Services.AddSingleton<ICache, MemoryCache>();

// Или с лямбдой
builder.Services.AddSingleton<IConfiguration>(provider =>
{
    return new ConfigurationBuilder().Build();
});

Важные нюансы:

  • Transient нельзя внедрять в Singleton (будет жить как Singleton)
  • Scoped нельзя внедрять в Singleton (будет жить как Singleton)
  • Для веб-приложений: Scoped = на один HTTP-запрос
  • Для консольных приложений: нужно создать IServiceScope

Как получить сервис вручную:

// Вне контекста контроллера
var service = app.Services.GetRequiredService<IUserService>();

// В контроллере через IServiceProvider
[FromServices] public IUserService UserService { get; set; }
IoC контейнеры: встроенный, Autofac, Unity — сравнение.
mid

Встроенный DI (.NET Core):

  • ✅ Лёгкий, простой, всегда доступен
  • ✅ Интегрирован в ASP.NET Core
  • ❌ Ограниченные возможности (нет property injection)
  • ❌ Сложные сценарии (декораторы) требуют обходных путей

Autofac:

  • ✅ Богатые возможности (декораторы, property injection)
  • ✅ Интеграция с ASP.NET Core
  • ✅ Модульная регистрация
  • ❌ Может быть сложным для новичков
// Autofac
var builder = new ContainerBuilder();
builder.RegisterType<UserService>().As<IUserService>();
builder.RegisterType<LoggingService>().As<ILogger>().InstancePerLifetimeScope();
builder.RegisterDecorator<LoggingUserService, IUserService>();

var container = builder.Build();

Unity:

  • ✅ Простой, от Microsoft
  • ❌ Устаревший, не развивается
  • ❌ Нет интеграции с ASP.NET Core

Выбор:

  • Встроенный: для 90% приложений
  • Autofac: для сложных сценариев (декораторы, перехват)
  • Unity: не рекомендуется (устарел)
Kestrel — что это, reverse proxy (Nginx/IIS).
обяз

Kestrel — кросс-платформенный веб-сервер для ASP.NET Core.

Характеристики:

  • Написан на C# (управляемый код)
  • Высокая производительность (использует libuv)
  • Поддерживает HTTP/1.1, HTTP/2, HTTP/3
  • Работает на Windows, Linux, macOS
  • Лёгкий, быстрый

Reverse Proxy (обратный прокси):

  • Kestrel используется за обратным прокси
  • Прокси принимает внешние запросы и перенаправляет в Kestrel
  • Обеспечивает безопасность, балансировку, SSL

Настройка:

// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.WebHost.ConfigureKestrel(options =>
{
    options.Listen(IPAddress.Any, 5000);  // HTTP
    options.Listen(IPAddress.Any, 5001, listenOptions =>
    {
        listenOptions.UseHttps("certificate.pfx", "password");
    });
});

Сравнение Kestrel и IIS:

Характеристика Kestrel IIS
Платформа Кросс-платформенный Только Windows
Производительность Высокая Средняя
Функции Базовые Богатые (SSL, auth, кэширование)
Настройка В коде Через GUI
Фильтры: Authorization, Resource, Action, Exception, Result.
mid

Фильтры — выполняют код до и после обработки запроса.

Типы фильтров (порядок выполнения):

1. Authorization Filters

  • Самый ранний этап
  • Проверка прав доступа
  • Может остановить выполнение
public class CustomAuthorizeFilter : IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        if (!context.HttpContext.User.Identity.IsAuthenticated)
        {
            context.Result = new UnauthorizedResult();
        }
    }
}

2. Resource Filters

  • До и после модели
  • Для кэширования, логирования
  • Может остановить выполнение
public class CacheResourceFilter : IResourceFilter
{
    public void OnResourceExecuting(ResourceExecutingContext context)
    {
        // До выполнения
    }
    
    public void OnResourceExecuted(ResourceExecutedContext context)
    {
        // После выполнения
    }
}

3. Action Filters

  • До и после выполнения метода контроллера
  • Может остановить выполнение
public class LogActionFilter : IActionFilter
{
    public void OnActionExecuting(ActionExecutingContext context)
    {
        // До выполнения метода
        Console.WriteLine($"Вызов: {context.ActionDescriptor.DisplayName}");
    }
    
    public void OnActionExecuted(ActionExecutedContext context)
    {
        // После выполнения метода
        Console.WriteLine($"Результат: {context.Result}");
    }
}

4. Exception Filters

  • Обработка исключений
  • Глобальная обработка ошибок
public class GlobalExceptionFilter : IExceptionFilter
{
    public void OnException(ExceptionContext context)
    {
        context.Result = new ObjectResult(new { error = context.Exception.Message })
        {
            StatusCode = 500
        };
        context.ExceptionHandled = true;
    }
}

5. Result Filters

  • До и после выполнения результата
  • Модификация ответа
public class FormatResultFilter : IResultFilter
{
    public void OnResultExecuting(ResultExecutingContext context)
    {
        // До отправки результата
    }
    
    public void OnResultExecuted(ResultExecutedContext context)
    {
        // После отправки результата
    }
}
Model Binding и Model Validation — Data Annotations.
обяз

Model Binding — преобразование данных запроса в объекты модели.

[ApiController]
[Route("api/users")]
public class UsersController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult GetUser([FromRoute] int id) { }
    
    [HttpPost]
    public IActionResult CreateUser([FromBody] CreateUserRequest request) { }
    
    [HttpGet]
    public IActionResult Search([FromQuery] SearchRequest request) { }
    
    [HttpPut("{id}")]
    public IActionResult Update([FromRoute] int id, [FromBody] UpdateRequest request) { }
}

Model Validation — Data Annotations:

public class CreateUserRequest
{
    [Required]
    [StringLength(50, MinimumLength = 2)]
    public string Name { get; set; }
    
    [Required]
    [EmailAddress]
    public string Email { get; set; }
    
    [Range(18, 100)]
    public int Age { get; set; }
    
    [RegularExpression(@"^\+7\d{10}$")]
    public string Phone { get; set; }
    
    [Compare("Password")]
    public string ConfirmPassword { get; set; }
}

Валидация в контроллере:

[HttpPost]
public IActionResult Create([FromBody] CreateUserRequest request)
{
    if (!ModelState.IsValid)
    {
        return BadRequest(ModelState);
    }
    
    // Обработка
    return Ok();
}

builder.Services.AddControllers()
