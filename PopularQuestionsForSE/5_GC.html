🧠 5. Garbage Collector. Управление памятью Mid+

Как работает GC — корневые объекты, маркировка, очистка.
обяз

Сборщик мусора (GC) автоматически управляет памятью в .NET.

Три основных этапа:

  1. Маркировка (Mark): GC находит корневые объекты и отмечает все достижимые объекты
  2. Очистка (Sweep): Удаляет недостижимые объекты (без ссылок)
  3. Сжатие (Compact): Перемещает выжившие объекты, чтобы память была непрерывной

Корневые объекты (Roots):

  • Локальные переменные в стеке
  • Статические поля
  • Зарегистрированные обработчики событий
  • Объекты в финализаторе
  • Ссылки из неуправляемого кода (GCHandle)

Процесс:

// GC находит корни → обходит граф объектов
class Program
{
    static Person _person;  // Корневой объект (статическое поле)
    
    void Example()
    {
        var p = new Person();  // Корень: локальная переменная
        p.Name = "Alice";
        
        // GC не удалит p, пока он в стеке
        // После выхода из метода p перестаёт быть корнем
    }
}

Когда запускается GC:

  • Недостаток памяти в куче
  • Вызов GC.Collect() (не рекомендуется)
  • Выход из процесса
  • Аллокация памяти превышает порог поколения
Поколения: Gen 0, Gen 1, Gen 2 — зачем?
обяз

Поколения (Generations) — оптимизация GC для разных типов объектов.

Gen 0 (Молодые объекты):

  • Новые объекты
  • Очищается часто (каждый раз, когда заполняется)
  • Быстрая сборка (небольшой размер)
  • Большинство объектов умирают здесь

Gen 1 (Пережившие Gen 0):

  • Объекты, которые пережили одну сборку Gen 0
  • Буферная зона
  • Сборка происходит реже

Gen 2 (Долгоживущие объекты):

  • Объекты, пережившие сборку Gen 1
  • Долгоживущие объекты (статические поля, кэши)
  • Сборка происходит редко
  • Полная сборка (Gen 0 + Gen 1 + Gen 2) — самая дорогая

Почему три поколения:

  • Гипотеза поколений: большинство объектов живут недолго
  • Оптимизация: частое освобождение мусора в Gen 0 (быстро)
  • Редкая очистка Gen 2 (медленно, но редко)
  • Баланс производительности и времени отклика

Демонстрация:

var obj = new object();       // Gen 0
GC.Collect();                 // obj выжил → Gen 1
GC.Collect();                 // obj выжил → Gen 2
GC.Collect();                 // obj может быть удалён (если нет ссылок)

// Посмотреть поколение
int generation = GC.GetGeneration(obj);  // 2
Large Object Heap (LOH) — объекты > 85 KB, особенности.
mid

Large Object Heap (LOH) — специальная куча для больших объектов.

Критерии попадания в LOH:

  • Объекты размером > 85 KB (для массивов)
  • Объекты размера > 85 KB (для ссылочных типов)
  • Все массивы double[] > 85 KB
  • Все объекты > 85 KB

Особенности LOH:

  • Не сжимается по умолчанию (это дорого)
  • Может вызывать фрагментацию памяти
  • Сборка происходит во время Gen 2
  • Объекты в LOH считаются Gen 2
  • В .NET Core 2.1+ появилась компактификация LOH

Проблемы LOH:

  • Фрагментация: объекты выделяются и освобождаются, оставляя "дыры"
  • Производительность: выделение больших объектов дороже
  • OutOfMemoryException: из-за фрагментации, даже если память есть

Как избежать проблем:

  • Используйте ArrayPool<T> для массивов
  • Используйте Span<T> и Memory<T>
  • Избегайте частого выделения больших объектов
  • Используйте GC.TryStartNoGCRegion() для критических участков
Когда вызывается GC — автоматически, GC.Collect() (не рекомендуется).
обяз

Автоматические вызовы GC:

  • Недостаточно памяти для нового объекта
  • Память в куче достигает порога для поколения
  • Физическая память системы заканчивается
  • Вызов GC.AddMemoryPressure()
  • Выход из приложения

Ручной вызов GC.Collect():

  • Не рекомендуется в продакшене
  • Может ухудшить производительность
  • Вызывает полную сборку (Gen 0 + 1 + 2 + LOH)
  • Используется только для диагностики и тестирования

Примеры:

// Принудительная сборка (только для диагностики!)
GC.Collect();          // Все поколения
GC.Collect(0);         // Только Gen 0
GC.Collect(2);         // Все поколения (включая LOH)

// Ожидание финализаторов
GC.WaitForPendingFinalizers();

// Проверка количества сборок
int gen0 = GC.CollectionCount(0);  // Количество сборок Gen 0
int gen1 = GC.CollectionCount(1);
int gen2 = GC.CollectionCount(2);

Когда всё же вызвать GC.Collect():

  • После тестирования на память
  • После освобождения больших ресурсов
  • В приложениях с низкой нагрузкой
  • Для диагностики утечек
IDisposable и Dispose — освобождение ресурсов.
обяз

IDisposable — интерфейс для ручного освобождения ресурсов.

Зачем нужен:

  • GC не знает о неуправляемых ресурсах (файлы, сокеты, соединения с БД)
  • Нужно освобождать ресурсы немедленно, а не ждать GC
  • Реализует паттерн "Deterministic Finalization"

Пример использования:

public class FileReader : IDisposable
{
    private FileStream _fileStream;
    private bool _disposed = false;
    
    public FileReader(string path)
    {
        _fileStream = File.OpenRead(path);
    }
    
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);  // Отключаем финализатор
    }
    
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        
        if (disposing)
        {
            // Освобождаем управляемые ресурсы
            _fileStream?.Dispose();
        }
        // Освобождаем неуправляемые ресурсы (если есть)
        
        _disposed = true;
    }
}

Использование с using:

// using гарантирует вызов Dispose()
using (var reader = new FileReader("file.txt"))
{
    // Читаем файл
} // Здесь вызывается reader.Dispose()

// Эквивалент без using
var reader2 = new FileReader("file.txt");
try { /* ... */ }
finally { reader2.Dispose(); }
Finalize (деструктор) — финализация, когда вызывается?
обяз

Finalize (финализатор) — метод, который вызывается сборщиком мусора перед удалением объекта.

Как реализовать:

public class MyClass
{
    // Финализатор (деструктор)
    ~MyClass()
    {
        // Освобождение ресурсов
        Console.WriteLine("Финализатор вызван");
    }
}

Когда вызывается:

  • GC обнаруживает недостижимый объект
  • Объект помещается в финализационную очередь
  • Отдельный поток GC вызывает финализаторы
  • Момент вызова недетерминирован — неизвестно когда
  • Может быть вызван несколько раз (если объект снова оживает)

Проблемы финализаторов:

  • Недетерминизм: неизвестно когда будет вызван
  • Производительность: объекты с финализаторами живут дольше
  • Сложность: нужно правильно реализовать паттерн Dispose
  • Может вызвать OutOfMemoryException (очередь финализации)

Правильный паттерн (Dispose + Finalize):

public class ResourceHolder : IDisposable
{
    private IntPtr _handle;  // Неуправляемый ресурс
    private bool _disposed = false;
    
    ~ResourceHolder()
    {
        Dispose(false);  // Только для неуправляемых ресурсов
    }
    
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);  // Не вызывать финализатор
    }
    
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        
        if (disposing)
        {
            // Освобождаем managed ресурсы
        }
        // Освобождаем unmanaged ресурсы (всегда)
        CloseHandle(_handle);
        _disposed = true;
    }
}

GC.SuppressFinalize:

  • Сообщает GC, что финализатор не нужно вызывать
  • Используется вместе с Dispose()
  • Улучшает производительность
using — во что компилируется?
обяз

using — синтаксический сахар для try-finally с вызовом Dispose().

Компиляция using:

// Исходный код
using (var stream = new FileStream("file.txt", FileMode.Open))
{
    stream.ReadByte();
}

// Компилируется в:
FileStream stream = null;
try
{
    stream = new FileStream("file.txt", FileMode.Open);
    stream.ReadByte();
}
finally
{
    if (stream != null)
        stream.Dispose();
}

using с несколькими объектами:

// Вложенные using
using (var file = new FileStream(...))
using (var reader = new StreamReader(file))
{
    reader.ReadToEnd();
}

// Компилируется в последовательные try-finally

using с throw:

// Dispose() вызывается даже при исключении
using (var stream = new FileStream("file.txt", FileMode.Open))
{
    throw new Exception("Ошибка");
} // stream.Dispose() всё равно вызовется

IAsyncDisposable (C# 8+):

// await using для асинхронного освобождения
await using (var conn = new SqlConnection(connectionString))
{
    await conn.OpenAsync();
    // ...
} // await conn.DisposeAsync()
Disposable паттерн (Dispose(bool disposing)) — для managed + unmanaged.
mid

Disposable паттерн — стандартная реализация для освобождения ресурсов.

Структура:

public class ResourceHolder : IDisposable
{
    private bool _disposed = false;
    
    // Публичный метод для клиентов
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }
    
    // Защищённый метод с параметром
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        
        if (disposing)
        {
            // ❗ Освобождаем УПРАВЛЯЕМЫЕ ресурсы
            // Ссылки на другие IDisposable объекты
            _stream?.Dispose();
            _connection?.Dispose();
        }
        
        // ❗ Освобождаем НЕУПРАВЛЯЕМЫЕ ресурсы
        // Всегда, даже при финализации
        CloseHandle(_handle);
        FreeMemory(_ptr);
        
        _disposed = true;
    }
    
    // Финализатор (вызывает Dispose(false))
    ~ResourceHolder()
    {
        Dispose(false);
    }
}

Почему bool disposing:

  • true — вызвано из Dispose() (явно). Можно освобождать managed ресурсы.
  • false — вызвано из финализатора. Нельзя обращаться к managed ресурсам (они могут быть уже удалены).

Пример использования:

public class ConnectionManager : IDisposable
{
    private SqlConnection _connection;  // Managed
    private IntPtr _nativeHandle;       // Unmanaged
    
    public void Open(string connectionString)
    {
        _connection = new SqlConnection(connectionString);
        _nativeHandle = CreateNativeConnection();
        _connection.Open();
    }
    
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        
        if (disposing)
        {
            // Только если явный вызов Dispose()
            _connection?.Dispose();
            _connection = null;
        }
        
        // Всегда освобождаем неуправляемые ресурсы
        if (_nativeHandle != IntPtr.Zero)
        {
            CloseNativeConnection(_nativeHandle);
            _nativeHandle = IntPtr.Zero;
        }
        
        _disposed = true;
    }
    
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }
    
    ~ConnectionManager()
    {
        Dispose(false);
    }
}
IAsyncDisposable — когда использовать?
mid

IAsyncDisposable — асинхронная версия IDisposable (C# 8+).

Когда использовать:

  • Освобождение асинхронных ресурсов
  • Закрытие сетевых соединений
  • Освобождение подключений к БД (асинхронное)
  • Закрытие потоков с асинхронными операциями

Пример:

public class AsyncResource : IAsyncDisposable
{
    private SqlConnection _connection;
    private bool _disposed = false;
    
    public async Task ConnectAsync(string connectionString)
    {
        _connection = new SqlConnection(connectionString);
        await _connection.OpenAsync();
    }
    
    public async ValueTask DisposeAsync()
    {
        await DisposeAsync(true);
        GC.SuppressFinalize(this);
    }
    
    protected virtual async ValueTask DisposeAsync(bool disposing)
    {
        if (_disposed) return;
        
        if (disposing)
        {
            // Асинхронное освобождение
            if (_connection != null)
                await _connection.DisposeAsync();
        }
        
        _disposed = true;
    }
}

// Использование
await using (var resource = new AsyncResource())
{
    await resource.ConnectAsync(connectionString);
    // ...
} // await resource.DisposeAsync()

Совместимость с IDisposable:

  • Класс может реализовывать оба интерфейса
  • await using вызывает DisposeAsync()
  • using вызовет Dispose()
WeakReference — зачем, когда использовать?
mid

WeakReference — слабая ссылка, которая не препятствует сборке мусора.

Когда использовать:

  • Кэширование — объекты могут быть удалены при нехватке памяти
  • События — слабые обработчики, чтобы не создавать утечек
  • Наблюдатели — без удержания объектов в памяти
  • Загрузка ресурсов — можно перезагрузить при необходимости

Пример:

public class Cache
{
    private Dictionary<string, WeakReference<object>> _cache = new();
    
    public void Add(string key, object value)
    {
        _cache[key] = new WeakReference<object>(value);
    }
    
    public object Get(string key)
    {
        if (_cache.TryGetValue(key, out var weakRef))
        {
            if (weakRef.TryGetTarget(out var target))
                return target;
            
            // Объект удалён сборщиком
            _cache.Remove(key);
        }
        return null;
    }
}

// Использование
var cache = new Cache();
cache.Add("data", new LargeObject());
var data = cache.Get("data");  // Объект жив

GC.Collect();
var data2 = cache.Get("data");  // null (если объект удалён)

Слабое событие:

public class EventSource
{
    private List<WeakReference<EventHandler>> _handlers = new();
    
    public void AddHandler(EventHandler handler)
    {
        _handlers.Add(new WeakReference<EventHandler>(handler));
    }
    
    public void RaiseEvent()
    {
        foreach (var weakRef in _handlers.ToList())
        {
            if (weakRef.TryGetTarget(out var handler))
                handler(this, EventArgs.Empty);
            else
                _handlers.Remove(weakRef);  // Удаляем мёртвые ссылки
        }
    }
}

Предостережения:

  • Проверяйте IsAlive или TryGetTarget перед использованием
  • Не используйте для критически важных объектов
  • Учитывайте, что объект может быть удалён в любой момент
GCHandle — закрепление объектов (pinning).
mid

GCHandle — закрепляет объект в памяти, чтобы GC не перемещал его.

Когда использовать:

  • P/Invoke — передача ссылок на объекты в неуправляемый код
  • Работа с указателями — безопасная адресация объекта
  • COM-взаимодействие — передача объектов в COM

Типы GCHandle:

  • Normal — обычная ссылка (удерживает объект)
  • Pinned — закреплённая ссылка (GC не перемещает)
  • Weak — слабая ссылка (не удерживает)
  • WeakTrackResurrection — слабая ссылка, отслеживающая финализацию

Пример:

// Закрепление массива для P/Invoke
byte[] buffer = new byte[1024];
GCHandle handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);

try
{
    // Получаем указатель на закреплённый объект
    IntPtr ptr = handle.AddrOfPinnedObject();
    
    // Передаём ptr в неуправляемый код
    SomeNativeMethod(ptr, buffer.Length);
}
finally
{
    // Обязательно освобождаем
    if (handle.IsAllocated)
        handle.Free();
}

// Безопасное получение указателя (упрощённо)
unsafe void PinArray(byte[] arr)
{
    fixed (byte* p = arr)  // Автоматически закрепляет и освобождает
    {
        // Работаем с p
    }
}

Предостережения:

  • Всегда освобождайте GCHandle (Free())
  • Закреплённые объекты ухудшают производительность GC
  • Избегайте длительного закрепления
  • Используйте fixed где возможно
GC.TryStartNoGCRegion — для высоконагруженных сценариев.
mid

GC.TryStartNoGCRegion() — пытается отключить GC на время выполнения критического участка.

Когда использовать:

  • Высоконагруженные системы (игры, финансы)
  • Критические участки, где GC недопустим
  • Обработка реального времени (real-time)
  • Когда нужно предсказуемое время выполнения

Пример:

// Попытка войти в режим без GC
if (GC.TryStartNoGCRegion(1024 * 1024 * 10))  // 10 MB
{
    try
    {
        // Код, где GC не должен выполняться
        ProcessCriticalData();
    }
    finally
    {
        // Выход из режима
        GC.EndNoGCRegion();
    }
}
else
{
    // Не удалось войти в режим (недостаточно памяти)
}

Важные нюансы:

  • Если во время NoGCRegion потребуется больше памяти, будет OutOfMemoryException
  • Используйте краткие участки
  • Не пытайтесь войти повторно (сначала выйдите)
  • Доступно только в .NET Core / .NET 5+
Что такое "утечка памяти" в .NET?
обяз

Утечка памяти — когда объект не может быть удалён GC, хотя он больше не нужен.

Основные причины:

1. Неотписанные события (Events)

  • Подписчик держит ссылку на издателя
  • Если не отписаться, подписчик живёт всегда
// ❌ Утечка
public class Publisher
{
    public event EventHandler Event;
}

public class Subscriber
{
    public Subscriber(Publisher p)
    {
        p.Event += OnEvent;  // Не отписались → утечка
    }
    void OnEvent(object sender, EventArgs e) { }
}

// ✅ Решение
p.Event -= OnEvent;  // Отписка
// или Weak Event Pattern

2. Статические поля

  • Статические поля живут вечно
  • Все объекты, на которые ссылается статическое поле, тоже живут вечно
public static class Cache
{
    public static List<object> Items = new();  // Растёт бесконечно
}

// Решение: использовать WeakReference или ограничивать размер

3. Закреплённые объекты (GCHandle)

  • Не освобождённые GCHandle удерживают объект
  • Всегда вызывайте Free()

4. Замыкания (Closures)

  • Лямбды захватывают переменные из внешнего контекста
  • Если лямбда хранится долго, все захваченные объекты тоже живут

5. Timer и таймеры

  • Не остановленный таймер держит объект
  • Всегда Dispose() таймеры

Как обнаружить утечку:

  • dotMemory (JetBrains)
  • PerfView (Microsoft)
  • Visual Studio Diagnostic Tools
  • Windows Performance Analyzer
Как найти утечку памяти — профайлеры.
mid

Инструменты для обнаружения утечек:

1. dotMemory (JetBrains)

  • Встроен в Rider / ReSharper
  • Анализ дампов памяти
  • Поиск самых больших объектов
  • Обнаружение утечек через события
  • Сравнение снимков (snapshots)

2. PerfView (Microsoft)

  • Бесплатный инструмент от Microsoft
  • Анализ GC и ETW событий
  • Поиск объектов, удерживаемых в памяти
  • Подходит для серверных приложений

3. Visual Studio Diagnostic Tools

  • Встроен в Visual Studio
  • Профилирование памяти
  • Анализ кучи
  • Поиск объектов с сильными ссылками

Процесс поиска утечки:

  1. Снимок 1 — до выполнения действия
  2. Снимок 2 — после выполнения действия (несколько раз)
  3. Сравнение — найти объекты, которые появились в снимке 2
  4. Анализ ссылок — найти GC Root, удерживающий объект

  • Сделать снимок памяти
  • Выполнить действие, которое должно освободить память
  • Сделать второй снимок
  • Найти объекты, которые остались в памяти
  • Изучить цепочку ссылок к GC Root

POH (Pinned Object Heap) — что это?
mid

Pinned Object Heap (POH) — отдельная куча для закреплённых объектов (появилась в .NET 5).

Проблема, которую решает:

  • Раньше закреплённые объекты (GCHandle) хранились в обычной куче
  • Мешали GC, так как не могли быть перемещены
  • Увеличивали фрагментацию

Как работает POH:

  • Закреплённые объекты выделяются в отдельной куче
  • Не влияют на компактификацию основной кучи
  • Улучшают производительность GC
  • Объекты в POH не сжимаются

Объекты, попадающие в POH:

  • GCHandle.Alloc с GCHandleType.Pinned
  • Массивы, закреплённые через fixed
  • P/Invoke буферы
  • Объекты, созданные через NativeMemory

Преимущества:

  • Меньше фрагментации в основной куче
  • GC работает быстрее
  • Лучшая производительность для P/Invoke
