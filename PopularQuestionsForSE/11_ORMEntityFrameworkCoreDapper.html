🔗 11. ORM: Entity Framework Core и Dapper 100%

Entity Framework Core — Code First vs Database First.
обяз

Code First:

  • Сначала пишутся классы C#
  • БД создаётся автоматически из моделей
  • Миграции для обновления схемы
  • Полный контроль над кодом
  • Подходит для новых проектов
// Модель
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
}

// DbContext
public class AppDbContext : DbContext
{
    public DbSet<User> Users { get; set; }
}

// Миграции
dotnet ef migrations add InitialCreate
dotnet ef database update

Database First:

  • Сначала создаётся БД
  • Генерируются классы из существующей БД
  • Подходит для существующих БД
  • Меньше контроля над кодом
// Scaffold из существующей БД
dotnet ef dbcontext scaffold "ConnectionString" Microsoft.EntityFrameworkCore.SqlServer
    -o Models
    -f

Сравнение:

Характеристика Code First Database First
Начало Код → БД БД → Код
Контроль Полный (код) Ограниченный (БД)
Миграции Автоматические Ручные (или генерируются)
Подходит для Новые проекты Существующие БД
Миграции (Migrations) — Add-Migration, Update-Database.
обяз

Миграции — управление изменениями схемы БД.

Команды:

// Создать миграцию
dotnet ef migrations add AddUserTable

// Обновить БД
dotnet ef database update

// Откатить к предыдущей миграции
dotnet ef database update PreviousMigrationName

// Удалить последнюю миграцию
dotnet ef migrations remove

// Сгенерировать SQL-скрипт
dotnet ef migrations script

Пример миграции:

public partial class AddUserTable : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateTable(
            name: "Users",
            columns: table => new
            {
                Id = table.Column<int>(nullable: false)
                    .Annotation("SqlServer:Identity", "1, 1"),
                Name = table.Column<string>(nullable: false),
                Email = table.Column<string>(nullable: false)
            },
            constraints: table =>
            {
                table.PrimaryKey("PK_Users", x => x.Id);
            });
    }
    
    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropTable(name: "Users");
    }
}

В продакшене:

  • Никогда не применяйте миграции автоматически
  • Генерируйте SQL-скрипты и применяйте вручную
  • Используйте EnsureCreated() только для тестов
AsNoTracking() — когда использовать (только чтение).
обяз

AsNoTracking() — отключает отслеживание изменений для запроса.

Когда использовать:

  • Только чтение (отображение данных)
  • Отчёты и аналитика
  • API для получения данных
  • Высоконагруженные запросы
  • Объекты, которые не будут изменяться

Преимущества:

  • Выше производительность (меньше накладных расходов)
  • Меньше потребление памяти
  • Быстрее выполнение запросов

Пример:

// ❌ Без AsNoTracking — отслеживание (медленнее)
var users = context.Users.ToList();

// ✅ С AsNoTracking — только чтение (быстрее)
var users = context.Users
    .AsNoTracking()
    .ToList();

// AsNoTrackingWithIdentityResolution (EF Core 5+)
// Убирает дубликаты при связях
var orders = context.Orders
    .Include(o => o.User)
    .AsNoTrackingWithIdentityResolution()
    .ToList();

Когда НЕ использовать:

  • Данные будут изменяться и сохраняться
  • Нужен ChangeTracker для обновлений
  • Каскадные обновления
Include() / ThenInclude() — Eager Loading.
обяз

Eager Loading — загрузка связанных данных в одном запросе.

Include() — загрузка навигационного свойства (один уровень).

// Загружаем пользователей с их заказами
var users = context.Users
    .Include(u => u.Orders)
    .ToList();

// Загружаем заказы с пользователями
var orders = context.Orders
    .Include(o => o.User)
    .ToList();

ThenInclude() — загрузка вложенных свойств (несколько уровней).

// Загружаем пользователей → заказы → товары в заказе
var users = context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.Items)
            .ThenInclude(i => i.Product)
    .ToList();

// Альтернативный синтаксис
var users2 = context.Users
    .Include("Orders.Items.Product")
    .ToList();

Сравнение подходов:

Подход Запросов к БД Когда использовать
Eager (Include) 1-2 запроса Данные нужны сразу
Lazy (по умолчанию) 1 + N запросов Редко используемые связи
Explicit (Load) По запросу Тонкий контроль

Внимание: чрезмерное использование Include() может привести к большим запросам (N+1 проблема).

Lazy Loading — прокси, когда опасно (N+1 проблема).
mid

Lazy Loading — загрузка связанных данных только при обращении к ним.

Настройка:

// Включение Lazy Loading
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseLazyLoadingProxies()
           .UseSqlServer(connectionString));

// Модель с виртуальными свойствами
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    
    public virtual ICollection<Order> Orders { get; set; }
}

N+1 проблема:

// ❌ Lazy Loading — N+1 запросов
var users = context.Users.ToList();  // 1 запрос
foreach (var user in users)
{
    // Каждый раз новый запрос (N запросов)
    foreach (var order in user.Orders)
    {
        Console.WriteLine(order.Total);
    }
}
// Итого: 1 + N запросов (медленно)

// ✅ Eager Loading — 1 запрос
var users = context.Users
    .Include(u => u.Orders)
    .ToList();
foreach (var user in users)
{
    foreach (var order in user.Orders)
    {
        Console.WriteLine(order.Total);
    }
}
// Итого: 1 запрос (быстро)

Когда опасно:

  • В циклах с большим количеством записей
  • В высоконагруженных API
  • При сериализации (JSON) — может загрузить всю БД
  • Когда не знаете о существовании Lazy Loading
IQueryable vs IEnumerable в EF — критично.
обяз

IQueryable — выполнение в БД

  • Строит SQL-запрос
  • Фильтрация на стороне сервера
  • Используйте для фильтрации
// ✅ IQueryable — фильтрация в БД
IQueryable<User> query = context.Users;
var users = query
    .Where(u => u.Age > 18)
    .OrderBy(u => u.Name)
    .Take(10)
    .ToList();
// SQL: SELECT * FROM Users WHERE Age > 18 ORDER BY Name OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY

IEnumerable — выполнение в памяти

  • Все данные загружаются в память
  • Фильтрация на клиенте
  • Используйте только после ToList()
// ❌ IEnumerable — все данные в память
IEnumerable<User> users = context.Users;
var result = users
    .Where(u => u.Age > 18)
    .OrderBy(u => u.Name)
    .Take(10)
    .ToList();
// SQL: SELECT * FROM Users (все записи!)
// Фильтрация, сортировка в .NET

Правила:

  • Всегда используйте IQueryable для фильтрации в БД
  • Превращайте в IEnumerable только после ToList()
  • Никогда не вызывайте ToList() до Where()
Транзакции в EF — BeginTransaction, SaveChanges.
обяз

Транзакции — гарантируют атомарность операций.

1. Автоматическая транзакция (SaveChanges)

// Одна транзакция
context.Users.Add(new User { Name = "Alice" });
context.Orders.Add(new Order { UserId = 1, Total = 100 });
await context.SaveChangesAsync();  // Всё или ничего

2. Явная транзакция (BeginTransaction)

using var transaction = await context.Database.BeginTransactionAsync();
try
{
    context.Users.Add(new User { Name = "Alice" });
    await context.SaveChangesAsync();
    
    context.Orders.Add(new Order { UserId = 1, Total = 100 });
    await context.SaveChangesAsync();
    
    await transaction.CommitAsync();  // Подтверждаем
}
catch
{
    await transaction.RollbackAsync();  // Откатываем
    throw;
}

3. Транзакция с сохранением точек

using var transaction = await context.Database.BeginTransactionAsync();
await transaction.CreateSavepointAsync("BeforeData");

try
{
    // Действия
    await context.SaveChangesAsync();
}
catch
{
    // Откат к точке
    await transaction.RollbackToSavepointAsync("BeforeData");
}

4. Распределённые транзакции (несколько БД)

using var scope = new TransactionScope(TransactionScopeAsyncFlowOption.Enabled);
try
{
    await context1.SaveChangesAsync();
    await context2.SaveChangesAsync();
    scope.Complete();  // Две БД в одной транзакции
}
catch
{
    // Автоматический откат
}
Dapper — микро-ORM, когда использовать.
mid

Dapper — лёгкая ORM от Stack Overflow.

Преимущества:

  • Максимальная производительность (близко к ADO.NET)
  • Маленький размер (без тяжеловесных функций)
  • Полный контроль над SQL
  • Поддержка raw SQL, хранимых процедур
  • Без сложных конфигураций

Примеры:

// Подключение
using var connection = new SqlConnection(connectionString);

// Простой запрос
var users = connection.Query<User>("SELECT * FROM Users WHERE Active = 1").ToList();

// Параметризованный запрос
var user = connection.QueryFirstOrDefault<User>(
    "SELECT * FROM Users WHERE Id = @Id",
    new { Id = 5 }
);

// Сложный запрос
var orders = connection.Query<Order, User, Order>(
    @"SELECT o.*, u.* 
      FROM Orders o
      INNER JOIN Users u ON o.UserId = u.Id
      WHERE o.Total > @MinTotal",
    (order, user) =>
    {
        order.User = user;
        return order;
    },
    new { MinTotal = 1000 }
).ToList();

// Хранимая процедура
var result = connection.Query<User>(
    "sp_GetUsers",
    new { Active = true },
    commandType: CommandType.StoredProcedure
);

Когда использовать:

  • Dapper: производительность критична, сложные запросы, микросервисы
  • EF Core: сложные связи, удобство разработки, CRUD-приложения
EF vs Dapper — производительность, удобство, когда что выбирать.
обяз
Характеристика Entity Framework Core Dapper
Производительность Медленнее (обёртка) Быстрее (почти как ADO.NET)
Удобство Высокое (LINQ, миграции) Низкое (ручной SQL)
Сложные запросы Ограниченные (LINQ) Полный контроль (SQL)
Миграции Автоматические Нет (ручные)
Отслеживание изменений Да (ChangeTracker) Нет
Связи (Include) Автоматические Ручные (JOIN)
Размер Тяжёлый Лёгкий
Где использовать CRUD, бизнес-приложения Отчёты, микросервисы, производительность

Когда выбрать EF Core:

  • Новый проект с типовыми CRUD-операциями
  • Сложная бизнес-логика с множеством связей
  • Команда не знает SQL на высоком уровне
  • Нужны миграции и отслеживание изменений

Когда выбрать Dapper:

  • Высокая производительность критична
  • Сложные запросы с оптимизациями
  • Микросервисная архитектура
  • Команда хорошо знает SQL
  • Работа с существующей БД
Query Tracking — отслеживание изменений, когда отключать.
mid

Change Tracking — отслеживание изменений объектов для SaveChanges.

По умолчанию: включено (объекты отслеживаются).

// Отслеживание включено
var user = context.Users.Find(1);
user.Name = "New Name";
context.SaveChanges();  // UPDATE в БД

Отключение отслеживания:

// 1. AsNoTracking() для конкретного запроса
var users = context.Users.AsNoTracking().ToList();

// 2. AsNoTrackingWithIdentityResolution() (EF Core 5+)
var users = context.Users
    .AsNoTrackingWithIdentityResolution()
    .ToList();

// 3. Глобальное отключение
context.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;
var users = context.Users.ToList();  // Без отслеживания

Когда отключать:

  • Только чтение (API, отчёты)
  • Большие объёмы данных
  • Высоконагруженные запросы
  • Объекты, которые не будут изменяться

Когда включено:

  • Данные будут изменяться
  • Нужны каскадные обновления
  • Работа с связями (загрузка связанных данных)

Производительность:

  • Отслеживание создаёт накладные расходы
  • Для 1000+ записей — заметная разница
  • Всегда отключайте для больших выборок
