🐳 14. Docker. CI/CD. Брокеры Mid+

Docker — что это, зачем нужен.
обяз

Docker — платформа для контейнеризации приложений.

Что такое контейнер:

  • Изолированная среда выполнения
  • Включает приложение + зависимости
  • Легче виртуальной машины
  • Один образ — везде работает одинаково

Основные понятия:

  • Image (Образ): шаблон для контейнера
  • Container: запущенный экземпляр образа
  • Dockerfile: инструкции для сборки образа
  • Registry: хранилище образов (Docker Hub)

Зачем нужен:

  • Одинаковое окружение (разработка → продакшен)
  • Изоляция (приложения не мешают друг другу)
  • Масштабирование (запуск нескольких контейнеров)
  • CI/CD (автоматизация деплоя)

Пример Dockerfile:

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /app
COPY *.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o out

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/out .
ENTRYPOINT ["dotnet", "MyApp.dll"]
Образ (Image) vs Контейнер (Container) — разница.
обяз

Образ (Image):

  • Шаблон для создания контейнеров
  • Статический (неизменяемый)
  • Хранится в реестре
  • Содержит слои (layers)
  • Пример: myapp:1.0

Контейнер (Container):

  • Экземпляр образа
  • Динамический (можно изменять)
  • Запускается на сервере
  • Имеет своё состояние
  • Пример: запущенный контейнер из образа myapp:1.0

Сравнение:

Характеристика Image (Образ) Container (Контейнер)
Состояние Статический Динамический
Изменяемость Неизменяемый Можно изменять
Хранение Registry Запущен / остановлен
Создание docker build docker run
Dockerfile — основные инструкции (FROM, COPY, RUN, CMD).
mid

Основные инструкции Dockerfile:

FROM — базовый образ

FROM mcr.microsoft.com/dotnet/aspnet:8.0

WORKDIR — рабочая директория

WORKDIR /app

COPY — копирование файлов

COPY . .

RUN — выполнение команд (при сборке)

RUN apt-get update && apt-get install -y curl

CMD — команда по умолчанию (может быть переопределена)

CMD ["dotnet", "MyApp.dll"]

ENTRYPOINT — команда запуска (не может быть переопределена)

ENTRYPOINT ["dotnet", "MyApp.dll"]

EXPOSE — открытый порт

EXPOSE 80

ENV — переменные окружения

ENV ASPNETCORE_ENVIRONMENT=Production

ARG — аргументы сборки

ARG VERSION=1.0

Пример полного Dockerfile:

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
ARG VERSION=1.0
WORKDIR /src
COPY ["MyApp.csproj", "."]
RUN dotnet restore
COPY . .
RUN dotnet build -c Release --no-restore
RUN dotnet publish -c Release -o /app --no-restore -p:Version=${VERSION}

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app .
ENV ASPNETCORE_URLS=http://*:8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "MyApp.dll"]
Docker Compose — для чего.
mid

Docker Compose — инструмент для запуска многоконтейнерных приложений.

Зачем нужен:

  • Запуск нескольких сервисов (API + БД + Redis)
  • Управление зависимостями
  • Одна команда: docker-compose up
  • Конфигурация в YAML

Пример docker-compose.yml:

version: '3.8'

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "5000:8080"
    environment:
      - ConnectionStrings__Default=Server=db;Database=MyApp;User=sa;Password=Passw0rd!
    depends_on:
      - db
      - redis
    networks:
      - app-network

  db:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      - ACCEPT_EULA=Y
      - SA_PASSWORD=Passw0rd!
    ports:
      - "1433:1433"
    volumes:
      - sql-data:/var/opt/mssql
    networks:
      - app-network

  redis:
    image: redis:alpine
    ports:
      - "6379:6379"
    networks:
      - app-network

volumes:
  sql-data:

networks:
  app-network:
Docker vs Виртуальная машина — различия.
обяз
Характеристика Docker (Контейнер) VM (Виртуальная машина)
Запуск Мгновенно (секунды) Медленно (минуты)
Размер Маленький (МБ) Большой (ГБ)
Ресурсы Мало (общая ОС) Много (полная ОС)
Изоляция Частичная (kernel) Полная (hypervisor)
Портативность Высокая Средняя
Скорость Высокая Низкая

Когда использовать Docker:

  • Микросервисы
  • CI/CD
  • Разработка и тестирование
  • Быстрый старт

Когда использовать VM:

  • Изоляция ядра (безопасность)
  • Требуется полная ОС
  • Совместимость с устаревшим ПО
  • Разные ОС (Windows + Linux)
Брокер сообщений — RabbitMQ, Apache Kafka.
обяз

Брокер сообщений — промежуточный слой для обмена сообщениями между сервисами.

RabbitMQ:

  • Очередь сообщений (AMQP)
  • Сложные маршрутизации (Exchanges, Bindings)
  • Гарантии доставки (acknowledgments)
  • Подходит для: микросервисы, задачи в фоне, RPC
  • Пример: отправка email, обработка заказов

Apache Kafka:

  • Распределённый лог (паттерн "журнал")
  • Высокая пропускная способность (миллионы сообщений/сек)
  • Хранение данных на диске
  • Подходит для: стриминг данных, аналитика, event sourcing
  • Пример: логирование, трекинг событий

Сравнение:

Характеристика RabbitMQ Kafka
Модель Очередь Журнал
Скорость Высокая Очень высокая
Хранение Пока не обработано Настраиваемое (дни/месяцы)
Повторное чтение Нет Да (офсеты)
Сложность Средняя Высокая
Очереди сообщений — зачем нужны, паттерны.
обяз

Зачем нужны очереди сообщений:

  • Развязка сервисов (Decoupling)
  • Асинхронная обработка (не блокировать пользователя)
  • Отказоустойчивость (сообщения не теряются)
  • Масштабирование (несколько потребителей)
  • Балансировка нагрузки (распределение задач)

Паттерны:

1. Point-to-Point (Очередь)

  • Один отправитель → Очередь → Один получатель
  • Сообщение удаляется после получения

2. Publish-Subscribe (Топик)

  • Один отправитель → Топик → Множество получателей
  • Каждый получатель получает копию

3. Request-Reply (Запрос-ответ)

  • Отправка запроса → Получение ответа
  • Асинхронный RPC

4. Event-Driven (События)

  • Публикация событий
  • Реакция сервисов на события
  • Event Sourcing, CQRS
At-least-once, At-most-once, Exactly-once семантика.
mid

At-most-once (Не более одного раза)

  • Сообщение доставляется максимум один раз
  • Может быть потеряно
  • Быстро, без подтверждений
  • Пример: логи, метрики (потеря допустима)

At-least-once (Не менее одного раза)

  • Сообщение доставляется как минимум один раз
  • Могут быть дубликаты
  • Требует идемпотентности получателя
  • Пример: заказы, платежи (дубликаты недопустимы)

Exactly-once (Ровно один раз)

  • Сообщение доставляется точно один раз
  • Сложно реализовать (идеальный случай)
  • Работает в Kafka с транзакциями
  • Пример: финансовые операции

Реализация в брокерах:

Брокер At-most-once At-least-once Exactly-once
RabbitMQ ✅ ✅ (ack) ❌ (только с доп. кодом)
Kafka ✅ ✅ (offset commit) ✅ (транзакции)
Idempotent сервисы — как строить.
mid

Идемпотентность — одинаковый результат при повторных вызовах.

Почему важна:

  • Повторные запросы из-за сетевых проблем
  • At-least-once доставка
  • Ретри клиентов

Способы реализации:

1. Уникальный ID запроса (Idempotency Key)

// Клиент
var requestId = Guid.NewGuid().ToString();
var response = await httpClient.PostAsync(url, 
    new { IdempotencyKey = requestId, Data = data });

// Сервер
public async Task<IActionResult> Process(ProcessRequest request)
{
    if (await _cache.ExistsAsync(request.IdempotencyKey))
        return Ok("Already processed");
    
    await ProcessData(request.Data);
    await _cache.SetAsync(request.IdempotencyKey, "done", TimeSpan.FromHours(24));
    return Ok("Processed");
}

2. Версионирование

// Использование ETag или версии ресурса
PUT /api/users/5 HTTP/1.1
If-Match: "123456789"

3. Обработка дубликатов

// В БД — проверка уникальности
CREATE TABLE ProcessedRequests (
    IdempotencyKey VARCHAR(36) PRIMARY KEY,
    ProcessedAt DATETIME
);

-- При вставке — уникальность обеспечивает идемпотентность

4. Обновление ресурсов

// PUT — идемпотентен по определению
PUT /api/users/5
{ "name": "Alice" }  // Повторный вызов даёт тот же результат
Circuit Breaker — паттерн для распределённых систем.
mid

Circuit Breaker (Предохранитель) — защита от cascading failures.

Состояния:

  • Closed (Закрыт): запросы проходят, счётчик ошибок растёт
  • Open (Открыт): запросы блокируются (fail fast)
  • Half-Open (Полуоткрыт): пробные запросы для восстановления

Пример с Polly:

using Polly;

var policy = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(
        exceptionsAllowedBeforeBreaking: 3,
        durationOfBreak: TimeSpan.FromSeconds(30),
        onBreak: (ex, timespan) => Console.WriteLine($"Circuit open: {timespan}"),
        onReset: () => Console.WriteLine("Circuit closed"),
        onHalfOpen: () => Console.WriteLine("Circuit half-open")
    );

// Использование
var result = await policy.ExecuteAsync(async () =>
{
    var response = await httpClient.GetAsync("https://api.example.com");
    return await response.Content.ReadAsStringAsync();
});

Реализация вручную:

public class CircuitBreaker
{
    private int _failureCount = 0;
    private DateTime _lastFailure;
    private CircuitState _state = CircuitState.Closed;
    
    public async Task<T> ExecuteAsync<T>(Func<Task<T>> action)
    {
        if (_state == CircuitState.Open)
        {
            if (DateTime.Now - _lastFailure > TimeSpan.FromSeconds(30))
                _state = CircuitState.HalfOpen;
            else
                throw new CircuitOpenException();
        }
        
        try
        {
            var result = await action();
            if (_state == CircuitState.HalfOpen)
                _state = CircuitState.Closed;
            _failureCount = 0;
            return result;
        }
        catch
        {
            _failureCount++;
            _lastFailure = DateTime.Now;
            if (_failureCount >= 3)
                _state = CircuitState.Open;
            throw;
        }
    }
}
