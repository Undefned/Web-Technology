⚡ 6. Многопоточность и Асинхронность 100%

Процесс vs Поток (Process vs Thread) — разница?
обяз

Процесс (Process):

  • Изолированный экземпляр выполняющейся программы
  • Имеет собственное виртуальное адресное пространство
  • Содержит один или несколько потоков
  • Ресурсы процесса изолированы от других процессов
  • Ошибка в одном процессе не влияет на другие
  • Создание процесса — дорогая операция

Поток (Thread):

  • Единица выполнения внутри процесса
  • Потоки делят память процесса (кучу, статические данные)
  • Каждый поток имеет свой стек и регистры
  • Создание потока — дешевле, чем процесса
  • Ошибка в одном потоке может "убить" весь процесс
  • Переключение между потоками быстрее, чем между процессами

Сравнение:

Характеристика Процесс Поток
Память Изолированная Общая
Создание Дорогое Дешёвое
Переключение Медленное Быстрое
Безопасность Высокая Низкая
Обмен данными IPC (сложно) Прямой доступ (легко)

Пример в C#:

// Процесс
var process = Process.Start("notepad.exe");
process.WaitForExit();

// Поток
var thread = new Thread(() => Console.WriteLine("Hello from thread"));
thread.Start();
Thread vs Task — отличия, что использовать?
обяз

Thread:

  • Низкоуровневый объект, представляющий поток ОС
  • Занимает ~1 МБ стека
  • Создание дорогое
  • Не имеет встроенной поддержки async/await
  • Используется для фоновых задач с долгим временем жизни
  • Можно управлять приоритетом, состоянием

Task:

  • Высокоуровневая абстракция над пулом потоков
  • Использует существующие потоки из ThreadPool
  • Создание дешёвое
  • Поддерживает async/await
  • Поддерживает отмену (CancellationToken)
  • Поддерживает продолжения (ContinueWith)
  • Поддерживает агрегацию (WhenAll, WhenAny)

Сравнение:

Характеристика Thread Task
Создание Дорогое (1 МБ) Дешёвое (пул потоков)
async/await Нет Да
Отмена Сложно CancellationToken
Возврат результата Нет Task<TResult>
Исключения В потоке Агрегированные

Что использовать:

  • Task: в 99% случаев (асинхронные операции, API, веб)
  • Thread: только для долгоживущих фоновых задач, где нужен контроль

Примеры:

// Thread
var thread = new Thread(() => DoWork());
thread.IsBackground = true;
thread.Start();

// Task
Task.Run(() => DoWork());  // Использует ThreadPool
await Task.Run(() => DoWork());  // С async/await

// Task с результатом
var task = Task.Run(() => ComputeResult());
int result = await task;
ThreadPool — зачем нужен, как работает?
обяз

ThreadPool (пул потоков) — управляет набором рабочих потоков для выполнения задач.

Зачем нужен:

  • Избегает затрат на создание/уничтожение потоков
  • Ограничивает количество параллельных потоков
  • Эффективно использует ресурсы
  • Автоматически управляет размером пула

Как работает:

  • При запуске создаётся минимальное количество потоков
  • Задачи помещаются в очередь
  • Потоки забирают задачи из очереди
  • При высокой нагрузке пул расширяется
  • При простое потоки завершаются

Параметры пула:

// Получить настройки
ThreadPool.GetMinThreads(out int minWorker, out int minIO);
ThreadPool.GetMaxThreads(out int maxWorker, out int maxIO);

// Изменить настройки
ThreadPool.SetMinThreads(4, 4);  // Минимум 4 рабочих и 4 порта завершения
ThreadPool.SetMaxThreads(100, 100);  // Максимум 100

// Использование
ThreadPool.QueueUserWorkItem(state => DoWork());
ThreadPool.QueueUserWorkItem(DoWork, "параметр");

Проблемы ThreadPool:

  • Блокирующие операции — могут исчерпать пул
  • Долгие задачи — лучше использовать отдельный поток
  • Нельзя контролировать конкретный поток
TPL (Task Parallel Library) — Parallel.For, Parallel.ForEach.
mid

TPL — библиотека для параллельного программирования.

Parallel.For — параллельный цикл (for)

// Обычный цикл
for (int i = 0; i < 1000; i++)
    Process(i);

// Параллельный цикл
Parallel.For(0, 1000, i => Process(i));

// С локальными данными (оптимизация)
Parallel.For(0, 1000,
    () => new List<int>(),  // Инициализация для каждого потока
    (i, state, local) =>    // Тело цикла
    {
        local.Add(i * i);
        return local;
    },
    local =>                // Пост-обработка
    {
        lock (results) results.AddRange(local);
    });

Parallel.ForEach — параллельный цикл по коллекции

var items = Enumerable.Range(0, 1000).ToList();

// Параллельная обработка
Parallel.ForEach(items, item => Process(item));

// С опциями
var options = new ParallelOptions
{
    MaxDegreeOfParallelism = 4,  // Не более 4 потоков
    CancellationToken = cts.Token
};
Parallel.ForEach(items, options, item => Process(item));

Важно:

  • Используйте для CPU-bound задач
  • Не используйте для IO-bound задач (лучше async/await)
  • Всегда обрабатывайте исключения
  • Следите за Deadlock при работе с общими ресурсами
async / await — как работает, State Machine.
обяз

async/await — механизм асинхронного программирования на основе State Machine.

Как работает:

  1. Компилятор генерирует структуру-состояние (IAsyncStateMachine)
  2. Метод разбивается на состояния (до await, после await)
  3. При вызове await метод приостанавливается
  4. Управление возвращается вызывающему коду
  5. Когда Task завершается, выполнение продолжается с того же места
  6. Контекст синхронизации восстанавливается (SynchronizationContext)

Пример (упрощённо):

// Исходный код
async Task<int> GetDataAsync()
{
    Console.WriteLine("Старт");
    var data = await DownloadAsync();
    Console.WriteLine("После загрузки");
    return data.Length;
}

// Компилируется в State Machine
struct GetDataAsyncStateMachine : IAsyncStateMachine
{
    int _state;
    TaskAwaiter<string> _awaiter;
    int _result;
    
    void MoveNext()
    {
        switch (_state)
        {
            case 0:
                Console.WriteLine("Старт");
                _awaiter = DownloadAsync().GetAwaiter();
                if (!_awaiter.IsCompleted)
                {
                    _state = 1;
                    // Регистрируем продолжение
                    return;
                }
                goto case 1;
            case 1:
                var data = _awaiter.GetResult();
                Console.WriteLine("После загрузки");
                _result = data.Length;
                _state = -1;
                break;
        }
    }
}

Важные нюансы:

  • async метод всегда возвращает Task или Task<T>
  • await можно использовать только в async методах
  • Метод выполняется синхронно до первого await
  • После await выполнение может продолжиться в другом потоке
  • Используйте ConfigureAwait(false) для избежания контекста UI
Почему async void — плохо (кроме событий)?
обяз

async void — асинхронный метод, который не возвращает Task.

Почему это плохо:

1. Исключения теряются

  • Исключения в async void не перехватываются вызывающим кодом
  • Приводят к падению приложения (UnhandledException)
  • Трудно отлаживать
async void BadMethod()
{
    throw new Exception("Ошибка");  // Вызовет UnhandledException
}

try
{
    BadMethod();  // Исключение НЕ перехватывается!
}
catch (Exception) { }  // Сюда не попадём

2. Нельзя дождаться завершения

  • Нельзя использовать await для async void
  • Неизвестно, когда метод закончится
  • Нельзя получить результат

3. Трудно тестировать

  • Unit-тесты не могут дождаться завершения
  • Сложно проверить результат

Когда всё же можно:

  • Обработчики событий (Windows Forms, WPF, ASP.NET Core)
  • Только если метод никогда не выбрасывает исключения
  • Всегда перехватывайте исключения внутри

Правильный подход:

// ❌ Плохо
async void OnButtonClick(object sender, EventArgs e)
{
    await DoSomethingAsync();  // Ошибка убьёт приложение
}

// ✅ Хорошо
async void OnButtonClick(object sender, EventArgs e)
{
    try
    {
        await DoSomethingAsync();
    }
    catch (Exception ex)
    {
        Logger.LogError(ex);
        MessageBox.Show("Ошибка: " + ex.Message);
    }
}
ConfigureAwait(false) — зачем, когда использовать?
обяз

ConfigureAwait(false) — указывает, что продолжение после await не требует исходного контекста синхронизации.

Что такое SynchronizationContext:

  • В UI приложениях (WPF, WinForms) — главный поток (UI Thread)
  • В ASP.NET Core — контекст запроса
  • По умолчанию после await выполнение продолжается в том же контексте
  • Это может вызвать Deadlock

Проблема Deadlock:

// WPF приложение
void Button_Click(object sender, EventArgs e)
{
    var task = GetDataAsync();
    task.Wait();  // ❌ Блокировка UI потока → Deadlock!
}

async Task<string> GetDataAsync()
{
    // UI поток
    var result = await DownloadAsync();  // После await нужно вернуться в UI поток
    return result;  // Deadlock — UI заблокирован ожиданием
}

// Решение
async Task<string> GetDataAsync()
{
    var result = await DownloadAsync().ConfigureAwait(false);
    // Продолжение в пуле потоков, а не в UI
    return result;
}

Когда использовать ConfigureAwait(false):

  • Библиотеки — не знают о контексте вызова
  • Код без UI — консоль, сервисы, микросервисы
  • Чтобы избежать Deadlock
  • Для производительности — меньше переключений контекста

Когда НЕ использовать ConfigureAwait(false):

  • UI приложения — нужно обновить UI после await
  • ASP.NET Core (современные версии) — Context не нужен
  • Когда важен HttpContext

Современные рекомендации (.NET Core 3+):

  • В ASP.NET Core нет SynchronizationContext
  • ConfigureAwait(false) не обязателен, но полезен
  • Лучше использовать ConfigureAwait(false) в библиотеках
Task vs ValueTask — разница, когда использовать ValueTask?
mid

Task:

  • Ссылочный тип, всегда аллоцируется в куче
  • Подходит для асинхронных операций
  • Хорош для долгих операций
  • Поддерживает все возможности TPL

ValueTask:

  • Структура (значимый тип), может не аллоцироваться
  • Подходит для синхронных операций, которые могут быть асинхронными
  • Может быть несколько раз использован (в отличие от ValueTask)
  • Ограниченная поддержка TPL

Когда использовать:

  • ValueTask: если результат часто синхронный (кэш, мемоизация)
  • ValueTask: в горячих путях (часто вызывается)
  • Task: для любых долгих асинхронных операций
  • Task: если нужны возможности TPL

Пример:

// ❌ Плохо — всегда аллоцирует Task
public async Task<int> GetCachedValueAsync()
{
    if (_cache.TryGetValue(out int value))
        return value;  // ❌ Всё равно создаётся Task
    return await ComputeValueAsync();
}

// ✅ Хорошо — ValueTask без аллокации
public async ValueTask<int> GetCachedValueAsync()
{
    if (_cache.TryGetValue(out int value))
        return value;  // ✅ Нет аллокации (ValueTask)
    return await ComputeValueAsync();
}

Важно:

  • ValueTask можно await только один раз
  • Не сохраняйте ValueTask в переменные (может быть уже использован)
  • Используйте ValueTask в горячих путях (часто вызываемые методы)
lock — синхронизация, объект блокировки.
обяз

lock — ключевое слово для синхронизации доступа к ресурсам.

Как работает:

  • Использует Monitor.Enter() и Monitor.Exit()
  • Только один поток может войти в блок lock
  • Остальные потоки блокируются до освобождения
  • Блокировка снимается в finally (гарантированно)

Пример:

private readonly object _locker = new object();
private int _counter = 0;

public void Increment()
{
    lock (_locker)
    {
        _counter++;
    }
}

public int GetCounter()
{
    lock (_locker)
    {
        return _counter;
    }
}

Правила выбора объекта блокировки:

  • Никогда не используйте lock(this) (публичный объект)
  • Никогда не используйте lock(typeof(MyClass)) (публичный объект)
  • Никогда не используйте lock("string") (строки интернируются)
  • Используйте private readonly object
  • Используйте отдельный объект для каждого ресурса

lock vs Monitor:

// lock — синтаксический сахар
lock (_locker)
{
    // Код
}

// Эквивалентно
try
{
    Monitor.Enter(_locker);
    // Код
}
finally
{
    Monitor.Exit(_locker);
}

Опасности:

  • Deadlock — взаимная блокировка
  • Starvation — поток долго ждёт блокировку
  • Нельзя использовать await внутри lock
Monitor — низкоуровневый аналог lock.
mid

Monitor — класс для синхронизации доступа к ресурсам (низкоуровневый аналог lock).

Основные методы:

  • Monitor.Enter() — войти в блокировку
  • Monitor.Exit() — выйти из блокировки
  • Monitor.Wait() — освободить блокировку и ждать сигнала
  • Monitor.Pulse() — уведомить один ожидающий поток
  • Monitor.PulseAll() — уведомить все ожидающие потоки
  • Monitor.TryEnter() — попытаться войти с таймаутом

Пример Producer-Consumer:

private readonly object _locker = new object();
private Queue<int> _queue = new Queue<int>();
private bool _isCompleted = false;

// Producer
public void Produce(int item)
{
    lock (_locker)
    {
        _queue.Enqueue(item);
        Monitor.Pulse(_locker);  // Уведомляем Consumer
    }
}

// Consumer
public int Consume()
{
    lock (_locker)
    {
        while (_queue.Count == 0 && !_isCompleted)
        {
            Monitor.Wait(_locker);  // Ждём уведомления
        }
        return _queue.Dequeue();
    }
}

lock vs Monitor:

  • lock — синтаксический сахар для Monitor.Enter/Exit
  • Monitor даёт больше контроля (Wait, Pulse, TryEnter)
  • Monitor может вызывать OutOfMemoryException (редко)
Mutex, Semaphore, SemaphoreSlim — межпроцессная/внутренняя синхронизация.
mid

Mutex:

  • Межпроцессная синхронизация
  • Только один поток может владеть Mutex
  • Именованный Mutex доступен другим процессам
  • Использует системные ресурсы (дороже)
using (var mutex = new Mutex(false, "Global\\MyMutex"))
{
    if (mutex.WaitOne(TimeSpan.FromSeconds(5)))
    {
        try { /* Критическая секция */ }
        finally { mutex.ReleaseMutex(); }
    }
}

Semaphore / SemaphoreSlim:

  • Разрешает ограниченное количество потоков одновременно
  • Semaphore — межпроцессный (системный)
  • SemaphoreSlim — внутрипроцессный (быстрее)
// SemaphoreSlim (внутрипроцессный)
var semaphore = new SemaphoreSlim(3, 3);  // Не более 3 потоков

async Task ProcessAsync()
{
    await semaphore.WaitAsync();
    try { /* Критическая секция */ }
    finally { semaphore.Release(); }
}

Выбор инструмента:

  • lock: для простых внутрипроцессных сценариев
  • Mutex: для синхронизации между процессами
  • SemaphoreSlim: для ограничения количества потоков
  • Semaphore: для межпроцессного ограничения
  • Monitor: для тонкого контроля (Wait/Pulse)
Deadlock — причины, как избежать?
обяз

Deadlock (взаимная блокировка) — два или более потоков ожидают друг друга.

Условия Deadlock (Coffman):

  1. Взаимное исключение — ресурсы нельзя разделить
  2. Удержание и ожидание — поток удерживает ресурс и ждёт другой
  3. Отсутствие вытеснения — ресурсы нельзя отобрать
  4. Циклическое ожидание — цепочка ожиданий образует цикл

Пример Deadlock:

// Поток 1
lock (resource1)
{
    Thread.Sleep(100);
    lock (resource2) { /* ... */ }
}

// Поток 2
lock (resource2)
{
    Thread.Sleep(100);
    lock (resource1) { /* ... */ }
}

Как избежать:

1. Фиксированный порядок блокировок

// Всегда блокируем в одном порядке
int hash1 = resource1.GetHashCode();
int hash2 = resource2.GetHashCode();

if (hash1 < hash2)
{
    lock (resource1) lock (resource2) { /* ... */ }
}
else
{
    lock (resource2) lock (resource1) { /* ... */ }
}

2. Использовать таймауты

if (Monitor.TryEnter(resource1, TimeSpan.FromSeconds(1)))
{
    try
    {
        if (Monitor.TryEnter(resource2, TimeSpan.FromSeconds(1)))
        {
            try { /* ... */ }
            finally { Monitor.Exit(resource2); }
        }
    }
    finally { Monitor.Exit(resource1); }
}

3. Использовать асинхронные блокировки

// SemaphoreSlim с async/await
await semaphore.WaitAsync();
try { /* ... */ }
finally { semaphore.Release(); }

4. Избегать блокировок в async методах

  • Никогда не используйте lock внутри async
  • Используйте SemaphoreSlim.WaitAsync()
  • Используйте AsyncLock из библиотек
Race Condition — что это, как избежать?
обяз

Race Condition (состояние гонки) — когда результат операции зависит от порядка выполнения потоков.

Пример Race Condition:

// ❌ Код с гонкой
private int _counter = 0;

public void Increment()
{
    _counter++;  // Не атомарно!
    // Читает _counter → инкрементирует → записывает
}

// Два потока одновременно:
// Поток 1: читает 0 → инкремент до 1 → записывает 1
// Поток 2: читает 0 → инкремент до 1 → записывает 1
// Результат: 1 (потеряли одно обновление)

Как избежать:

1. Использовать атомарные операции

private int _counter = 0;
public void Increment()
{
    Interlocked.Increment(ref _counter);  // Атомарно!
}

2. Использовать блокировки

private readonly object _locker = new object();
private int _counter = 0;

public void Increment()
{
    lock (_locker) { _counter++; }
}

3. Использовать потокобезопасные коллекции

var dict = new ConcurrentDictionary<string, int>();
dict.AddOrUpdate("key", 1, (k, v) => v + 1);  // Атомарно!

4. Использовать неизменяемые структуры

// Неизменяемый объект — безопасен
public record Person(string Name, int Age);
var p1 = new Person("Alice", 30);
var p2 = p1 with { Age = 31 };  // Новая копия

Обнаружение Race Condition:

  • Сложно воспроизвести
  • Используйте Data Race Detector (ThreadSanitizer)
  • Тестируйте с высоким параллелизмом
Interlocked — атомарные операции.
mid

Interlocked — класс для атомарных операций без блокировок.

Основные методы:

  • Increment(ref int) — атомарное увеличение
  • Decrement(ref int) — атомарное уменьшение
  • Add(ref int, int) — атомарное добавление
  • CompareExchange(ref int, int, int) — CAS (Compare and Swap)
  • Exchange(ref int, int) — атомарная замена
  • Read(ref long) — атомарное чтение (для 64-битных)

Примеры:

private int _counter = 0;
private long _longValue = 0;

public void Increment()
{
    // Атомарное увеличение
    int newValue = Interlocked.Increment(ref _counter);
}

public bool TryUpdate(int oldValue, int newValue)
{
    // CAS (Compare and Swap)
    int original = Interlocked.CompareExchange(ref _counter, newValue, oldValue);
    return original == oldValue;
}

public long GetLongValue()
{
    // Атомарное чтение для 64-битных типов
    return Interlocked.Read(ref _longValue);
}

Interlocked vs lock:

Характеристика Interlocked lock
Производительность Очень быстрый Медленнее
Атомарность Одна операция Блок кода
Deadlock Нет Возможен

Асинхронность vs Многопоточность vs Параллелизм — разница.
обяз

Асинхронность (Asynchronous):

  • Не блокирует поток во время ожидания
  • Использует один поток для обработки нескольких задач
  • Освобождает поток для других операций
  • Идеально для IO-bound операций (диск, сеть, БД)
  • Реализуется через async/await

Многопоточность (Multithreading):

  • Использует несколько потоков одновременно
  • Каждый поток — отдельный поток ОС
  • Потоки могут выполняться параллельно на разных ядрах
  • Идеально для CPU-bound операций (вычисления)
  • Требует синхронизации (lock, Monitor)

Параллелизм (Parallelism):

  • Частный случай многопоточности
  • Выполнение задач одновременно на разных ядрах
  • Фокус на производительности
  • Реализуется через Parallel.For, PLINQ

Сравнение:

Характеристика Асинхронность Многопоточность Параллелизм
Цель Не блокировать поток Использовать несколько потоков Ускорение на нескольких ядрах
Использование IO-bound CPU-bound + IO CPU-bound
Потоки Один или несколько Несколько Несколько
Синхронизация Не требуется Требуется Требуется
Пример await DownloadAsync() new Thread(() => Work()) Parallel.For(0, n, i => Work(i))

Примеры в коде:

// Асинхронность (IO-bound)
async Task<string> GetDataAsync()
{
    var response = await httpClient.GetStringAsync("https://api.com");
    return response;
}

// Многопоточность (CPU-bound)
void ProcessData()
{
    var thread = new Thread(() => HeavyComputation());
    thread.Start();
}

// Параллелизм (CPU-bound)
void ProcessDataParallel()
{
    Parallel.For(0, 1000, i => HeavyComputation(i));
}
CPU-bound vs IO-bound задачи — как выбирать подход.
обяз

CPU-bound задачи (привязанные к процессору):

  • Требуют вычислений (циклы, расчёты, алгоритмы)
  • Используют процессор на 100%
  • Подход: Task.Run() или Parallel
  • Количество задач = количество ядер

IO-bound задачи (привязанные к вводу-выводу):

  • Ожидают внешние ресурсы (диск, сеть, БД)
  • Процессор простаивает большую часть времени
  • Подход: async/await
  • Много задач может быть выполнено на одном потоке

Примеры:

// CPU-bound — используем Task.Run
async Task<int> ProcessDataAsync()
{
    return await Task.Run(() =>
    {
        // Долгие вычисления
        int result = 0;
        for (int i = 0; i < 1000000; i++)
            result += i * i;
        return result;
    });
}

// IO-bound — используем async/await
async Task<string> DownloadDataAsync(string url)
{
    using var client = new HttpClient();
    return await client.GetStringAsync(url);  // Не блокирует поток
}

Критерии выбора:

  • IO-bound: используйте async/await
  • CPU-bound: используйте Task.Run, Parallel, PLINQ
  • Смешанные: комбинируйте подходы

Рекомендации Microsoft:

  • Для CPU-bound задач используйте Parallel.For или PLINQ
  • Для IO-bound задач используйте async/await
  • В UI приложениях всегда используйте async/await (не блокируйте UI поток)
