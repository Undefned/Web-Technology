Модель OSI — основные уровни (L4, L7).
mid

OSI (Open Systems Interconnection) — 7 уровней сетевой модели.

1. Физический (Physical) — биты, кабели, разъёмы

2. Канальный (Data Link) — Ethernet, MAC-адреса

3. Сетевой (Network) — IP, маршрутизация

4. Транспортный (Transport) — TCP, UDP (L4)

5. Сеансовый (Session) — управление сессиями

6. Представления (Presentation) — шифрование, кодирование

7. Прикладной (Application) — HTTP, FTP, SMTP (L7)

Для разработчика важны:

  • L4 (Transport): TCP/UDP — порты, надёжность
  • L7 (Application): HTTP/HTTPS — API, веб

Когда использовать:

  • TCP: данные важны, порядок важен (веб, файлы, БД)
  • UDP: скорость важна, потеря допустима (голос, видео, игры)
TCP Handshake (3-way handshake) — как устанавливается соединение.
mid

3-way handshake — установка TCP-соединения.

Шаги:

  1. SYN (Client → Server): клиент отправляет SYN (seq=x)
  2. SYN-ACK (Server → Client): сервер отвечает SYN-ACK (seq=y, ack=x+1)
  3. ACK (Client → Server): клиент отправляет ACK (seq=x+1, ack=y+1)

Схема:

Client                     Server
  |                          |
  |------ SYN (seq=x) ----->|
  |                          |
  |<-- SYN-ACK (seq=y, ack=x+1)|
  |                          |
  |------ ACK (seq=x+1, ack=y+1) ->|
  |                          |
  |======= Соединение установлено =======|

Завершение соединения (4-way handshake):

  1. FIN (Client → Server): клиент закрывает соединение
  2. ACK (Server → Client): сервер подтверждает
  3. FIN (Server → Client): сервер закрывает
  4. ACK (Client → Server): клиент подтверждает
HTTP vs HTTPS — разница, TLS/SSL.
обяз

HTTP (HyperText Transfer Protocol):

  • Передача данных в открытом виде
  • Порт 80
  • Нет шифрования
  • Уязвим для перехвата

HTTPS (HTTP Secure):

  • HTTP + TLS/SSL шифрование
  • Порт 443
  • Защита данных
  • Требуется сертификат

TLS (Transport Layer Security):

  • Протокол шифрования
  • Заменяет SSL (устаревший)
  • Асимметричное шифрование для обмена ключами
  • Симметричное шифрование для данных

Процесс установки HTTPS:

  1. Клиент подключается к серверу
  2. Сервер отправляет сертификат (публичный ключ)
  3. Клиент проверяет сертификат (CA)
  4. Клиент генерирует session key
  5. Клиент шифрует ключ публичным ключом сервера
  6. Сервер расшифровывает ключ приватным ключом
  7. Дальше используется симметричное шифрование
SQL-инъекции — как защититься (параметризованные запросы).
обяз

SQL-инъекция — внедрение SQL-кода в запрос через пользовательский ввод.

Пример уязвимости:

// ❌ Уязвимый код
string query = $"SELECT * FROM Users WHERE Email = '{email}' AND Password = '{password}'";
var cmd = new SqlCommand(query, connection);

// Злоумышленник вводит:
// email = admin' --
// password = anything
// SQL: SELECT * FROM Users WHERE Email = 'admin' --' AND Password = 'anything'
// Получает доступ без пароля

Защита:

1. Параметризованные запросы (основной способ)

// ✅ Безопасный код
string query = "SELECT * FROM Users WHERE Email = @Email AND Password = @Password";
var cmd = new SqlCommand(query, connection);
cmd.Parameters.AddWithValue("@Email", email);
cmd.Parameters.AddWithValue("@Password", password);

2. Использование ORM (EF Core, Dapper)

// EF Core — автоматическая защита
var user = await context.Users
    .FirstOrDefaultAsync(u => u.Email == email && u.Password == password);

// Dapper — параметры
var user = await connection.QueryFirstOrDefaultAsync<User>(
    "SELECT * FROM Users WHERE Email = @Email",
    new { Email = email });

3. Ограничение прав БД

  • Минимальные права для приложения
  • Только SELECT, INSERT, UPDATE в нужных таблицах
  • Запрет DDL (CREATE, DROP, ALTER)

4. Валидация ввода

  • Проверка типов (int, email, guid)
  • Экранирование специальных символов
  • Белые списки (white-lists)
CORS — зачем нужен, как настроить в ASP.NET Core.
обяз

CORS (Cross-Origin Resource Sharing) — политика безопасности браузера.

Зачем нужен:

  • Браузер блокирует запросы к другому домену
  • Защита от CSRF-атак
  • API должно разрешать кросс-доменные запросы

Настройка в ASP.NET Core:

// Program.cs
var builder = WebApplication.CreateBuilder(args);

// Добавление CORS
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowAll", policy =>
    {
        policy.AllowAnyOrigin()
              .AllowAnyMethod()
              .AllowAnyHeader();
    });
    
    options.AddPolicy("AllowSpecific", policy =>
    {
        policy.WithOrigins("https://example.com", "https://localhost:3000")
              .WithMethods("GET", "POST", "PUT")
              .WithHeaders("Authorization", "Content-Type")
              .AllowCredentials();
    });
});

var app = builder.Build();

// Использование CORS
app.UseCors("AllowAll");
// или
app.UseCors("AllowSpecific");

app.MapControllers();

// Контроллер с CORS
[EnableCors("AllowSpecific")]
[ApiController]
[Route("api/users")]
public class UsersController : ControllerBase
{
    // ...
}

// Отключение CORS для метода
[DisableCors]
[HttpGet("test")]
public IActionResult Test() { }
JWT — структура, подпись, срок жизни.
обяз

JWT (JSON Web Token) — структура:

header.payload.signature

Header (Заголовок)

{
  "alg": "HS256",  // Алгоритм подписи
  "typ": "JWT"     // Тип токена
}

Payload (Данные)

{
  "sub": "1234567890",   // Subject (ID пользователя)
  "name": "John Doe",
  "iat": 1516239022,     // Issued At (время создания)
  "exp": 1516242622,     // Expiration (время истечения)
  "aud": "myapp",        // Audience (кому предназначен)
  "iss": "auth-server",  // Issuer (кто создал)
  "role": "admin"        // Custom claims
}

Signature (Подпись)

  • Создаётся из header + payload + секретный ключ
  • Обеспечивает целостность (нельзя подделать)
  • Проверяется на сервере
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

Срок жизни токена:

  • Access Token: короткий (15-60 минут)
  • Refresh Token: долгий (дни, месяцы)
  • JWT включает exp: сервер проверяет срок
  • Нельзя отозвать до истечения (если нет чёрного списка)
OWASP Top 10 — базовое понимание.
mid

OWASP Top 10 — список наиболее критичных уязвимостей веб-приложений.

Топ 10 (2021):

1. Broken Access Control — нарушение контроля доступа

  • Пользователь может получить доступ к чужим данным
  • Решение: проверка прав на сервере

2. Cryptographic Failures — ошибки шифрования

  • Хранение паролей в открытом виде
  • Решение: HTTPS, bcrypt, шифрование

3. Injection — SQL, NoSQL, OS инъекции

  • Внедрение вредоносного кода
  • Решение: параметризованные запросы, валидация

4. Insecure Design — небезопасный дизайн

  • Архитектурные ошибки
  • Решение: Threat Modeling, безопасный дизайн

5. Security Misconfiguration — небезопасная конфигурация

  • Дефолтные пароли, открытые порты
  • Решение: безопасная конфигурация

6. Vulnerable and Outdated Components — уязвимые компоненты

  • Старые версии библиотек
  • Решение: обновление зависимостей

7. Identification and Authentication Failures — ошибки аутентификации

  • Слабые пароли, отсутствие 2FA
  • Решение: сильные пароли, 2FA, OAuth

8. Software and Data Integrity Failures — ошибки целостности

  • Подделка данных
  • Решение: подписи, контрольные суммы

9. Security Logging and Monitoring Failures — ошибки логирования

  • Отсутствие логов атак
  • Решение: логирование, мониторинг

10. Server-Side Request Forgery — подделка запросов

  • SSRF — внутренние запросы
  • Решение: валидация URL
