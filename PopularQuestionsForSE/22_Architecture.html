🏗️ 22. Архитектурные вопросы (System Design) Mid+

Как спроектировать систему? (High-Level Design).
обяз

Этапы проектирования:

1. Сбор требований

  • Функциональные: что система делает
  • Нефункциональные: нагрузка (RPS), надёжность (SLA), задержки (latency)

2. Оценка нагрузки

  • DAU (Daily Active Users)
  • RPS (Requests Per Second)
  • Хранилище (Storage)
  • Сеть (Bandwidth)

3. Выбор архитектуры

  • Монолит или микросервисы
  • SQL или NoSQL
  • Синхронный или асинхронный обмен

4. Проектирование данных

  • Схема БД
  • Кэширование
  • Индексы

5. Масштабирование

  • Горизонтальное (более экземпляров)
  • Вертикальное (более мощное железо)
  • Sharding (разделение данных)
  • Replication (репликация)

6. Надёжность

  • Отказоустойчивость
  • Резервирование
  • Backup/Restore

Пример для системы заказов:

API Gateway (Ocelot)
    ├── Auth Service (JWT)
    ├── Order Service (PostgreSQL)
    │   ├── Order → OrderItems (1:N)
    │   └── Redis (кэш заказов)
    ├── Payment Service (RabbitMQ)
    │   └── Payment → Status (pending → completed)
    ├── Inventory Service (Event Sourcing)
    │   └── Reserve → Release
    └── Notification Service (Email, SMS)
Как масштабировать БД? (Sharding, Replication).
mid

1. Replication (репликация)

  • Копирование данных на несколько серверов
  • Master (запись) → Slaves (чтение)
  • Масштабирование чтения
  • Отказоустойчивость
    Master (Write)
      ├── Slave 1 (Read)
      ├── Slave 2 (Read)
      └── Slave 3 (Read)

2. Sharding (шардирование)

  • Разделение данных по разным серверам
  • По ключу: UserId, City, Range
  • Масштабирование записи
  • Сложный запросы (JOIN'ы между шардами)
    Shard 1 (User 1-1000)
    Shard 2 (User 1001-2000)
    Shard 3 (User 2001-3000)

3. CQRS + Event Sourcing

  • Отдельные БД для чтения и записи
  • Read DB — оптимизирована для запросов
  • Write DB — транзакционная

4. Кэширование

  • Redis / Memcached
  • Уменьшает нагрузку на БД
  • Cache-Aside, Write-Through, Write-Behind
Как обработать 1 млн запросов в секунду?

Стратегии для высокой нагрузки:

1. Балансировка нагрузки (Load Balancing)

  • Nginx, HAProxy, AWS ELB
  • Распределение запросов между инстансами

2. Горизонтальное масштабирование

  • Больше экземпляров приложения
  • Автоматическое масштабирование (Kubernetes HPA)

3. Кэширование

  • CDN (для статики)
  • Redis / Memcached (для динамики)
  • Cache-Aside, Write-Through

4. Асинхронная обработка

  • Очереди (RabbitMQ, Kafka)
  • Фоновые задачи (BackgroundService)
  • Не блокировать основной поток

5. Оптимизация БД

  • Индексы (правильные)
  • Шардирование (Sharding)
  • Read Replicas
  • NoSQL (для неструктурированных данных)

6. Rate Limiting

  • Защита от DDoS
  • Ограничение клиентов

7. Микросервисы

  • Каждый сервис масштабируется отдельно
  • Слабосвязанные системы

8. gRPC вместо REST

  • В 10 раз быстрее
  • Меньше задержек
  • HTTP/2 стриминг
Как обеспечить отказоустойчивость? (Resilience).
mid

Стратегии отказоустойчивости:

1. Retry (повторы)

  • Повтор при временных ошибках
  • Exponential backoff (задержка растёт)
  • jitter (случайная задержка)

2. Circuit Breaker (предохранитель)

  • Быстрый отказ при проблемах
  • Автоматическое восстановление

3. Timeout (тайм-аут)

  • Ограничение времени ожидания
  • Предотвращение блокировок

4. Bulkhead (изоляция)

  • Ограничение параллельных запросов
  • Изоляция ошибок

5. Health Checks

  • Проверка работоспособности
  • Kubernetes liveness/readiness

6. Graceful Shutdown

  • Корректное завершение
  • Завершение текущих запросов

7. Monitoring & Alerting

  • Отслеживание ошибок
  • Оповещения

Пример с Polly:

var policy = Policy
    .Handle<HttpRequestException>()
    .Or<TimeoutException>()
    .WaitAndRetryAsync(3, retryAttempt => 
        TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)) + TimeSpan.FromMilliseconds(Random.Shared.Next(0, 1000)))
    .WrapAsync(Policy
        .TimeoutAsync(TimeSpan.FromSeconds(5)))
    .WrapAsync(Policy
        .CircuitBreakerAsync(3, TimeSpan.FromSeconds(30)));
Как реализовать Distributed Lock?
mid

Distributed Lock — блокировка между разными экземплярами.

Способы реализации:

1. Redis (RedLock)

// Использование RedLock.net
var resource = "my-lock-key";
var expiry = TimeSpan.FromSeconds(30);

using (var lock = await _distributedLock.CreateLockAsync(resource, expiry))
{
    if (lock.IsAcquired)
    {
        // Критическая секция
    }
}

2. Database (PostgreSQL advisory locks)

// PostgreSQL
SELECT pg_advisory_lock(123456);
-- Критическая секция
SELECT pg_advisory_unlock(123456);

3. ZooKeeper / Etcd

  • Распределённые системы
  • Атомарные операции

4. AWS DynamoDB (Conditional Update)

// Псевдокод
var result = await db.UpdateItemAsync(new UpdateItemRequest
{
    Key = { { "lock_key", new AttributeValue("my-lock") } },
    UpdateExpression = "SET #ttl = :ttl",
    ConditionExpression = "attribute_not_exists(#ttl) OR #ttl < :now",
    ExpressionAttributeNames = new Dictionary<string, string> { { "#ttl", "ttl" } },
    ExpressionAttributeValues = new Dictionary<string, AttributeValue>
    {
        { ":ttl", new AttributeValue { N = (DateTime.UtcNow.AddSeconds(30)).ToString() } },
        { ":now", new AttributeValue { N = DateTime.UtcNow.ToString() } }
    }
});

Важно:

  • Всегда устанавливать TTL (время жизни)
  • Освобождать блокировку в finally
  • Использовать unique идентификатор (owner)
Как гарантировать доставку сообщений? (At-least-once, Exactly-once).
mid

Семантика доставки:

At-most-once (не более одного раза)

  • Сообщение может быть потеряно
  • Быстро, без подтверждений
  • Пример: логи, метрики

At-least-once (не менее одного раза)

  • Сообщение доставляется как минимум один раз
  • Могут быть дубликаты
  • Требует идемпотентности получателя
  • Пример: заказы, платежи

Exactly-once (ровно один раз)

  • Идеальный случай
  • Сложно реализовать
  • Пример: финансовые операции

Как реализовать Exactly-once:

// 1. Idempotency Key (уникальный ID запроса)
public async Task ProcessMessageAsync(Message message)
{
    if (await _cache.ExistsAsync(message.IdempotencyKey))
        return;  // Уже обработано
    
    // Обработка сообщения
    await ProcessData(message.Data);
    
    // Сохранить ключ (с TTL)
    await _cache.SetAsync(message.IdempotencyKey, "done", TimeSpan.FromHours(24));
}

// 2. Транзакционная обработка (БД + брокер)
using var transaction = await _dbContext.Database.BeginTransactionAsync();
try
{
    await _dbContext.Orders.AddAsync(order);
    await _dbContext.SaveChangesAsync();
    
    // Только после успешного сохранения в БД
    await _messageBus.PublishAsync(new OrderCreatedEvent(order.Id));
    
    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}
