Реляционные vs Нереляционные БД — плюсы/минусы.
обяз

Реляционные БД (SQL):

  • Структурированные данные в таблицах
  • Связи между таблицами (Foreign Key)
  • Язык запросов: SQL
  • ACID транзакции
  • Строгая схема (миграции)
  • Примеры: PostgreSQL, MySQL, SQL Server, Oracle

Плюсы:

  • Целостность данных (Foreign Key, Constraints)
  • Сложные запросы (JOIN, GROUP BY)
  • Транзакции (ACID)
  • Стандартизированный язык (SQL)

Минусы:

  • Жёсткая схема
  • Масштабирование (сложное горизонтальное)
  • Производительность при больших данных

Нереляционные БД (NoSQL):

  • Документы, ключ-значение, графы, колонки
  • Гибкая схема (schemaless)
  • Язык запросов: свой (MongoDB Query, etc.)
  • BASE транзакции (Eventually Consistent)
  • Примеры: MongoDB, Redis, Cassandra, Elasticsearch

Плюсы:

  • Гибкая схема (легко менять)
  • Горизонтальное масштабирование
  • Высокая производительность
  • Разные модели данных (документы, графы)

Минусы:

  • Нет жёстких связей
  • Меньше гарантий целостности
  • Сложные запросы (JOIN) труднее
  • Разные языки запросов

Когда использовать:

  • SQL: финансовые данные, транзакции, строгие связи
  • NoSQL: большие данные, высокая нагрузка, гибкая схема
Первичный ключ (PK) vs Внешний ключ (FK).
обяз

Первичный ключ (Primary Key):

  • Уникально идентифицирует запись в таблице
  • Не может быть NULL
  • Только один на таблицу
  • Автоматически индексируется
CREATE TABLE Users (
    Id INT PRIMARY KEY IDENTITY(1,1),
    Name NVARCHAR(100)
);

Внешний ключ (Foreign Key):

  • Ссылается на первичный ключ другой таблицы
  • Обеспечивает целостность ссылок
  • Может быть NULL
  • Может быть несколько на таблицу
CREATE TABLE Orders (
    Id INT PRIMARY KEY IDENTITY(1,1),
    UserId INT NOT NULL,
    Total DECIMAL(18,2),
    FOREIGN KEY (UserId) REFERENCES Users(Id)
);

Каскадные операции:

FOREIGN KEY (UserId) REFERENCES Users(Id)
    ON DELETE CASCADE  -- При удалении пользователя удалить заказы
    ON UPDATE CASCADE  -- При изменении Id обновить UserId
JOIN: INNER, LEFT, RIGHT, FULL, CROSS — разница.
обяз

INNER JOIN: только совпадающие записи в обеих таблицах.

SELECT Users.Name, Orders.Total
FROM Users
INNER JOIN Orders ON Users.Id = Orders.UserId;

LEFT JOIN: все записи из левой таблицы, совпадающие из правой (NULL если нет).

SELECT Users.Name, Orders.Total
FROM Users
LEFT JOIN Orders ON Users.Id = Orders.UserId;
-- Все пользователи, даже без заказов

RIGHT JOIN: все записи из правой таблицы, совпадающие из левой.

SELECT Users.Name, Orders.Total
FROM Users
RIGHT JOIN Orders ON Users.Id = Orders.UserId;
-- Все заказы, даже без пользователей

FULL JOIN: все записи из обеих таблиц.

SELECT Users.Name, Orders.Total
FROM Users
FULL JOIN Orders ON Users.Id = Orders.UserId;

CROSS JOIN: декартово произведение (все комбинации).

SELECT Users.Name, Products.Name
FROM Users
CROSS JOIN Products;
-- Каждый пользователь с каждым товаром

Визуализация:

  • INNER: только пересечение
  • LEFT: вся левая + пересечение
  • RIGHT: вся правая + пересечение
  • FULL: все записи из обоих
  • CROSS: все комбинации
Агрегатные функции: COUNT, SUM, AVG, MAX, MIN.
обяз

COUNT — количество записей

SELECT COUNT(*) FROM Users;  -- Все записи
SELECT COUNT(DISTINCT City) FROM Users;  -- Уникальные города
SELECT COUNT(Email) FROM Users;  -- Не NULL

SUM — сумма

SELECT SUM(Total) FROM Orders;
SELECT SUM(DISTINCT Total) FROM Orders;  -- Уникальные суммы

AVG — среднее

SELECT AVG(Total) FROM Orders;
SELECT AVG(DISTINCT Total) FROM Orders;

MAX — максимум

SELECT MAX(Total) FROM Orders;
SELECT MAX(Date) FROM Orders;  -- Самая поздняя дата

MIN — минимум

SELECT MIN(Total) FROM Orders;

С GROUP BY:

SELECT UserId, COUNT(*) as OrderCount, SUM(Total) as TotalSum
FROM Orders
GROUP BY UserId
HAVING COUNT(*) > 5;  -- Только с > 5 заказов
GROUP BY и HAVING — фильтрация групп.
обяз

GROUP BY — группировка записей по одному или нескольким столбцам.

-- Количество заказов по пользователям
SELECT UserId, COUNT(*) as OrderCount
FROM Orders
GROUP BY UserId;

-- Средняя сумма заказа по пользователям
SELECT UserId, AVG(Total) as AvgOrder
FROM Orders
GROUP BY UserId;

HAVING — фильтрация сгруппированных результатов (аналог WHERE для групп).

-- Пользователи с > 5 заказами
SELECT UserId, COUNT(*) as OrderCount
FROM Orders
GROUP BY UserId
HAVING COUNT(*) > 5;

-- Пользователи со средней суммой > 1000
SELECT UserId, AVG(Total) as AvgOrder
FROM Orders
GROUP BY UserId
HAVING AVG(Total) > 1000;

WHERE vs HAVING:

  • WHERE: фильтрует строки до группировки
  • HAVING: фильтрует группы после группировки
-- WHERE фильтрует до группировки
SELECT UserId, COUNT(*) as OrderCount
FROM Orders
WHERE Total > 100  -- Только заказы > 100
GROUP BY UserId
HAVING COUNT(*) > 5;  -- Только пользователи с > 5 такими заказами
Индексы — B-Tree, структура, когда использовать.
обяз

Индекс — структура данных для быстрого поиска записей.

Структура B-Tree:

  • Сбалансированное дерево
  • Корень, внутренние узлы, листья
  • Сложность поиска: O(log n)
  • Поддерживает поиск, вставку, удаление

Когда использовать индексы:

  • ✅ Часто в WHERE (фильтрация)
  • ✅ Часто в JOIN (связи)
  • ✅ Часто в ORDER BY (сортировка)
  • ✅ Часто в GROUP BY (группировка)
  • ❌ Маленькие таблицы (до 1000 записей)
  • ❌ Редко используемые столбцы
  • ❌ Столбцы, которые часто обновляются

Когда НЕ использовать:

  • Маленькие таблицы
  • Столбцы, которые редко используются в WHERE
  • Столбцы с низкой селективностью (например, boolean)
  • Таблицы с частыми вставками/обновлениями (индекс замедляет)

Создание индекса:

CREATE INDEX IX_Users_Email ON Users(Email);

-- Составной индекс
CREATE INDEX IX_Orders_UserId_Date ON Orders(UserId, OrderDate);

-- Уникальный индекс
CREATE UNIQUE INDEX UX_Users_Email ON Users(Email);
Кластеризованный vs Некластеризованный индекс — разница.
обяз

Кластеризованный индекс (Clustered Index):

  • Определяет физический порядок данных в таблице
  • Только один на таблицу
  • По умолчанию = Primary Key
  • Данные хранятся в листьях дерева
  • Поиск — O(log n)

Некластеризованный индекс (Non-Clustered Index):

  • Не влияет на физический порядок данных
  • Может быть много на таблицу
  • Листья содержат ссылки на данные
  • Поиск — O(log n) + дополнительный поиск по ссылке
  • Медленнее, чем кластеризованный

Сравнение:

Характеристика Кластеризованный Некластеризованный
Количество Только 1 Много
Порядок данных Физический Не влияет
Листья Данные Ссылки на данные
Скорость поиска Быстрее Медленнее
По умолчанию Primary Key —

Пример:

-- Кластеризованный (по умолчанию на PK)
CREATE TABLE Users (
    Id INT PRIMARY KEY,  -- Clustered Index
    Name NVARCHAR(100)
);

-- Некластеризованный
CREATE NONCLUSTERED INDEX IX_Users_Name ON Users(Name);
ACID — расшифровка, примеры.
обяз

ACID — свойства транзакций в реляционных БД.

A — Atomicity (Атомарность)

  • Транзакция выполняется полностью или не выполняется совсем
  • При ошибке — откат (Rollback)
  • Пример: перевод денег — списать и зачислить должны оба выполниться

C — Consistency (Согласованность)

  • Транзакция переводит БД из одного согласованного состояния в другое
  • Не нарушает ограничения (Foreign Key, Unique)
  • Пример: баланс не может стать отрицательным

I — Isolation (Изоляция)

  • Транзакции изолированы друг от друга
  • Промежуточные результаты не видны другим транзакциям
  • Уровни изоляции: Read Uncommitted, Read Committed и т.д.
  • Пример: две транзакции видят согласованное состояние

D — Durability (Устойчивость)

  • После фиксации (Commit) данные сохраняются навсегда
  • Перезагрузка системы не приводит к потере данных
  • Пример: подтверждённый перевод сохранится даже при сбое

Пример транзакции:

BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;

-- Если ошибка — ROLLBACK
COMMIT;  -- Только если всё успешно
Уровни изоляции транзакций: Read Uncommitted, Read Committed, Repeatable Read, Serializable, Snapshot.
обяз

Уровни изоляции определяют, как транзакции видят изменения друг друга.

Уровень Грязное чтение Неповторяющееся чтение Фантомное чтение Описание
Read Uncommitted ✅ Да ✅ Да ✅ Да Читает незафиксированные данные (грязное чтение)
Read Committed ❌ Нет ✅ Да ✅ Да Читает только зафиксированные данные
Repeatable Read ❌ Нет ❌ Нет ✅ Да Одинаковое чтение в рамках транзакции
Serializable ❌ Нет ❌ Нет ❌ Нет Полная изоляция (самый строгий)
Snapshot ❌ Нет ❌ Нет ❌ Нет Снимок данных на момент начала транзакции

Проблемы:

  • Грязное чтение: чтение незафиксированных данных
  • Неповторяющееся чтение: разное чтение при повторном запросе
  • Фантомное чтение: появление новых записей

Пример в SQL:

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN TRANSACTION;
SELECT * FROM Users WHERE Id = 1;  -- Видит только зафиксированные данные
COMMIT;
DELETE vs TRUNCATE — разница.
обяз
Характеристика DELETE TRUNCATE
Скорость Медленно (построчно) Быстро (вся таблица)
Логирование Построчное Минимальное
WHERE ✅ Можно ❌ Нельзя
Триггеры ✅ Вызываются ❌ Не вызываются
Сброс Identity ❌ Нет ✅ Да
Можно откатить ✅ Да ✅ Да
Использование Удаление части данных Очистка всей таблицы

Примеры:

-- DELETE — удаление части данных
DELETE FROM Users WHERE Active = 0;

-- DELETE с JOIN
DELETE FROM Orders
FROM Orders o
INNER JOIN Users u ON o.UserId = u.Id
WHERE u.Active = 0;

-- TRUNCATE — очистка всей таблицы
TRUNCATE TABLE Logs;

Когда использовать:

  • DELETE: удаление части данных, нужно WHERE
  • TRUNCATE: быстрая очистка таблицы, сброс Identity
Оконные функции: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD.
mid

Оконные функции — выполняют вычисления по группе строк без GROUP BY.

ROW_NUMBER — нумерация строк

SELECT 
    Name,
    Salary,
    ROW_NUMBER() OVER (ORDER BY Salary DESC) as Rank
FROM Employees;

RANK — с пропусками при связях

SELECT 
    Name,
    Salary,
    RANK() OVER (ORDER BY Salary DESC) as Rank
FROM Employees;
-- 1, 2, 2, 4 (если два одинаковых — пропуск)

DENSE_RANK — без пропусков

SELECT 
    Name,
    Salary,
    DENSE_RANK() OVER (ORDER BY Salary DESC) as Rank
FROM Employees;
-- 1, 2, 2, 3 (без пропусков)

LAG — предыдущее значение

SELECT 
    Date,
    Amount,
    LAG(Amount, 1) OVER (ORDER BY Date) as PrevAmount,
    Amount - LAG(Amount, 1) OVER (ORDER BY Date) as Diff
FROM Sales;

LEAD — следующее значение

SELECT 
    Date,
    Amount,
    LEAD(Amount, 1) OVER (ORDER BY Date) as NextAmount
FROM Sales;

С PARTITION BY (группировка):

-- Ранги в каждой группе (по отделам)
SELECT 
    Name,
    Department,
    Salary,
    ROW_NUMBER() OVER (PARTITION BY Department ORDER BY Salary DESC) as RankInDept
FROM Employees;
CTE (Common Table Expression) — WITH ... AS.
mid

CTE — временный именованный результат запроса.

Преимущества:

  • Улучшает читаемость
  • Позволяет рекурсивные запросы
  • Можно использовать несколько раз

Примеры:

-- Простой CTE
WITH UserOrders AS (
    SELECT UserId, COUNT(*) as OrderCount
    FROM Orders
    GROUP BY UserId
)
SELECT u.Name, uo.OrderCount
FROM Users u
INNER JOIN UserOrders uo ON u.Id = uo.UserId;

-- Рекурсивный CTE (иерархия)
WITH EmployeeHierarchy AS (
    -- Базовый случай (руководители)
    SELECT Id, Name, ManagerId, 0 as Level
    FROM Employees
    WHERE ManagerId IS NULL
    
    UNION ALL
    
    -- Рекурсивный случай (подчинённые)
    SELECT e.Id, e.Name, e.ManagerId, eh.Level + 1
    FROM Employees e
    INNER JOIN EmployeeHierarchy eh ON e.ManagerId = eh.Id
)
SELECT * FROM EmployeeHierarchy
ORDER BY Level, Name;

Множественные CTE:

WITH
ActiveUsers AS (
    SELECT * FROM Users WHERE Active = 1
),
UserOrders AS (
    SELECT au.Id, COUNT(o.Id) as OrderCount
    FROM ActiveUsers au
    LEFT JOIN Orders o ON au.Id = o.UserId
    GROUP BY au.Id
)
SELECT * FROM UserOrders;
План выполнения запроса (Execution Plan) — как читать.
mid

Execution Plan — стратегия выполнения SQL-запроса.

Как получить:

-- В SQL Server
SET SHOWPLAN_TEXT ON;  -- Текстовый план
SET SHOWPLAN_XML ON;   -- XML план

-- Через SSMS
-- Включить "Include Actual Execution Plan" (Ctrl+M)

-- В PostgreSQL
EXPLAIN ANALYZE SELECT * FROM Users WHERE Id = 1;

Основные операции (читаем справа налево, снизу вверх):

  • Table Scan: чтение всей таблицы (плохо для больших таблиц)
  • Clustered Index Scan: чтение кластеризованного индекса
  • Index Seek: поиск по индексу (быстро)
  • Key Lookup: поиск по ключу (медленно)
  • Join: соединение таблиц
  • Hash Match: соединение через хэш-таблицу
  • Nested Loops: соединение через вложенные циклы

На что обращать внимание:

  • Cost (стоимость): процент от общего времени
  • Rows (строки): ожидаемое vs фактическое количество
  • Warnings (предупреждения): отсутствующие индексы
  • Index Scans: вместо Seeks (медленно)
  • Key Lookups: дополнительные запросы
Оптимизация запросов: WHERE по индексированным полям, избегать SELECT *.
обяз

Советы по оптимизации:

1. Используйте индексы в WHERE

-- ❌ Плохо (без индекса на Email)
SELECT * FROM Users WHERE Email = 'test@example.com';

-- ✅ Хорошо (индекс на Email)
CREATE INDEX IX_Users_Email ON Users(Email);

2. Избегайте SELECT * (указывайте только нужные поля)

-- ❌ Плохо — все поля
SELECT * FROM Users WHERE Id = 1;

-- ✅ Хорошо — только нужные
SELECT Id, Name, Email FROM Users WHERE Id = 1;

3. Используйте индексы для сортировки

-- Индекс на OrderDate ускорит сортировку
SELECT * FROM Orders
ORDER BY OrderDate DESC;

4. Избегайте функций в WHERE

-- ❌ Плохо (индекс не используется)
SELECT * FROM Users WHERE YEAR(CreatedDate) = 2023;

-- ✅ Хорошо (используется индекс)
SELECT * FROM Users 
WHERE CreatedDate >= '2023-01-01' AND CreatedDate < '2024-01-01';

5. Используйте EXISTS вместо COUNT для проверки наличия

-- ❌ Плохо
IF (SELECT COUNT(*) FROM Users WHERE Active = 1) > 0

-- ✅ Хорошо
IF EXISTS (SELECT 1 FROM Users WHERE Active = 1)

6. Используйте TOP/LIMIT для больших результатов

-- SQL Server
SELECT TOP 100 * FROM Users ORDER BY CreatedDate;

-- PostgreSQL
SELECT * FROM Users ORDER BY CreatedDate LIMIT 100;
