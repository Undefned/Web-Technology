🧪 8. Исключения. Тестирование база

try / catch / finally — порядок выполнения.
обяз

Порядок выполнения:

  1. Выполняется код в try
  2. Если ошибка — ищем подходящий catch
  3. finally выполняется всегда (даже при исключении)
  4. Если catch есть — обработка продолжается
  5. Если catch нет — исключение передаётся выше

Пример:

try
{
    Console.WriteLine("1. try");
    int x = int.Parse("не число");  // Исключение
    Console.WriteLine("2. после ошибки (не выполнится)");
}
catch (FormatException ex)
{
    Console.WriteLine("3. catch FormatException");
}
catch (Exception ex)
{
    Console.WriteLine("4. catch Exception");
}
finally
{
    Console.WriteLine("5. finally — всегда");
}

// Вывод:
// 1. try
// 3. catch FormatException
// 5. finally — всегда

Важно:

  • catch без параметров перехватывает все исключения
  • catch (Exception ex) — перехватывает все
  • finally выполняется даже при return в try
  • Если исключение в finally — перехватывается внешним блоком
Когда finally НЕ выполняется?
mid

finally НЕ выполняется в следующих случаях:

  • Environment.FailFast() — немедленное завершение процесса
    • Environment.FailFast("Критическая ошибка");  // finally не выполнится
  • StackOverflowException — не может быть перехвачен
    • void Infinite() { Infinite(); }  // StackOverflow → finally не выполнится
  • OutOfMemoryException — может не выполнить finally
    • var huge = new byte[long.MaxValue];  // OutOfMemory
  • Аварийное завершение процесса (Task Manager, kill)
  • Выключение питания / сбой системы

Важно:

  • finally выполняется при обычном выходе и исключениях
  • Не полагайтесь на finally в критических операциях
  • Используйте using для освобождения ресурсов (это тоже finally)
throw vs throw ex — разница (потеря stack trace).
обяз

throw — сохраняет стек вызовов

  • Перебрасывает исходное исключение
  • Сохраняет полный стек вызовов
  • Лучше для отладки
try
{
    DoWork();
}
catch (Exception ex)
{
    throw;  // Сохраняет стек (ex не теряется)
}

throw ex — теряет стек вызовов

  • Создаёт новое исключение
  • Теряет исходный стек вызовов
  • Усложняет отладку
try
{
    DoWork();
}
catch (Exception ex)
{
    throw ex;  // ❌ Потеря стека
}

throw new Exception("message", ex) — сохраняет InnerException

try
{
    DoWork();
}
catch (Exception ex)
{
    // Сохраняет исходное исключение как InnerException
    throw new CustomException("Ошибка", ex);
}

Сравнение:

// throw — стек полностью сохраняется
try { throw new Exception("Test"); }
catch (Exception ex) { throw; }

// throw ex — стек обрезается
try { throw new Exception("Test"); }
catch (Exception ex) { throw ex; }  // Исходный стек потерян
Когда создавать своё исключение.
mid

Создавайте своё исключение когда:

  • Встроенных исключений недостаточно для описания ошибки
  • Нужно передать дополнительную информацию об ошибке
  • Ошибка относится к бизнес-логике приложения
  • Нужно отличить ошибку приложения от системной
  • Библиотека / API для других разработчиков

Пример:

// Создание собственного исключения
public class InsufficientFundsException : Exception
{
    public decimal Balance { get; }
    public decimal RequestedAmount { get; }
    
    public InsufficientFundsException(decimal balance, decimal requested)
        : base($"Недостаточно средств: баланс {balance}, запрошено {requested}")
    {
        Balance = balance;
        RequestedAmount = requested;
    }
    
    public InsufficientFundsException(decimal balance, decimal requested, Exception inner)
        : base($"Недостаточно средств", inner)
    {
        Balance = balance;
        RequestedAmount = requested;
    }
}

// Использование
public void Withdraw(decimal amount)
{
    if (amount > _balance)
    {
        throw new InsufficientFundsException(_balance, amount);
    }
}

// Перехват
try
{
    account.Withdraw(1000);
}
catch (InsufficientFundsException ex)
{
    Console.WriteLine($"Баланс: {ex.Balance}, Запрошено: {ex.RequestedAmount}");
}

Правила:

  • Наследуйте от Exception
  • Добавляйте параметры для контекста
  • Реализуйте serializable конструкторы
  • Используйте суффикс Exception в имени
Unit-тесты vs Интеграционные тесты — разница.
обяз

Unit-тесты (Модульные):

  • Проверяют отдельный модуль (класс, метод)
  • Изолированы от внешних зависимостей (mock, stub)
  • Быстрые (миллисекунды)
  • Много (сотни/тысячи)
  • Легко поддерживать
  • Пример: тест метода расчёта скидки

Интеграционные тесты:

  • Проверяют взаимодействие между компонентами
  • Используют реальные зависимости (БД, API, файлы)
  • Медленнее (секунды)
  • Меньше (десятки)
  • Сложнее в поддержке
  • Пример: тест взаимодействия с БД

Сравнение:

Характеристика Unit-тесты Интеграционные тесты
Область Один модуль Несколько модулей
Зависимости Mock/Stub Реальные
Скорость Быстрые Медленные
Количество Много Мало
Сложность Низкая Высокая
Пример Тест математической функции Тест сохранения в БД

Пирамида тестирования:

  • Основа: Unit-тесты (много, быстро)
  • Середина: Интеграционные тесты (средне)
  • Верх: End-to-End тесты (мало, медленно)
AAA — Arrange, Act, Assert.
обяз

AAA — шаблон написания тестов.

1. Arrange (Подготовка)

  • Создание объектов
  • Настройка зависимостей (mock)
  • Подготовка данных

2. Act (Действие)

  • Вызов тестируемого метода
  • Выполнение операции

3. Assert (Проверка)

  • Проверка результатов
  • Сравнение с ожидаемым

Пример:

[Fact]
public void CalculateDiscount_ValidCustomer_ReturnsCorrectDiscount()
{
    // Arrange
    var customer = new Customer { IsVip = true };
    var calculator = new DiscountCalculator();
    decimal price = 100m;
    
    // Act
    decimal discount = calculator.Calculate(customer, price);
    
    // Assert
    Assert.Equal(20m, discount);  // 20% скидка для VIP
}

[Fact]
public void Add_WhenListIsFull_ThrowsException()
{
    // Arrange
    var list = new FixedSizeList(3);
    list.Add(1);
    list.Add(2);
    list.Add(3);
    
    // Act & Assert
    Assert.Throws<InvalidOperationException>(() => list.Add(4));
}

Преимущества:

  • Чёткая структура
  • Легко читать
  • Легко поддерживать
  • Стандарт де-факто
Mock / Stub / Fake — разница.
mid

Stub (Заглушка):

  • Заменяет зависимость
  • Возвращает заданные ответы
  • Не проверяет, как вызвали
  • Простой, минимальный
// Stub — всегда возвращает 5
class StubCalculator : ICalculator
{
    public int Add(int a, int b) => 5;
}

Mock (Имитация):

  • Заменяет зависимость
  • Позволяет проверять вызовы
  • Проверяет, как и сколько раз вызвали
  • Более сложный
// Mock — проверяет вызовы
var mock = new Mock<ILogger>();
mock.Setup(x => x.Log(It.IsAny<string>()));

// Act
service.Process();

// Verify
mock.Verify(x => x.Log("Processed"), Times.Once);

Fake (Фальшивка):

  • Рабочая упрощённая реализация
  • Не подходит для продакшена
  • Имеет реальную логику (упрощённую)
// Fake — упрощённая БД в памяти
class FakeUserRepository : IUserRepository
{
    private List<User> _users = new List<User>();
    
    public void Add(User user) => _users.Add(user);
    public User Get(int id) => _users.FirstOrDefault(u => u.Id == id);
}

Сравнение:

Тип Поведение Проверка Сложность
Stub Заданное поведение Нет Низкая
Mock Настраиваемое Да Высокая
Fake Упрощённая логика Нет Средняя
Moq / NSubstitute — популярные фреймворки.
mid

Moq:

  • Самый популярный фреймворк для моков
  • Использует лямбда-выражения
  • Сильная типизация
var mock = new Mock<IUserRepository>();

// Настройка поведения
mock.Setup(repo => repo.GetUser(It.IsAny<int>()))
    .Returns(new User { Id = 1, Name = "Alice" });

mock.Setup(repo => repo.GetUser(10))
    .Returns((User)null);

mock.Setup(repo => repo.GetUser(It.IsInRange(1, 10, Range.Inclusive)))
    .Returns(new User { Id = 5 });

// Проверка вызовов
mock.Verify(repo => repo.GetUser(1), Times.Once);
mock.Verify(repo => repo.GetUser(It.IsAny<int>()), Times.AtLeastOnce);

NSubstitute:

  • Более лаконичный синтаксис
  • Меньше шаблонного кода
  • Более читаемый
var repo = Substitute.For<IUserRepository>();

// Настройка
repo.GetUser(Arg.Any<int>()).Returns(new User { Id = 1, Name = "Alice" });
repo.GetUser(10).Returns((User)null);
repo.GetUser(Arg.Is<int>(x => x > 5)).Returns(new User { Id = 5 });

// Проверка вызовов
repo.Received(1).GetUser(1);
repo.Received().GetUser(Arg.Any<int>());

Сравнение:

Характеристика Moq NSubstitute
Синтаксис Многословный Лаконичный
Популярность Очень высокая Высокая
Сложность Средняя Низкая
Документация Отличная Хорошая
