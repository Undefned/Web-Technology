⚡ 26. Производительность и оптимизация Mid+

Профилирование — как найти узкие места.
mid

Инструменты профилирования:

  • BenchmarkDotNet — бенчмаркинг кода
  • dotMemory / dotTrace — память и производительность
  • PerfView — от Microsoft (GC, CPU, ETW)
  • Visual Studio Diagnostic Tools — встроенные
  • Application Insights / DataDog — в продакшене

Пример с BenchmarkDotNet:

[MemoryDiagnoser]
public class StringBenchmark
{
    [Benchmark]
    public string Concat()
    {
        string s = "";
        for (int i = 0; i < 1000; i++)
            s += i.ToString();
        return s;
    }

    [Benchmark]
    public string StringBuilder()
    {
        var sb = new StringBuilder();
        for (int i = 0; i < 1000; i++)
            sb.Append(i);
        return sb.ToString();
    }
}

Что искать:

  • CPU — много вычислений, плохие алгоритмы
  • Memory — много аллокаций → GC
  • IO — блокирующие операции
  • Locks — contention (конкуренция за блокировки)
Оптимизация памяти: Span, Memory, ArrayPool, ObjectPool.
mid

Span<T> — без аллокаций, работа с памятью.

string text = "Hello World";
ReadOnlySpan<char> slice = text.AsSpan(6, 5);  // "World"

Memory<T> — для асинхронных операций.

Memory<byte> memory = new byte[1024];
await stream.ReadAsync(memory);

ArrayPool<T> — пул массивов (уменьшает GC).

var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(1024);
try
{
    // Используем buffer
}
finally
{
    pool.Return(buffer);
}

ObjectPool<T> — пул объектов (Microsoft.Extensions.ObjectPool).

var pool = new DefaultObjectPool<StringBuilder>(
    new DefaultPooledObjectPolicy<StringBuilder>());

var sb = pool.Get();
try
{
    sb.Append("Hello");
    return sb.ToString();
}
finally
{
    sb.Clear();
    pool.Return(sb);
}
Оптимизация LINQ — когда использовать, когда избегать.
mid

Когда использовать LINQ:

  • Читаемость важнее производительности
  • Небольшие коллекции (< 1000 элементов)
  • Не в горячих путях

Когда избегать LINQ:

  • Большие коллекции (петля может быть быстрее)
  • Горячие пути (высокая нагрузка)
  • Сложные запросы (несколько Where, Select, OrderBy)
  • Критичные по производительности участки

Оптимизации:

// ❌ Медленно — лямбды создаются каждый раз
list.Where(x => x > 5).Select(x => x * 2).ToList();

// ✅ Быстрее — предварительная компиляция
static readonly Func<int, bool> _filter = x => x > 5;
static readonly Func<int, int> _map = x => x * 2;
list.Where(_filter).Select(_map).ToList();

// ❌ Медленно — Count() в условии
if (list.Count(x => x > 5) > 0) { }

// ✅ Быстрее — Any()
if (list.Any(x => x > 5)) { }
Оптимизация строк — StringBuilder, String.Create, интернирование.
mid

StringBuilder — для частых изменений.

var sb = new StringBuilder(1000);
for (int i = 0; i < 1000; i++)
    sb.Append(i);
string result = sb.ToString();

String.Create — минимальные аллокации (C# 10).

string result = string.Create(10, 42, (span, state) =>
{
    span[0] = 'H';
    span[1] = 'e';
    span[2] = 'l';
    span[3] = 'l';
    span[4] = 'o';
});

String.Intern — пул строк (экономия памяти).

string s1 = "Hello";  // В пуле
string s2 = new string('H', 5);  // Не в пуле
string s3 = string.Intern(s2);  // В пуле
GC-оптимизация — избегать аллокаций в горячих путях.
mid

Правила:

  • Избегать new object() в циклах
  • Использовать struct вместо class для маленьких объектов
  • Использовать ArrayPool<T> и ObjectPool<T>
  • Избегать string конкатенации в циклах
  • Использовать Span<T> и Memory<T>
  • Отключать ChangeTracker в EF Core для чтения

Примеры:

// ❌ Много аллокаций
List<string> result = new();
for (int i = 0; i < 10000; i++)
    result.Add(new string('A', i));  // Каждый раз новая строка

// ✅ Меньше аллокаций (пул строк?)
// Но здесь строки нужны — это нормально

// ❌ Аллокации в горячем пути
public void Process(Span<int> data)
{
    foreach (int x in data)
        ProcessItem(x);  // Может создавать объекты внутри
}

// ✅ Без аллокаций (если ProcessItem не создаёт объекты)
Кэширование — стратегии (Cache-Aside, Write-Through, Write-Behind).
mid

Cache-Aside (Lazy Loading)

  • Сначала проверяем кэш
  • Если нет — загружаем из БД
  • Сохраняем в кэш
async Task<User> GetUserAsync(int id)
{
    var user = await cache.GetAsync<User>($"user:{id}");
    if (user == null)
    {
        user = await db.GetUserAsync(id);
        await cache.SetAsync($"user:{id}", user, TimeSpan.FromMinutes(10));
    }
    return user;
}

Write-Through

  • Запись одновременно в БД и кэш
  • Гарантирует актуальность кэша
async Task UpdateUserAsync(User user)
{
    await db.UpdateUserAsync(user);
    await cache.SetAsync($"user:{user.Id}", user, TimeSpan.FromMinutes(10));
}

Write-Behind (Write-Back)

  • Запись в кэш, асинхронно в БД
  • Быстрее, но возможна потеря данных
  • Используется в высоконагруженных системах
Асинхронная производительность — ValueTask, ConfigureAwait.
mid

ValueTask<T> — для синхронных результатов.

public async ValueTask<int> GetCachedValueAsync()
{
    if (_cache.TryGetValue("key", out int value))
        return value;  // Нет аллокации
    return await ComputeValueAsync();  // Только если асинхронно
}

ConfigureAwait(false) — избегает захвата контекста.

// В библиотеках
await httpClient.GetStringAsync(url).ConfigureAwait(false);

// В UI-приложениях — использовать только в не-UI коде
// После await — продолжение в пуле потоков, а не в UI

Избегать async void

// ❌ Плохо — исключения теряются
async void BadMethod() { throw new Exception(); }

// ✅ Хорошо
async Task GoodMethod() { throw new Exception(); }
