Пакеты — правила видимости (экспорт)

Видимость в Go определяется простым правилом:
Имена с большой буквы — экспортируются (видны из других пакетов).
Имена с маленькой буквы — приватные (видны только внутри пакета).

Пример:

package mypackage

// Экспортируемая (публичная) переменная
var PublicVar = "видна всем"

// Приватная переменная
var privateVar = "видна только внутри пакета"

// Экспортируемая функция
func PublicFunc() string {
    return "вызов из других пакетов"
}

// Приватная функция
func privateFunc() string {
    return "только внутри пакета"
}

// Экспортируемая структура
type PublicStruct struct {
    PublicField  string  // экспортируемое поле
    privateField int     // приватное поле
}

// Приватная структура
type privateStruct struct {
    // ...
}

Как использовать экспортированные имена из другого пакета:

package main

import "mypackage"

func main() {
    // Доступно
    mypackage.PublicFunc()
    fmt.Println(mypackage.PublicVar)
    
    // НЕ доступно
    // mypackage.privateFunc()    // ошибка
    // fmt.Println(mypackage.privateVar)  // ошибка
}

Почему это важно:

  • Экспорт — основа инкапсуляции в Go
  • Приватные имена можно менять без страха сломать внешний код
  • Публичные имена формируют API пакета
Инициализация пакетов и `init()`

Порядок инициализации в Go очень важен для понимания.

Порядок выполнения:

  1. Инициализируются пакеты (в порядке импорта, но без циклов)
  2. Внутри пакета: сначала константы, потом переменные (с вычислением выражений)
  3. Выполняются функции init() в порядке объявления
  4. Выполняется main() (если пакет main)

Функция init():

  • Может быть в любом пакете
  • Не принимает аргументов и ничего не возвращает
  • В пакете может быть несколько функций init()
  • Выполняется автоматически при импорте пакета
  • Часто используется для настройки, регистрации драйверов

Пример:

package database

import "fmt"

// Инициализация переменной
var dbConnection string = initDB()

func initDB() string {
    fmt.Println("Инициализация базы данных...")
    return "localhost:5432"
}

// Первая функция init
func init() {
    fmt.Println("Первый init: настройка логгера")
}

// Вторая функция init
func init() {
    fmt.Println("Второй init: проверка соединения")
}

func main() {
    // Здесь уже всё инициализировано
}

// Вывод при запуске:
// Инициализация базы данных...
// Первый init: настройка логгера
// Второй init: проверка соединения

Импорт ради init():

import (
    "database/sql"
    _ "github.com/lib/pq"  // _ означает «не используем напрямую, но init() выполним»
)
Интерфейсы — неявная реализация

Интерфейс в Go — это набор методов. Любой тип, который реализует все эти методы, автоматически реализует интерфейс.

Ключевое отличие от других языков:

  • В Go не нужно явно указывать implements
  • Реализация интерфейса неявная — если методы совпадают, интерфейс считается реализованным
  • Это делает код более гибким и слабо связанным

Пример:

// Определяем интерфейс
type Speaker interface {
    Speak() string
}

// Структура Dog (метод Speak совпадает → реализует Speaker)
type Dog struct{ Name string }

func (d Dog) Speak() string {
    return "Гав-гав!"
}

// Структура Cat (тоже реализует Speaker)
type Cat struct{ Name string }

func (c Cat) Speak() string {
    return "Мяу!"
}

// Функция работает с любым Speaker
func MakeSound(s Speaker) {
    fmt.Println(s.Speak())
}

func main() {
    dog := Dog{Name: "Бобик"}
    cat := Cat{Name: "Мурка"}
    
    MakeSound(dog)  // Гав-гав!
    MakeSound(cat)  // Мяу!
}

Почему это мощно:

  • Можно добавлять новые типы, реализующие интерфейс, не меняя существующий код
  • Интерфейсы можно определять после того, как тип уже написан
  • Отлично подходит для тестирования (легко подменять реализации)
Пустой интерфейс `interface{}` (`any`)

interface{} (с Go 1.18 появился синоним any) — это интерфейс без методов.

Что это значит:

  • Любой тип автоматически реализует пустой интерфейс
  • Это как object в C# или Object в Java
  • Может хранить любое значение любого типа

Пример:

var anything any  // то же что interface{}

anything = 42
anything = "Hello"
anything = []int{1, 2, 3}
anything = Dog{Name: "Бобик"}

Когда использовать:

  • Когда функция может принимать абсолютно любые типы (fmt.Println)
  • Для структур данных, где тип не известен заранее
  • Для работы с JSON (неструктурированные данные)

Когда НЕ использовать:

  • Потеря безопасности типов (ошибки во время выполнения)
  • Ухудшение производительности (нужно приводить типы)
  • Когда можно использовать обобщения (generics) с Go 1.18+

Приведение типа (type assertion):

var val any = "Hello"

// Без проверки (паника, если тип не совпадает)
s := val.(string)
fmt.Println(s)

// С проверкой (безопасно)
s, ok := val.(string)
if ok {
    fmt.Println("Строка:", s)
} else {
    fmt.Println("Это не строка")
}
Приведение типов (Type Assertion) — `x.(T)` и `v, ok := x.(T)`

Type Assertion — это способ извлечь значение конкретного типа из интерфейса.

Две формы:

1. Без проверки (опасно):

var i any = 42
x := i.(int)  // если i содержит int — ок, иначе паника
fmt.Println(x)

2. С проверкой (безопасно):

var i any = "Hello"
x, ok := i.(string)
if ok {
    fmt.Println("Это строка:", x)
} else {
    fmt.Println("Это не строка")
}

Когда использовать какую форму:

  • Без проверки: когда вы абсолютно уверены в типе (например, после проверки if)
  • С проверкой: всегда, когда есть хоть малейшая неопределённость

Пример с type switch:

func describe(v any) {
    switch v := v.(type) {
    case int:
        fmt.Printf("Целое число: %d\n", v)
    case string:
        fmt.Printf("Строка: %s\n", v)
    case bool:
        fmt.Printf("Булево: %t\n", v)
    default:
        fmt.Printf("Неизвестный тип: %T\n", v)
    }
}
Ошибки (Errors) — почему нет исключений?

В Go нет исключений (try/catch/finally) в классическом понимании. Вместо этого используется явная обработка ошибок через возвращаемые значения.

Почему так сделано:

  • Явность: вы всегда видите, где может возникнуть ошибка
  • Надёжность: ошибки не могут «улететь» на несколько уровней вверх незамеченными
  • Простота: код легче читать и понимать
  • Производительность: нет накладных расходов на стек исключений

Как это выглядит:

// Стандартный паттерн — возвращаем (result, error)
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("деление на ноль")
    }
    return a / b, nil  // nil означает «ошибки нет»
}

func main() {
    result, err := divide(10, 2)
    if err != nil {
        fmt.Println("Ошибка:", err)
        return
    }
    fmt.Println("Результат:", result)
}

Интерфейс error:

type error interface {
    Error() string
}

Любой тип, у которого есть метод Error() string, может быть ошибкой.

Создание ошибок:

// Простая ошибка
err1 := errors.New("что-то пошло не так")

// С форматированием
err2 := fmt.Errorf("не удалось открыть файл %s: %w", filename, originalErr)

// Кастомная ошибка
type MyError struct {
    Code    int
    Message string
}

func (e MyError) Error() string {
    return fmt.Sprintf("код %d: %s", e.Code, e.Message)
}
Паттерн `if err != nil` — почему это нормально?

if err != nil — это самый частый код в Go. Новички часто жалуются, что это «многословно», но у этого подхода есть причины.

Пример:

func readConfig(filename string) error {
    data, err := os.ReadFile(filename)
    if err != nil {
        return fmt.Errorf("не удалось прочитать файл: %w", err)
    }
    
    config, err := parseConfig(data)
    if err != nil {
        return fmt.Errorf("не удалось распарсить конфиг: %w", err)
    }
    
    err = validateConfig(config)
    if err != nil {
        return fmt.Errorf("конфиг невалидный: %w", err)
    }
    
    return nil
}

Почему это хорошо:

  • Читаемость: сразу видно, где код может завершиться с ошибкой
  • Контроль: на каждом шаге вы решаете, что делать с ошибкой
  • Отладка: легко добавить логирование на любом шаге
  • Обёртывание ошибок: можно добавить контекст (%w)

Сравнение с исключениями:

// В Java/C# — исключение может улететь далеко
try {
    readConfig();
    startServer();
} catch (Exception e) {
    // Непонятно, где именно упало
}

// В Go — всё явно
if err := readConfig(); err != nil {
    log.Fatal("ошибка чтения конфига:", err)
}
if err := startServer(); err != nil {
    log.Fatal("ошибка старта сервера:", err)
}

Советы:

  • Не игнорируйте ошибки (не пишите _, _ = ...)
  • Всегда обрабатывайте ошибку или пробрасывайте её выше
  • Добавляйте контекст с помощью fmt.Errorf("...: %w", err)
`errors.Is` и `errors.As` — цепочки ошибок

Начиная с Go 1.13, появилась возможность обёртывать ошибки и проверять их.

Обёртывание ошибок (%w):

originalErr := errors.New("соединение потеряно")
err := fmt.Errorf("не удалось отправить запрос: %w", originalErr)
// Теперь err содержит originalErr внутри

errors.Is — проверка на конкретную ошибку:

var ErrNotFound = errors.New("не найдено")

func findUser(id int) error {
    return fmt.Errorf("пользователь %d: %w", id, ErrNotFound)
}

err := findUser(42)
if errors.Is(err, ErrNotFound) {
    fmt.Println("Пользователь не найден")
}

errors.As — извлечение ошибки конкретного типа:

type MyError struct {
    Code int
    Msg  string
}

func (e MyError) Error() string {
    return fmt.Sprintf("код %d: %s", e.Code, e.Msg)
}

func doSomething() error {
    return MyError{Code: 500, Msg: "внутренняя ошибка"}
}

err := doSomething()
var myErr MyError
if errors.As(err, &myErr) {
    fmt.Printf("Код ошибки: %d\n", myErr.Code)
}

Разница Is vs As:

  • Is: проверяет, есть ли в цепочке конкретная ошибка (по значению)
  • As: извлекает ошибку конкретного типа (по типу)
Panic / Recover — когда использовать?

panic — это состояние, когда программа не может продолжить работу и начинает «падать».

recover — позволяет перехватить панику и восстановить управление.

Когда возникает паника:

  • Обращение к nil указателю
  • Выход за границы массива/слайса
  • Явный вызов panic("сообщение")

Пример с recover:

func safeCall() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Восстановились после паники:", r)
        }
    }()
    
    // Какой-то код, который может вызвать панику
    panic("что-то пошло не так")
}

func main() {
    safeCall()
    fmt.Println("Программа продолжает работу")
}

Когда использовать panic:

  • Почти никогда в обычном коде
  • Только когда программа не может продолжать работу (например, не удалось инициализировать критический компонент)
  • В тестах — для проверки поведения при ошибках

Когда использовать recover:

  • В HTTP-хендлерах — чтобы не уронить весь сервер из-за одной паники
  • В горутинах — чтобы одна упавшая горутина не убила всю программу
  • В библиотеках — чтобы перехватить панику и вернуть ошибку

Золотое правило:
Для ожидаемых ошибок используйте возврат error.
Для неожиданных критических ситуаций — panic.

Встраивание (Embedding) vs Наследование

В Go нет наследования классов, как в ООП-языках. Вместо него используется композиция через встраивание (embedding).

Что такое встраивание:

  • Вы включаете одну структуру в другую без имени поля
  • Поля и методы встроенной структуры «поднимаются» на уровень внешней
  • Это не наследование — это делегирование

Пример:

type Animal struct {
    Name string
}

func (a Animal) Speak() string {
    return "..."
}

type Dog struct {
    Animal      // встраивание (без имени)
    Breed string
}

func (d Dog) Speak() string {
    return "Гав-гав!"  // переопределение метода
}

func main() {
    d := Dog{
        Animal: Animal{Name: "Бобик"},
        Breed:  "Овчарка",
    }
    
    // Доступ к полям Animal напрямую
    fmt.Println(d.Name)  // "Бобик"
    fmt.Println(d.Speak())  // "Гав-гав!" (переопределённый)
}

Разница с наследованием:

Наследование (Java/C#)Встраивание (Go)
Отношение IS-AОтношение HAS-A
Жёсткая связьГибкая композиция
Один родительМожно встроить несколько
Полиморфизм классовПолиморфизм интерфейсов

Когда использовать встраивание:

  • Когда нужно переиспользовать методы и поля
  • Для реализации паттерна «декоратор»
  • Для создания простых иерархий без сложности наследования
