🧠 5. Память, GC и Производительность

Сборщик мусора (GC) — как работает в Go?

Сборщик мусора (Garbage Collector, GC) в Go — это автоматический механизм освобождения памяти, которая больше не используется.

Особенности GC в Go:

  • Параллельный — работает одновременно с вашим кодом (не останавливает программу полностью)
  • Неинвазивный — не требует ручного управления памятью
  • Низкая латентность — паузы обычно меньше 1 мс
  • Три поколения? Нет, в Go используется однопоколенный GC (в отличие от C#/Java)

Как примерно работает:

  1. Маркировка (Mark) — GC находит все объекты, на которые есть ссылки из корневых объектов (глобальные переменные, стек горутин)
  2. Очистка (Sweep) — память, которая не была отмечена, считается свободной и может быть переиспользована
  3. Процесс происходит параллельно с выполнением программы (не останавливает её полностью)

Когда запускается GC:

  • Когда объём выделенной памяти достигает определённого порога
  • Порог вычисляется автоматически на основе скорости аллокаций
  • Можно вызвать вручную через runtime.GC() (но не рекомендуется)

Настройка GC:

import "runtime/debug"

// Установить цель — 50% времени на GC (по умолчанию 100%)
debug.SetGCPercent(50)  // чаще запускать GC, но меньше паузы

// Отключить GC (для экстремальной оптимизации!)
debug.SetGCPercent(-1)

Важно: В отличие от C#/Java, в Go нет поколений (Gen 0, 1, 2). Это упрощает GC, но может быть менее эффективно для долгоживущих объектов.

Утечки памяти в Go — возможны?

Да, утечки памяти в Go возможны, хотя GC автоматически освобождает память.

Основные причины утечек:

1. Забытые горутины — горутина ждёт данные из канала, который никогда не получит данные

func main() {
    ch := make(chan int)
    go func() {
        v := <-ch  // блокируется навсегда, горутина не завершится
        fmt.Println(v)
    }()
    // ch никогда не получит данные → горутина висит вечно
}

2. Ссылки в глобальных переменных — объекты, на которые ссылаются глобальные переменные, никогда не будут собраны

var cache = map[string][]byte{}  // глобальная карта

func addToCache(key string, data []byte) {
    cache[key] = data  // никогда не удаляется → память растёт
}

3. Срезы, которые не освобождают память

func leak() {
    big := make([]byte, 1024*1024)  // 1 МБ
    small := big[:100]  // создаём маленький срез, но big всё ещё в памяти!
    // small держит ссылку на весь массив → 1 МБ не освободится
}

4. Циклические ссылки — два объекта ссылаются друг на друга

type A struct { B *B }
type B struct { A *A }

a := &A{}
b := &B{}
a.B = b
b.A = a
// GC не может удалить их, так как они ссылаются друг на друга

Как обнаружить утечки:

  • Использовать pprof для профилирования памяти
  • Смотреть на рост памяти во время работы программы
  • Тестировать с нагрузкой и анализировать графики
Профилирование — `pprof` и бенчмарки

Профилирование — это способ измерить, где программа тратит время и память.

Встроенный профилировщик pprof:

  • Позволяет смотреть CPU, память, блокировки, горутины
  • Может работать в веб-интерфейсе или командной строке

Добавление профилировщика в код:

import _ "net/http/pprof"

func main() {
    go func() {
        log.Println(http.ListenAndServe("localhost:6060", nil))
    }()
    // ... остальной код
}

Команды для анализа:

# Сбор CPU-профиля
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30

# Сбор памяти
go tool pprof http://localhost:6060/debug/pprof/heap

# Веб-интерфейс
go tool pprof -http=:8080 cpu.pprof

Бенчмарки (написание тестов производительности):

// файл: math_test.go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(10, 20)  // N раз
    }
}

// Запуск
go test -bench=. -benchmem ./...

Как читать результаты бенчмарка:

`sync.Pool` — пул объектов

sync.Pool — это временное хранилище объектов, чтобы переиспользовать их и снизить нагрузку на GC.

Когда использовать:

  • Объекты создаются и удаляются очень часто
  • Создание объектов дорогое (например, большие буферы)
  • Высокая нагрузка и нужно снизить аллокации

Пример:

var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 1024)  // создаётся, когда пуст
    },
}

func process() {
    // Берём буфер из пула
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)  // возвращаем обратно
    
    // Используем buf...
}

Важные моменты:

  • Объекты в пуле могут быть удалены GC в любой момент
  • Не храните важные данные в пуле — только временные
  • Не предполагайте, что объект сохранит состояние между использованиями
  • Используйте defer для возврата объекта, даже если паника

Когда НЕ использовать:

  • Для маленьких объектов (аллокация дешевле, чем работа с пулом)
  • Для объектов с состоянием (будут использованы повторно с непредсказуемым состоянием)
Трейсинг — `go tool trace`

Трейсинг — это запись того, что происходило в программе во времени.

Что можно увидеть в трейсе:

  • Когда запускались и завершались горутины
  • Работу планировщика Go
  • Время выполнения GC
  • Блокировки на мьютексах и каналах
  • Взаимодействие с сетью и файловой системой

Как записать трейс:

import "runtime/trace"

func main() {
    // Создаём файл для трейса
    f, err := os.Create("trace.out")
    if err != nil {
        panic(err)
    }
    defer f.Close()
    
    // Начинаем запись
    err = trace.Start(f)
    if err != nil {
        panic(err)
    }
    defer trace.Stop()
    
    // ... ваш код
}

Просмотр трейса:

go tool trace trace.out
# Откроется браузер с интерактивным интерфейсом

Когда использовать:

  • Загадочные падения производительности
  • Много горутин, которые не работают
  • Проблемы с планировщиком
  • Когда pprof не даёт ответа

Пример задачи для трейсинга:

  • Вы запустили 1000 горутин, но загрузка CPU низкая
  • Трейс покажет, что горутины блокируются на каналах или мьютексах
Ручной вызов GC — когда нужно?

В большинстве случаев не нужно вызывать GC вручную. Go делает это автоматически.

Когда может понадобиться:

  • Перед важным измерением производительности — чтобы GC не сбил замеры
  • После большого объёма выделений — чтобы освободить память до следующей нагрузки
  • В тестах — для детерминированного поведения

Как вызвать:

import "runtime"

func main() {
    // Принудительно запустить GC
    runtime.GC()
    
    // Дождаться завершения GC
    runtime.GC()
}

Важные нюансы:

  • Вызов runtime.GC() блокирует выполнение программы
  • Может быть дорогим и замедлить программу
  • В продакшене почти никогда не используется
  • Иногда полезен для тестов, чтобы изолировать влияние GC

Вместо ручного вызова:

  • Настройте debug.SetGCPercent() — измените частоту запуска
  • Снизьте количество аллокаций — используйте sync.Pool
  • Оптимизируйте код, чтобы создавать меньше объектов
Как снизить нагрузку на GC?

Главный совет: создавайте меньше объектов. Чем меньше аллокаций, тем реже запускается GC.

Стратегии оптимизации:

1. Используйте sync.Pool — переиспользуйте объекты вместо создания новых

var pool = sync.Pool{New: func() any { return &MyStruct{} }}

obj := pool.Get().(*MyStruct)
// работаем
pool.Put(obj)  // возвращаем

2. Избегайте временных объектов в циклах

// ПЛОХО — каждый раз создаётся новый слайс
for i := 0; i < 1000; i++ {
    s := make([]int, 100)
    // работаем
}

// ХОРОШО — переиспользуем один слайс
s := make([]int, 100)
for i := 0; i < 1000; i++ {
    // работаем с s
}

3. Используйте слайсы с предварительной аллокацией

// ПЛОХО — много переаллокаций
var s []int
for i := 0; i < 1000; i++ {
    s = append(s, i)
}

// ХОРОШО — выделяем сразу нужный размер
s := make([]int, 0, 1000)
for i := 0; i < 1000; i++ {
    s = append(s, i)
}

4. Избегайте конвертации string ↔ []byte — она создаёт копии

// ПЛОХО — создаёт копию
b := []byte(s)

// ХОРОШО (но опасно!) — без копирования
import "unsafe"
b := unsafe.Slice(unsafe.StringData(s), len(s))

5. Используйте fmt.Fprintf вместо fmt.Sprintf + конкатенация

// ПЛОХО — создаёт промежуточные строки
msg := fmt.Sprintf("User %d", id)

// ХОРОШО — пишет сразу в буфер
var buf bytes.Buffer
fmt.Fprintf(&buf, "User %d", id)

6. Увеличьте процент GC, чтобы он запускался реже

debug.SetGCPercent(200)  // реже запускать GC
Команда `go test -bench` — детально

Бенчмарки в Go позволяют измерить производительность функций.

Структура бенчмарка:

  • Файл должен заканчиваться на _test.go
  • Функция начинается с Benchmark
  • Принимает *testing.B
  • Цикл for i := 0; i < b.N; i++ — b.N подбирается автоматически

Пример:

// math_test.go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(10, 20)
    }
}

func BenchmarkAddParallel(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            Add(10, 20)
        }
    })
}

Команды:

# Запустить все бенчмарки
go test -bench=.

# Запустить конкретный
go test -bench=BenchmarkAdd

# С подсчётом аллокаций
go test -bench=. -benchmem

# Запустить N раз (для точности)
go test -bench=. -count=5

# Сравнение двух реализаций (benchstat)
go test -bench=. -count=10 > old.txt
# ... меняем код ...
go test -bench=. -count=10 > new.txt
benchstat old.txt new.txt

Что означают результаты:

BenchmarkAdd-8    100000000    12.3 ns/op    0 B/op    0 allocs/op
      │              │           │             │          │
  кол-во ядер   кол-во итераций  время    байт на опер. аллокаций

Полезные флаги:

  • -benchtime=5s — увеличить время выполнения
  • -benchmem — показать аллокации
  • -cpu=1,2,4,8 — протестировать с разным числом ядер
