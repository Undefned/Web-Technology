☁️ 19. Микросервисы и Распределённые системы Mid+

Что такое микросервисы? Отличие от монолита.
обяз

Микросервисная архитектура — подход, при котором приложение строится как набор небольших, независимо развёртываемых сервисов.

Ключевые характеристики:

  • Каждый сервис решает одну бизнес-задачу
  • Сервисы независимо развёртываются
  • Каждый сервис имеет свою БД
  • Сервисы общаются по сети (HTTP/gRPC/Message Queue)
  • Разные технологии в разных сервисах
  • Команды работают независимо

Сравнение с монолитом:

Характеристика Монолит Микросервисы
Развёртывание Один деплой Много деплоев
Масштабирование Всё приложение Отдельные сервисы
БД Одна У каждого своя
Технологии Один стек Разные стеки
Команда Одна Много команд
Сложность Низкая Высокая

Когда выбрать микросервисы:

  • Большая команда (> 50 человек)
  • Высокая нагрузка
  • Частые релизы
  • Разные технологии для разных задач
Способы коммуникации микросервисов (REST, gRPC, Message Bus).
обяз

1. REST (HTTP/HTTPS) — синхронный

  • Простой, понятный
  • JSON/XML
  • Подходит для внешних API
  • Медленнее, чем gRPC

2. gRPC — синхронный (высокопроизводительный)

  • Protocol Buffers (бинарный)
  • Быстрее REST (в 10 раз)
  • Поддерживает стриминг
  • Требует генерации кода
  • Подходит для внутренних сервисов

3. Message Queue (RabbitMQ, Kafka) — асинхронный

  • Слабая связанность
  • Отказоустойчивость
  • Поддерживает события
  • Может задерживать доставку

Сравнение:

Характеристика REST gRPC Message Bus
Скорость Средняя Высокая Низкая (задержка)
Синхронность Да Да Нет (асинхронный)
Связанность Высокая Средняя Низкая
Пример Public API Внутренние сервисы События, фоновые задачи
Service Discovery (Consul, Eureka) — зачем?
mid

Service Discovery — механизм автоматического обнаружения сервисов.

Проблема:

  • В микросервисах адреса сервисов меняются (масштабирование, падения)
  • Нельзя прописывать IP вручную

Решение:

  • Сервисы регистрируются в Service Discovery
  • Клиенты спрашивают: "Где находится Service X?"
  • Получают адрес и подключаются

Популярные реализации:

  • Consul (HashiCorp) — + KV store, health checks
  • Eureka (Netflix) — для Spring Cloud
  • Kubernetes — встроенный (Services + DNS)

Пример в .NET:

// Регистрация в Consul
builder.Services.AddConsul(options =>
{
    options.Address = new Uri("http://consul:8500");
    options.Service = new Service
    {
        Name = "UserService",
        Address = "userservice",
        Port = 5000
    };
});
API Gateway (Ocelot, YARP) — зачем?
mid

API Gateway — единая точка входа для всех клиентов.

Зачем нужен:

  • Единый URL для всех микросервисов
  • Аутентификация (централизованная)
  • Маршрутизация запросов
  • Балансировка нагрузки
  • Кэширование
  • Логирование
  • Rate Limiting

Популярные реализации:

  • Ocelot — для .NET, настраивается JSON
  • YARP (Yet Another Reverse Proxy) — от Microsoft
  • Kong — Nginx-based
  • Traefik — для Kubernetes

Пример Ocelot:

// ocelot.json
{
    "Routes": [
        {
            "DownstreamPathTemplate": "/api/users/{everything}",
            "DownstreamScheme": "http",
            "DownstreamHostAndPorts": [
                { "Host": "localhost", "Port": 5001 }
            ],
            "UpstreamPathTemplate": "/users/{everything}",
            "UpstreamHttpMethod": [ "GET", "POST" ],
            "AuthenticationOptions": {
                "AuthenticationProviderKey": "Bearer"
            }
        }
    ]
}
Distributed Tracing (Jaeger, Zipkin) — зачем?
mid

Distributed Tracing — отслеживание запроса через цепочку микросервисов.

Проблема:

  • Запрос проходит через 5-10 сервисов
  • Непонятно, где возникает задержка
  • Логи каждого сервиса не дают целостной картины

Решение:

  • Каждый сервис добавляет span (отрезок времени)
  • Все span'ы собираются в один trace
  • Видно полную картину

Популярные реализации:

  • Jaeger (Uber) — популярный, OpenTelemetry
  • Zipkin (Twitter) — простой
  • OpenTelemetry — стандарт (поддерживает Jaeger, Zipkin, Datadog)

Пример в .NET:

// OpenTelemetry
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing =>
    {
        tracing
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation()
            .AddOtlpExporter(options =>
            {
                options.Endpoint = new Uri("http://jaeger:4317");
            });
    });
Saga паттерн — для распределённых транзакций.
mid

Saga — паттерн для управления распределёнными транзакциями.

Проблема:

  • Одна бизнес-операция затрагивает несколько микросервисов
  • Каждый сервис имеет свою БД
  • Нельзя использовать 2PC (двухфазный коммит)

Решение Saga:

  • Каждая операция — последовательность шагов
  • Каждый шаг имеет компенсирующее действие
  • При ошибке — выполняются компенсации

Два типа Saga:

1. Choreography (хореография)

  • Сервисы общаются через события
  • Нет координатора
  • Пример: Order → Payment → Delivery

2. Orchestration (оркестрация)

  • Центральный координатор (Saga Orchestrator)
  • Управляет последовательностью шагов
  • Пример: Saga Coordinator → Order → Payment → Delivery

Пример (Orchestration):

public class OrderSaga
{
    public async Task ExecuteAsync(Order order)
    {
        try
        {
            await _paymentService.ProcessAsync(order);
            await _inventoryService.ReserveAsync(order);
            await _deliveryService.ScheduleAsync(order);
            
            await _orderService.UpdateStatusAsync(order, "Completed");
        }
        catch (Exception)
        {
            // Компенсации
            await _deliveryService.CancelAsync(order);
            await _inventoryService.ReleaseAsync(order);
            await _paymentService.RefundAsync(order);
            
            await _orderService.UpdateStatusAsync(order, "Failed");
        }
    }
}
Circuit Breaker (Polly) — в распределённых системах.
mid

Circuit Breaker — предотвращает каскадные отказы.

Состояния:

  • Closed (Закрыт): запросы проходят, счётчик ошибок растёт
  • Open (Открыт): запросы блокируются (fail fast)
  • Half-Open (Полуоткрыт): пробные запросы для восстановления

Пример с Polly:

var policy = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(
        exceptionsAllowedBeforeBreaking: 3,
        durationOfBreak: TimeSpan.FromSeconds(30)
    );

await policy.ExecuteAsync(async () =>
{
    await httpClient.GetAsync("https://api.example.com");
});

Зачем:

  • Защита от перегрузки зависимостей
  • Быстрый отказ вместо тайм-аута
  • Автоматическое восстановление
Event Sourcing + CQRS — базовое понимание.
mid

Event Sourcing — хранение не текущего состояния, а всех событий, которые к нему привели.

Принцип:

  • Вместо UPDATE записей — сохраняем событие
  • Текущее состояние = сумма всех событий
  • Можно восстановить любое состояние в прошлом
  • Пример: аудит, логи, финансы

CQRS (Command Query Responsibility Segregation) — разделение операций чтения и записи.

  • Command: изменения (CREATE, UPDATE, DELETE)
  • Query: чтение (SELECT)
  • Разные модели для чтения и записи

Event Sourcing + CQRS вместе:

// Command — запись события
public class CreateOrderCommand
{
    public async Task Handle(Order order)
    {
        var @event = new OrderCreatedEvent(order);
        await _eventStore.SaveAsync(@event);
    }
}

// Query — чтение из проекции
public class GetOrderQuery
{
    public async Task<OrderDto> Handle(int orderId)
    {
        return await _readModel.GetAsync(orderId);
    }
}

Когда использовать:

  • Нужен полный аудит
  • Сложная бизнес-логика
  • Возможность отката
  • Высокая нагрузка (разделение чтения/записи)
Docker + Kubernetes — для микросервисов.
обяз

Docker — контейнеризация приложений.

  • Упаковка приложения + зависимостей
  • Одинаковое окружение везде
  • Лёгкий изоляция

Kubernetes (k8s) — оркестрация контейнеров.

  • Управление сотнями контейнеров
  • Автоматическое масштабирование
  • Автоматическое восстановление
  • Обновления без простоя (rolling update)

Kubernetes компоненты:

  • Pod — минимальная единица (один или несколько контейнеров)
  • Service — стабильный адрес для Pod'ов
  • Ingress — вход для внешних запросов
  • Deployment — управление версиями Pod'ов
  • ConfigMap / Secret — конфигурация и секреты

Пример деплоя:

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
      - name: user-service
        image: myapp/user-service:latest
        ports:
        - containerPort: 5000

---
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user-service
  ports:
  - port: 80
    targetPort: 5000
  type: LoadBalancer
