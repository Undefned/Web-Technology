⚡ 4. Конкурентность и Параллелизм

Goroutine vs Thread — в чем разница?

Горутина (goroutine) и поток (thread) — это не одно и то же.

Сравнение:

ХарактеристикаПоток ОС (Thread)Горутина (Goroutine)
Размер стека~1 МБ (фиксированный)~2 КБ (может расширяться)
СозданиеДорогое (системный вызов)Дешёвое (рантайм Go)
КоличествоОграничено (обычно < 10000)Миллионы!
ПланировщикОС (прерывает)Планировщик Go (не прерывает)
ПереключениеДорогое (переключение контекста)Дешёвое (управляет рантайм)

Модель M:N:

  • Go использует модель M горутин на N потоков
  • Планировщик Go распределяет горутины по потокам ОС
  • Обычно N = количество ядер процессора
  • Горутины могут «перемещаться» между потоками

Пример создания горутины:

func main() {
    // Обычный вызов (синхронный)
    doWork()
    
    // Горутина (асинхронный)
    go doWork()
    
    // Ждём завершения (иначе программа может завершиться раньше)
    time.Sleep(time.Second)
}
`sync.WaitGroup` — ожидание горутин

sync.WaitGroup — это семафор для ожидания завершения группы горутин.

Три метода:

  • Add(n) — увеличивает счётчик на n (сколько горутин будем ждать)
  • Done() — уменьшает счётчик на 1 (горутина завершилась)
  • Wait() — блокируется, пока счётчик не станет 0

Пример:

func main() {
    var wg sync.WaitGroup
    
    // Запускаем 5 горутин
    for i := 0; i < 5; i++ {
        wg.Add(1)  // увеличиваем счётчик
        go func(id int) {
            defer wg.Done()  // уменьшаем счётчик при завершении
            fmt.Printf("Горутина %d работает\n", id)
            time.Sleep(time.Second)
        }(i)
    }
    
    wg.Wait()  // ждём все 5 горутин
    fmt.Println("Все горутины завершились")
}

Важные правила:

  • Add() должен вызываться до запуска горутины
  • Done() следует вызывать через defer — это гарантирует выполнение
  • Нельзя копировать WaitGroup (передавайте по указателю)
`sync.Mutex` и `sync.RWMutex` — блокировки

Мьютексы (mutex) — это примитивы синхронизации для защиты общих данных от одновременного доступа.

sync.Mutex — взаимное исключение:

  • Только одна горутина может владеть блокировкой в любой момент
  • Методы: Lock() и Unlock()
  • Используйте defer для автоматической разблокировки

Пример с Mutex:

type Counter struct {
    mu    sync.Mutex
    value int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.value++
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.value
}

sync.RWMutex — блокировка с разделением:

  • Много читателей могут одновременно читать
  • Только один писатель может писать (и блокирует всех)
  • Методы: RLock() / RUnlock() для чтения, Lock() / Unlock() для записи
  • Используйте, когда чтений гораздо больше, чем записей

Пример с RWMutex:

type Cache struct {
    mu    sync.RWMutex
    data  map[string]string
}

func (c *Cache) Get(key string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.data[key]
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = value
}
`sync.Map` — когда использовать?

sync.Map — это конкурентно-безопасная карта (хэш-таблица).

Когда НЕ использовать (в большинстве случаев):

  • Обычный map + Mutex быстрее для большинства сценариев
  • sync.Map оптимизирован для особых случаев
  • Не используйте «на всякий случай» — это медленнее

Когда использовать sync.Map:

  1. Ключи читаются намного чаще, чем записываются (кэш)
  2. Ключи известны заранее и не меняются
  3. Ключи уникальные и их много

Пример:

var cache sync.Map

// Запись
cache.Store("key", "value")

// Чтение
val, ok := cache.Load("key")
if ok {
    fmt.Println(val)
}

// Удаление
cache.Delete("key")

// Итерация
cache.Range(func(key, value any) bool {
    fmt.Println(key, value)
    return true  // продолжаем итерацию
})

Золотое правило:
Если вы не уверены, что вам нужен sync.Map, используйте обычный map + sync.Mutex.

Каналы (Channels) — устройство, буферизация

Канал (channel) — это средство коммуникации между горутинами. Это как труба, по которой можно передавать данные.

Создание канала:

// Небуферизированный (синхронный)
ch1 := make(chan int)

// Буферизированный (асинхронный, на 10 элементов)
ch2 := make(chan string, 10)

Операции с каналом:

ch := make(chan int)

// Отправка
ch <- 42

// Получение
value := <-ch

// Закрытие
close(ch)

// Проверка, закрыт ли канал
value, ok := <-ch

Небуферизированный канал:

  • Отправляющая горутина блокируется, пока кто-то не прочитает
  • Читающая горутина блокируется, пока кто-то не отправит
  • Гарантирует синхронизацию

Буферизированный канал:

  • Отправка не блокируется, пока буфер не заполнится
  • Чтение не блокируется, пока буфер не опустеет
  • Не гарантирует синхронизацию

Пример:

func main() {
    // Небуферизированный
    ch := make(chan string)
    go func() {
        ch <- "Hello"  // блокируется до чтения
    }()
    msg := <-ch  // блокируется до отправки
    fmt.Println(msg)
}
`for range` по каналу

for range читает из канала до тех пор, пока он не будет закрыт.

Пример:

func main() {
    ch := make(chan int)
    
    // Отправляем данные в канал
    go func() {
        for i := 0; i < 5; i++ {
            ch <- i
        }
        close(ch)  // обязательно закрыть!
    }()
    
    // Читаем до закрытия
    for v := range ch {
        fmt.Println(v)  // 0, 1, 2, 3, 4
    }
    fmt.Println("Канал закрыт")
}

Важные моменты:

  • Если канал не закрыть, range будет ждать вечно (deadlock)
  • Если канал закрыт, итерация завершается
  • Если канал nil, range блокируется навсегда

Кто должен закрывать канал:

  • Тот, кто отправляет данные, должен и закрывать
  • Получатель не должен закрывать канал (можно вызвать панику)
  • Закрывать канал нужно только когда больше не будет отправки
`select` — работа с несколькими каналами

select позволяет ждать события на нескольких каналах одновременно.

Как работает:

  • Блокируется, пока один из каналов не станет готов
  • Если несколько готовы — выбирает случайный
  • Аналог switch, но для каналов

Пример:

func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)
    
    go func() {
        time.Sleep(1 * time.Second)
        ch1 <- "из канала 1"
    }()
    
    go func() {
        time.Sleep(2 * time.Second)
        ch2 <- "из канала 2"
    }()
    
    for i := 0; i < 2; i++ {
        select {
        case msg1 := <-ch1:
            fmt.Println("Получено:", msg1)
        case msg2 := <-ch2:
            fmt.Println("Получено:", msg2)
        }
    }
}

select с default (неблокирующий):

select {
case msg := <-ch:
    fmt.Println(msg)
default:
    fmt.Println("Нет данных, продолжаем работу")
}

select с таймаутом:

select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(5 * time.Second):
    fmt.Println("Таймаут! Ничего не пришло")
}
Контекст (`context.Context`) — зачем нужен?

Контекст — это способ передать сигналы отмены и дедлайны между горутинами.

Зачем нужен:

  • Остановка долгих операций (запросы к БД, HTTP-запросы)
  • Передача дедлайнов (таймаутов)
  • Передача метаданных (например, ID запроса)
  • Каскадная отмена (если отменён родитель, отменяются все дети)

Создание контекста:

// Пустой контекст (корень)
ctx := context.Background()

// С отменой
ctx, cancel := context.WithCancel(context.Background())
defer cancel()  // важно вызвать!

// С таймаутом
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// С дедлайном
ctx, cancel := context.WithDeadline(context.Background(), time.Now().Add(time.Hour))
defer cancel()

// С метаданными
ctx := context.WithValue(context.Background(), "userID", 123)

Пример с отменой:

func worker(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            fmt.Println("Работа остановлена")
            return
        default:
            fmt.Println("Работаем...")
            time.Sleep(1 * time.Second)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    go worker(ctx)
    
    time.Sleep(3 * time.Second)
    cancel()  // останавливаем
    time.Sleep(1 * time.Second)
}
Fan-in / Fan-out паттерны

Это популярные паттерны работы с каналами и горутинами.

Fan-out (разветвление):

  • Одна горутина читает из одного канала
  • Несколько горутин обрабатывают данные параллельно
  • Результат отправляется в общий канал

Fan-in (схождение):

  • Несколько горутин пишут в общий канал
  • Одна горутина читает из общего канала

Пример Fan-out:

func main() {
    jobs := make(chan int, 10)
    results := make(chan int, 10)
    
    // Запускаем 3 воркера (fan-out)
    for w := 0; w < 3; w++ {
        go worker(jobs, results)
    }
    
    // Отправляем задачи
    for j := 0; j < 5; j++ {
        jobs <- j
    }
    close(jobs)
    
    // Собираем результаты (fan-in)
    for r := 0; r < 5; r++ {
        fmt.Println(<-results)
    }
}

func worker(jobs <-chan int, results chan<- int) {
    for job := range jobs {
        results <- job * 2  // обработка
    }
}
Worker Pool — реализация пула воркеров

Worker Pool — это ограниченное количество горутин, которые обрабатывают задачи из очереди.

Зачем:

  • Ограничение параллелизма (чтобы не убить систему)
  • Контроль над ресурсами
  • Эффективная обработка большого количества задач

Реализация:

type Task struct {
    ID   int
    Data string
}

func workerPool(numWorkers int, tasks <-chan Task) {
    var wg sync.WaitGroup
    
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for task := range tasks {
                fmt.Printf("Worker %d обрабатывает задачу %d\n", id, task.ID)
                time.Sleep(time.Millisecond * 500)
            }
        }(i)
    }
    
    wg.Wait()
}

func main() {
    tasks := make(chan Task, 100)
    
    // Заполняем задачами
    for i := 0; i < 20; i++ {
        tasks <- Task{ID: i, Data: "data"}
    }
    close(tasks)
    
    workerPool(3, tasks)  // 3 воркера
}
Data Race — что это, как обнаружить?

Data Race (гонка данных) — это ситуация, когда несколько горутин одновременно обращаются к одной памяти, и как минимум одно обращение — запись.

Пример гонки:

var counter int

func increment() {
    counter++  // НЕ атомарно! (читать, увеличить, записать)
}

func main() {
    for i := 0; i < 1000; i++ {
        go increment()
    }
    time.Sleep(time.Second)
    fmt.Println(counter)  // не 1000! (результат непредсказуем)
}

Как обнаружить:

  • Запуск с флагом -race: go run -race main.go
  • Тесты с -race: go test -race ./...
  • Программа выдаст подробный отчёт о гонках

Как исправить:

  1. Мьютекс — синхронизация доступа
  2. Атомарные операции (sync/atomic)
  3. Каналы — для коммуникации вместо общих данных
  4. Однопоточный доступ — дизайн без общего состояния

Исправление:

var mu sync.Mutex
var counter int

func increment() {
    mu.Lock()
    counter++
    mu.Unlock()
}

// Или через atomic
var counter int64

func increment() {
    atomic.AddInt64(&counter, 1)
}
Атомарные операции (`sync/atomic`)

sync/atomic — пакет для атомарных операций без блокировок.

Когда использовать:

  • Счётчики (increment)
  • Флаги (bool)
  • Атомарная замена указателей
  • Когда производительность критична, а мьютексы слишком тяжелы

Примеры:

import "sync/atomic"

var counter int64
var flag int32
var ptr unsafe.Pointer

// Инкремент
atomic.AddInt64(&counter, 1)

// Чтение
value := atomic.LoadInt64(&counter)

// Установка флага
atomic.StoreInt32(&flag, 1)

// Сравнение и замена (CAS)
atomic.CompareAndSwapInt32(&flag, 1, 0)

// Атомарная замена указателя
oldPtr := atomic.SwapPointer(&ptr, newPointer)

Почему атомарные операции быстрее мьютексов:

  • Не требуют переключения контекста
  • Обычно реализуются одной машинной инструкцией
  • Используют аппаратную поддержку процессора

Когда НЕ использовать:

  • Для сложных структур данных (используйте мьютекс)
  • Для операций, которые не встроены в пакет atomic
  • Когда сложно читать код (мьютекс понятнее)
