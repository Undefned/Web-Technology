🔁 31. Транзакции в распределённых системах Mid+

2PC (Two-Phase Commit) — что это, почему не используют в микросервисах.
mid

2PC (Two-Phase Commit) — протокол гарантированного коммита транзакции.

Фазы:

  • Фаза 1 (Prepare): координатор спрашивает все участники: "Готовы закоммитить?"
  • Фаза 2 (Commit): если все ответили "Да" — координатор отправляет "Commit", иначе "Rollback"
Координатор          Участник 1          Участник 2
    |                    |                   |
    |----- Prepare ----->|                   |
    |                    |----- Prepare ----->|
    |<---- Yes ----------|                   |
    |                    |<---- Yes ----------|
    |----- Commit ------>|                   |
    |                    |----- Commit ------>|
    |<---- Done ---------|                   |
    |                    |<---- Done ---------|

Почему не используют в микросервисах:

  • Блокировки: ресурсы залочены до завершения (плохо для высокой нагрузки)
  • Single Point of Failure: отказ координатора — все виснут
  • Задержки: синхронный, медленный
  • Сложность: трудно реализовать надёжно

Альтернатива: Saga паттерн (есть в Блоке 19).

Saga — Choreography vs Orchestration (подробно).
mid

Saga — паттерн для распределённых транзакций.

1. Choreography (хореография)

  • Сервисы общаются через события
  • Нет центрального координатора
  • Каждый сервис публикует события и реагирует на них
  • Гибкий, слабая связанность
  • Сложно отслеживать весь процесс
Order Service → (OrderCreated) → Payment Service
Payment Service → (PaymentCompleted) → Inventory Service
Inventory Service → (StockReserved) → Delivery Service

2. Orchestration (оркестрация)

  • Центральный Orchestrator управляет последовательностью
  • Orchestrator знает все шаги и компенсации
  • Проще управлять, легче отлаживать
  • Orchestrator — Single Point of Failure
Orchestrator:
    1. Create Order → Order Service
    2. Process Payment → Payment Service
    3. Reserve Stock → Inventory Service
    4. Schedule Delivery → Delivery Service
    5. Complete Order → Order Service

Когда что использовать:

  • Choreography: для простых процессов, слабой связанности
  • Orchestration: для сложных процессов, где нужен контроль
Eventual Consistency — что это, когда допустимо.
mid

Eventual Consistency (Согласованность в конечном счёте) — гарантия, что система станет согласованной, но не мгновенно.

Пример:

  • Пользователь создал заказ
  • Сервис заказов сохранил заказ
  • Сервис доставки получит событие через 1-2 секунды
  • За это время заказ может быть "не виден" в доставке
  • Через пару секунд всё согласуется

Когда допустимо:

  • Социальные сети (лайки, комментарии)
  • Аналитика и отчёты
  • Кэширование
  • Рекомендательные системы
  • Логи и аудит

Когда НЕ допустимо:

  • Финансовые транзакции (перевод денег)
  • Бронирование билетов (двойная продажа)
  • Инвентаризация (учёт товаров)
  • Там, где нужна строгая согласованность

CAP теорема: Consistency, Availability, Partition Tolerance — можно выбрать только 2.

  • CA: согласованность + доступность (реляционные БД)
  • CP: согласованность + устойчивость (ZooKeeper)
  • AP: доступность + устойчивость (Cassandra, DynamoDB) — eventual consistency
Compensating Transaction — компенсирующие транзакции.
mid

Compensating Transaction — действие, отменяющее эффект предыдущей операции.

Пример Saga с компенсациями:

// Шаги и компенсации
1. OrderService.CreateOrder()
   → Если ошибка: компенсация не нужна (ничего не создано)

2. PaymentService.ProcessPayment()
   → Компенсация: PaymentService.RefundPayment()

3. InventoryService.ReserveStock()
   → Компенсация: InventoryService.ReleaseStock()

4. DeliveryService.ScheduleDelivery()
   → Компенсация: DeliveryService.CancelDelivery()

// Если шаг 3 упал:
- Компенсация шага 3: ReleaseStock()
- Компенсация шага 2: RefundPayment()
- Компенсация шага 1: не нужна

Реализация компенсаций:

public class OrderOrchestrator
{
    public async Task ExecuteAsync(Order order)
    {
        var compensations = new Stack<Func<Task>>();
        
        try
        {
            // Шаг 1
            await _orderService.CreateOrderAsync(order);
            compensations.Push(() => _orderService.CancelOrderAsync(order.Id));
            
            // Шаг 2
            await _paymentService.ProcessPaymentAsync(order);
            compensations.Push(() => _paymentService.RefundPaymentAsync(order.Id));
            
            // Шаг 3
            await _inventoryService.ReserveStockAsync(order);
            compensations.Push(() => _inventoryService.ReleaseStockAsync(order.Id));
            
            // Шаг 4
            await _deliveryService.ScheduleDeliveryAsync(order);
            compensations.Push(() => _deliveryService.CancelDeliveryAsync(order.Id));
            
            // Все успешно
        }
        catch (Exception)
        {
            // Откат в обратном порядке
            foreach (var compensate in compensations)
                await compensate();
            throw;
        }
    }
}
Outbox Pattern — как гарантировать доставку событий.
mid

Outbox Pattern — гарантированная доставка событий через БД.

Проблема:

  • Сохранение заказа в БД + публикация события
  • Если после БД произошла ошибка — событие потеряно
  • Если событие опубликовано, а БД не сохранила — противоречие

Решение — Outbox:

// 1. В одной транзакции сохраняем заказ + событие
public async Task CreateOrderAsync(Order order)
{
    using var transaction = await _dbContext.Database.BeginTransactionAsync();
    try
    {
        await _dbContext.Orders.AddAsync(order);
        
        // Сохраняем событие в Outbox
        var outbox = new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "OrderCreated",
            Data = JsonSerializer.Serialize(order),
            CreatedAt = DateTime.UtcNow
        };
        await _dbContext.OutboxMessages.AddAsync(outbox);
        
        await _dbContext.SaveChangesAsync();
        await transaction.CommitAsync();
    }
    catch { await transaction.RollbackAsync(); throw; }
}

// 2. Фоновый процесс доставки
public class OutboxProcessor : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var messages = await _dbContext.OutboxMessages
                .Where(m => !m.Processed)
                .OrderBy(m => m.CreatedAt)
                .Take(100)
                .ToListAsync(stoppingToken);
            
            foreach (var msg in messages)
            {
                try
                {
                    // Публикуем событие
                    await _eventBus.PublishAsync(msg.Type, msg.Data);
                    
                    // Отмечаем обработанным
                    msg.Processed = true;
                    msg.ProcessedAt = DateTime.UtcNow;
                    
                    await _dbContext.SaveChangesAsync(stoppingToken);
                }
                catch (Exception ex)
                {
                    // Логируем ошибку, сообщение останется в Outbox
                    _logger.LogError(ex, "Failed to process outbox message {Id}", msg.Id);
                    
                    // Оставляем для повторной попытки
                    if (msg.RetryCount >= 3)
                    {
                        msg.Failed = true;
                        msg.FailedAt = DateTime.UtcNow;
                        await _dbContext.SaveChangesAsync(stoppingToken);
                    }
                    else
                    {
                        msg.RetryCount++;
                        await _dbContext.SaveChangesAsync(stoppingToken);
                    }
                }
            }
            
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}
